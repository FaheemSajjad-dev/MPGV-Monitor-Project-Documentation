\section*{\huge Abstract}
This thesis presents \textbf{MPGV Monitor}, a web application for exploring Icelandic earthquake data from June 2020 onwards. The work addresses a data-integration problem that arises because the Icelandic Meteorological Office MPGV archive and Quakes API provide partially overlapping records with differences in time, location, magnitude, and depth. The objective is to construct a traceable merged catalogue and make it available through connected spatial and analytical views, rather than displaying the two sources independently.

The backend scrapes MPGV records, retrieves recent Quakes API events, and reconciles candidate pairs using temporal, spatial, and magnitude constraints. For a uniquely matched event, the current policy retains the MPGV time and magnitude while using the Quakes API coordinates and depth. Events without an acceptable unique match remain explicitly identified as MPGV-only records. This provenance is retained in the database and API so that depth-based analysis can use matched values by default and label raw MPGV-only depths as unverified when a user chooses to include them. Events with magnitude $M \geq 3.0$ are stored in an SQLite database through SQLAlchemy, and APScheduler initiates ingestion and reconciliation every three minutes. Flask provides the catalogue, analysis limits, volcano metadata, CSV export, and on-demand ShakeMap lookup through REST endpoints.

The final frontend is implemented with React and Vite. MapLibre GL renders vector and raster map views and the heatmap, while deck.gl renders interactive earthquake markers. The map supports time and magnitude filtering, timeline- and magnitude-based colour encodings, satellite and terrain views, volcano and fault/fissure overlays, a latitude/longitude grid, recent selections, and event-level ShakeMap access. A separate Insights page, implemented with Recharts, applies date, magnitude, depth-quality, provenance, and time-grouping filters to the same catalogue. It provides summary statistics, interactive charts, sortable tables, filtered CSV export, print-ready output, and a link from each listed event back to the map. Both views adapt their controls and information panels for desktop and mobile layouts.

The principal contribution is an end-to-end pipeline that preserves source provenance from acquisition and reconciliation through map-based and aggregate presentation. The application also documents the evolution from a static Folium prototype and a Google Maps implementation, through Leaflet, to a MapLibre GL and deck.gl architecture without Google Maps credentials or a Leaflet compatibility layer. MPGV Monitor is a research application rather than a replacement for operational seismic monitoring. Remaining limitations include accessibility, external-service and tile-licensing dependencies, HTTP-only deployment on the current university server, and the concurrency constraints of SQLite.

\section{Introduction}
\label{sec:introduction}
Icelandic seismicity is monitored continuously, but the public interfaces through which it can be explored are mainly designed for recent-event awareness. The Icelandic Meteorological Office (IMO), for example, publishes a map of earthquakes detected during the previous 48 hours \cite{imo_quakes_48h}. Global services operated by the U.S. Geological Survey and the European-Mediterranean Seismological Centre provide broader geographical coverage \cite{usgs_latest_map,emsc_home}, while the IRIS Interactive Earthquake Browser supports longer-term catalogue exploration \cite{iris_ieb_app}. These services are valuable in their intended settings, but none is organised around the specific combination required by this project: reconciling the two Icelandic data sources used here, retaining a multi-year catalogue, and connecting individual events with relevant Icelandic ShakeMap products.

\textbf{MPGV Monitor} was developed to investigate how that combination could be provided through a single web application. The backend scrapes the IMO MPGV archive, retrieves recent event metadata from the IMO Quakes API, and reconciles the two sources into a merged catalogue. The current application concentrates on events of magnitude $M \geq 3.0$ from June 2020 onwards. A scheduled ingestion cycle runs every three minutes, while the public interface reads from the merged table rather than exposing the two source catalogues separately.

The project has passed through several frontend implementations. The first prototype generated a static Folium map on the server, and a later version used the Google Maps JavaScript API. Google Maps provided a workable interactive prototype, but it introduced an API-key and billing dependency that was undesirable for an academic system intended for institutional deployment. Leaflet was subsequently used as an open-source replacement. In the final implementation described by this thesis, Leaflet has also been removed: MapLibre GL renders the map and its tile layers, while deck.gl renders the interactive earthquake markers. This separation allows the application to use the same WebGL map for vector, raster, and heatmap views, and avoids maintaining parallel mapping engines.

This chapter introduces the motivation and scope of the work, states the problem addressed by the application, and summarises its principal contributions. Detailed discussion of the scientific context, data pipeline, backend, frontend, and deployment is left to the later chapters.

\subsection*{Context and Motivation}
Iceland lies on the Mid-Atlantic Ridge at the divergent boundary between the North American and Eurasian plates. Its tectonic setting is complicated by the mantle hotspot beneath the island, so earthquakes may be associated with plate motion, crustal faulting, magma movement, or interaction between these processes. The resulting activity includes persistent low-magnitude seismicity, concentrated earthquake swarms, and less frequent damaging events. This scientific background is considered in more detail in the following chapter; for the present work, its main consequence is that useful exploration must cover both space and time. A short list of recent epicentres cannot show how a swarm developed over several months or how activity shifted between volcanic systems.

Recent unrest on the Reykjanes Peninsula made this limitation particularly visible during the development of the project. Large numbers of events may occur within a small region, and the significance of an individual point depends partly on its relationship to the surrounding sequence. A map therefore needs filtering and alternative visual encodings, but it also needs access to a catalogue long enough for comparison. The application is not intended to replace operational monitoring or support eruption prediction. Its purpose is narrower: to make the available catalogue easier to inspect and to expose the provenance of records assembled from more than one source.

Data quality is part of this problem. MPGV and the Quakes API do not provide identical records, and a single physical event may appear in both with small differences in time, coordinates, magnitude, or depth. Displaying the feeds together without reconciliation would create duplicates and could give a misleading impression of event density. Conversely, discarding one source would lose either the continuity of the MPGV archive or the more detailed metadata supplied by the Quakes API. The backend therefore treats source integration as a distinct stage before visualisation rather than attempting to hide inconsistencies in the user interface.

\subsection*{Need for a Modern Monitoring Tool}
The design problem was not simply to place earthquake markers on a web map. Existing public platforms already do that effectively for recent situational awareness. MPGV Monitor instead addresses three connected requirements. First, it maintains an Iceland-focused catalogue over a period beginning in June 2020 and provides day, week, month, and year views through a continuous time-window control. Second, it reconciles MPGV records with Quakes API records before presenting them. Third, it supports both map-based inspection and aggregate exploration without requiring the user to move between unrelated services.

The ingestion pipeline uses APScheduler to initiate a three-minute cycle. Each cycle updates the MPGV source table, requests recent Quakes API events, refreshes volcano metadata from the IMO EPOS service, and rebuilds the merged catalogue from June 2020 onwards. Candidate earthquake records are compared using temporal, spatial, and magnitude constraints. For a matched record, the current policy retains the MPGV time and magnitude but uses the Quakes API coordinates and depth. Records without a unique acceptable match remain in the catalogue with an MPGV-only status. This distinction is important in the Insights page: matched depths are treated as the reference set, whereas raw MPGV-only depths are excluded from depth analysis by default and can be included only as explicitly labelled unverified values.

SQLite was selected because the catalogue and deployment are currently served by a single application instance, and its file-based operation keeps local setup and transfer straightforward. It is used with SQLAlchemy and write-ahead logging. This is an appropriate compromise for the present scale, but it is not presented as a general solution for a high-concurrency monitoring service. The application also limits public responses by date window and row count, applies per-client rate limits, and protects state-changing maintenance routes with an administrator token in production. These controls do not replace infrastructure-level security, but they prevent the research deployment from exposing unrestricted ingestion and reconciliation operations.

\subsection*{System Features}
The backend is a Flask application using SQLAlchemy for persistence. It exposes the merged earthquake catalogue, volcano records, catalogue limits for analysis, CSV export, health information, and on-demand ShakeMap lookup through a small REST interface. Normal ingestion is initiated by the scheduler; separate authenticated maintenance endpoints are available for controlled administrative use. The React 18 frontend is built with Vite and served from the same Flask deployment in production.

The main map uses MapLibre GL for the map view and deck.gl scatterplot layers for earthquake markers. Users can filter the displayed events by time and minimum magnitude, and can colour markers either by their position within the selected timeline or by magnitude. Four map modes are available: an OpenFreeMap vector map, Esri satellite imagery, an IMO terrain map, and a density-oriented heatmap over a dark OpenFreeMap style. The heatmap deliberately suppresses individual marker selection so that it represents spatial concentration rather than a second marker view. Optional overlays show IMO EPOS volcano metadata, EGDI/HIKE fault and fissure linework, and an Iceland-focused latitude/longitude grid. Selecting an earthquake opens an information card and, where a validated product is available, provides access to the corresponding ShakeMap. A recent-selections panel allows previously inspected events to be reopened.

The map is complemented by an Insights page built with Recharts. It applies date, magnitude, depth, provenance, and time-grouping filters to the same merged catalogue and presents summary statistics, five interactive charts, and tables of recent and strongest events. Filtered results can be exported as CSV or prepared for printing to PDF, and a \emph{View on Map} action returns an event to the map while preserving the current map state. Both pages use responsive layouts; mobile presentation changes the arrangement of controls, tables, and information panels rather than providing a separate application.

These features are intended to support exploratory use rather than automated scientific interpretation. In particular, the charts do not infer causes or forecast activity, and the ShakeMap link does not constitute an independent validation of an earthquake. The interface exposes available records and their provenance so that users can examine patterns while remaining aware of the limits of the underlying data.

\subsection*{Contributions and Future Directions}
The principal contribution of the project is an end-to-end method for presenting two partially overlapping Icelandic earthquake sources as a traceable merged catalogue. The implementation does not simply remove apparent duplicates. It records whether a row was uniquely matched or remains MPGV-only, retains match diagnostics, and carries that provenance into the API and analytical interface. This makes the assumptions of the merge visible and allows depth-dependent analysis to distinguish reference values from unverified source values.

A second contribution is the integration of that catalogue into two connected forms of exploration. The map supports spatial inspection, temporal and magnitude filtering, alternative colour encodings, contextual overlays, and event-level ShakeMap access. The Insights page provides aggregate summaries, charts, tables, and filtered exports using the same data and depth-quality policy. The \emph{View on Map} interaction links these forms without treating them as separate tools. A third contribution is the evolution of the frontend away from static Folium output and paid Google Maps access, through a Leaflet version, to a MapLibre GL and deck.gl architecture with no Google Maps credentials or Leaflet compatibility layer.

Several limitations remain. Keyboard and screen-reader support require further work, and the colour schemes need formal accessibility evaluation. The present Pluto deployment is served over HTTP, so HTTPS depends on server-level configuration outside the Flask application. External tile and data-provider licensing also requires review before formal institutional deployment. SQLite remains suitable for the current single-instance research deployment but would need to be reconsidered if write concurrency or the number of application workers increased substantially.

Possible extensions include a native mobile client, more specialised analyses such as Gutenberg--Richter and clustering views, and carefully evaluated forecasting experiments. These are proposed directions rather than completed parts of the system. The work reported in this thesis is the implemented ingestion, reconciliation, map, and Insights pipeline. Together, these components show that the central difficulty in a multi-source earthquake monitor is not marker rendering alone, but preserving data provenance and consistent behaviour as records move from acquisition through reconciliation to several forms of presentation.

\section{Background and Related Work}

Building a seismic monitoring tool for Iceland turned out to involve more prior work than I initially expected. Once the scope expanded beyond a simple map of recent earthquakes into a system that reconciles two catalogues, classifies markers by colour-encoded magnitude, links events to ShakeMap products, and stays running on a three-minute polling loop, it became clear that each of those pieces had been addressed in some form before, and reading that work saved real time during implementation. This chapter covers what I found most relevant: Iceland's seismotectonic setting, the web mapping libraries and tile delivery methods that informed the frontend architecture, existing earthquake platforms and why they fall short for multi-year exploration, how colour encoding of seismic data has been studied in the literature, the multi-source integration problem and how others have tackled deduplication, the backend patterns that guided the Flask and APScheduler design, and the ShakeMap system that MPGV Monitor hooks into at the event level.

\subsection{Seismotectonic Context of Iceland}

Iceland sits on the Mid-Atlantic Ridge, the divergent boundary between the North American and Eurasian plates, which are pulling apart at roughly 18--20\,mm per year. A mantle hotspot underneath the island adds a second source of heat and magma on top of the spreading tectonics, which is why Iceland has such an unusually dense collection of active volcanic systems relative to its size. The result is a country where earthquakes and eruptions are not rare events but a near-constant background condition that any monitoring tool has to account for.

The island's seismicity is concentrated in a handful of zones. The \textbf{South Iceland Seismic Zone} (SISZ) is a left-lateral transform belt that transfers spreading motion between two volcanic rift zones. It has a history of M\,6+ events; the most recent destructive sequences occurred in June 2000 and May 2008. Further southwest, the \textbf{Reykjanes Peninsula} is where the mid-ocean ridge comes ashore, and it was geologically quiet for roughly 800 years before abruptly awakening around 2020. Between 2021 and 2024 the peninsula experienced a series of magmatic intrusions, large swarms, and six volcanic fissure eruptions in close succession -- a sequence that flooded existing 48-hour monitoring portals with event counts they were never designed to handle, and that was a direct motivation for building a tool with a multi-year time window. In the north, the \textbf{Tjörnes Fracture Zone} (TFZ) connects the Northern Volcanic Zone to the offshore Kolbeinsey Ridge and is capable of generating M\,6--7 events. The \textbf{Eastern Volcanic Zone} (EVZ), home to Katla, Hekla, Grímsvötn, and Bárðarbunga among others, adds volcanic earthquake swarms tied to magma intrusion and caldera subsidence.

Iceland's national monitoring network is operated by the Icelandic Meteorological Office (IMO), which runs a dense grid of broadband and short-period seismometers and publishes detected events in near real time through the Skjálftalísa REST API. The MPGV catalogue is a separate, independently maintained archive that covers a longer historical span and was built using a different detection workflow. These two catalogues do not agree perfectly -- they have different magnitude completeness thresholds, different reported attributes, and different update latencies -- which is exactly what makes building a merged view non-trivial and is the problem that much of the backend is designed to solve.

\subsection{Interactive Web Mapping: Frameworks and Tile Architectures}

Web-based interactive mapping has changed considerably over the past decade. What used to require a desktop GIS installation can now run entirely in a browser, and the ecosystem of libraries and tile services that makes this possible has matured to the point where a small team can build a capable geospatial application without deploying any map infrastructure of its own.

\textbf{Leaflet.js} is the library MPGV Monitor is built on. It is widely used in web mapping projects because it is lightweight (around 42\,kB gzipped), has a clean layer model, and works reliably across browsers without WebGL. Leaflet represents a map as a stack of layers in a defined Z-order: a base tile layer at the bottom, then GeoJSON or custom marker layers on top, with controls sitting above everything else. Each layer gets lifecycle hooks for pan and zoom events, which keeps the visible content in sync with the viewport. \textbf{React-Leaflet} wraps Leaflet's imperative API in React components, so the same props-and-state patterns that control the rest of the UI also control which layers are shown, what markers are rendered, and when they update \cite{Netek2023}.

The tile architecture in MPGV Monitor is not uniform -- different basemap modes use different delivery mechanisms, for reasons that are worth explaining. The \textbf{satellite} and \textbf{dark-mode} basemaps use raster tiles from Esri's ArcGIS REST services (\texttt{server.arcgisonline.com}). Esri's World Imagery and Canvas Dark Gray Base services work without an API key, deliver pre-rendered PNG tiles up to zoom level 17, and plug directly into Leaflet's standard \texttt{TileLayer} component. A few tile-fetch options were tuned to improve pan/zoom smoothness: the tile buffer was widened to four rows in each direction to reduce blank edges during fast panning, and retina tile requests were turned off to avoid unnecessary double-resolution fetches on high-DPI screens.

The \textbf{roadmap} basemap takes a different path. It uses a self-hosted \textbf{PMTiles} file, which is a single binary container for vector tiles that supports HTTP range requests. The browser asks for only the byte ranges it needs for the current viewport rather than fetching a tile image for each tile slot, which means no tile server is needed on the backend -- the file just sits on the static file server alongside the HTML and JavaScript. Rendering is handled by \textbf{MapLibre GL} through the \texttt{@maplibre/maplibre-gl-leaflet} adapter, which embeds the MapLibre GL canvas inside the Leaflet layer stack. The cartographic style comes from the Protomaps Themes Base library, but it was substantially trimmed for the Iceland seismic monitoring use case: building footprints, land-use fills, railway lines, POI labels, and address numbers were all removed since they add visual clutter at the zoom levels used for earthquake browsing. A custom glacier fill layer was added to handle Iceland's ice caps, and the background colour outside the tile data extent was changed from the default mid-grey to the ocean colour so that zoomed-out Atlantic views look correct rather than showing a hard grey edge around the Iceland data file.

Running two rendering engines simultaneously -- MapLibre GL for vector tile rasterisation and Leaflet for everything else -- required some care. The MapLibre canvas is placed below all Leaflet marker panes in Z-order and its \texttt{pointer-events} CSS property is set to \texttt{none}, so clicks and scroll events fall through to the Leaflet layer. All of MapLibre's own navigation handlers (pan, zoom, rotate, keyboard shortcuts) are disabled at startup; Leaflet remains the sole controller of the viewport. Netek et al.\ measured that vector tiles consistently deliver lower bandwidth usage and shorter tile load times than raster tiles at equivalent zoom levels, with the gap widening at higher zoom \cite{Netek2020}. This is part of why PMTiles was chosen for the default roadmap view even though raster tiles from Esri would have been simpler to implement. For satellite and dark-mode, photorealistic imagery and a pre-styled dark canvas are not things vector tiles can provide, so raster delivery makes sense there.

The \textbf{heatmap} mode is technically a fourth basemap mode but works differently from the other three. Rather than switching the tile source, it adds a canvas overlay rendered by the \texttt{leaflet.heat} plugin on top of whichever raster or vector base is showing. Each earthquake is passed to the plugin as a weighted point, with the weight derived from its magnitude, and the plugin computes a kernel-density surface from those points and draws it as a colour gradient. The overlay re-draws whenever the magnitude filter or time window changes, and since all the filtering happens in JavaScript on the already-downloaded catalogue, there is no server round-trip involved \cite{Netek2023}.

\subsection{Existing Earthquake Visualization Platforms}

Before building yet another earthquake map, it made sense to spend time with what already exists. The short version is that the existing tools are good at what they were designed for, but none of them was designed for the kind of multi-year, multi-source exploration this project needed.

The \textbf{Icelandic Meteorological Office} map shows the last 48 hours of automatically detected events, colour-coded by depth \cite{imo_quakes_48h}. It updates continuously and is the main public-facing tool for earthquake awareness in Iceland. However, it has no magnitude threshold slider, no way to look further back than 48 hours, and no alternative visual representation beyond the depth colour coding. The \textbf{USGS Earthquake Hazards Program} portal offers a global view with basic magnitude and date filters \cite{usgs_latest_map}, and the \textbf{EMSC} provides a similar multi-agency aggregation \cite{emsc_home}. All three are operationally excellent for situational awareness -- if you want to know what happened in the last day or two, they work well. The problem is that they were designed for that use case and are fairly rigid outside of it.

Mazzei and Quaroni built a WebGIS application specifically for seismic risk assessment on infrastructure networks, rendering earthquake hypocentre clouds, fault surfaces, and building vulnerability data together in a single 3D scene \cite{Mazzei2022}. Their work shows that a purpose-built seismic interface, rather than a general GIS tool adapted for earthquake data, much better serves the analytical needs of domain users. The architecture they chose -- a REST backend that pre-processes data and delivers GeoJSON to a WebGL frontend -- also cleanly separates what belongs on the server (data integration, deduplication, spatial joins) from what belongs in the browser (rendering, filtering, user interaction). That same separation guided the design of MPGV Monitor, even though the rendering is 2D rather than 3D. Their observation that combining source parameters with derived products in a single interface reduces the navigation burden on users was also relevant: in MPGV Monitor that means linking earthquake events directly to ShakeMap products rather than making users find them separately.

Netek et al.\ ran a systematic comparison of server-side versus client-side geospatial processing, testing operations like polygon intersection and buffer queries across datasets of varying size \cite{Netek2023}. Their finding that client-side JavaScript can match or outperform server-side processing for moderate-sized datasets -- because the network round-trip disappears once the data is already in the browser -- directly informed the decision to send the entire merged catalogue to the frontend in one request rather than having the server apply the magnitude and time-window filters. In practice this means that adjusting the magnitude slider or moving the time window in MPGV Monitor produces an immediate re-draw with no waiting, which matters a lot for an interface where those controls are adjusted repeatedly during exploration.

\subsection{Visual Encoding of Seismic Data}

How earthquakes are drawn on a map has a real effect on what patterns become visible and which ones stay hidden. Traditional printed seismicity maps typically encode magnitude as circle radius and depth as colour, following conventions that date back decades. On an interactive web map, those conventions run into some practical problems. When hundreds of events are plotted at a region that is seismically very active, size-encoded markers overlap into a dense mass where individual events are indistinguishable. Depth colour coding is also less useful in an interface that already needs to distinguish magnitude levels, so some re-thinking of the encoding was needed.

In MPGV Monitor's scatter view, all markers are drawn as \textbf{fixed-size circles} with a 10-pixel diameter. Magnitude is encoded in colour instead of size. The main reason for this is density: at zoom levels where hundreds of events appear in the viewport, a fixed size keeps the markers identifiable while colour still communicates magnitude to the eye even in a crowded region, because the dominant tone of a dense cluster reflects whether most of the events in it are large or small. The palette runs five stops from a light blue-grey (\texttt{\#8aa0c0}) near the lower display threshold to near-black (\texttt{\#060820}) at the top of the magnitude range. Colour is computed per marker at render time by normalising each event's magnitude against the current filtered maximum and interpolating through the stops.

There is also a \emph{twilight} colour mode, which assigns each event a hue based on the calendar month of its UTC origin time rather than its magnitude. The hues run through a narrow red-violet band from dark rose in January to near-black in December. The purpose of this is to make seasonal patterns in seismicity visible without any additional filtering step. The Reykjanes Peninsula, for instance, shows some seasonal variation in event rates linked to glacial load changes, and having a mode where month reads directly from colour makes that pattern immediately apparent rather than requiring the user to filter by date range and compare two different views.

The science of colour choice for visualisation data is more nuanced than it might appear. Crameri, Shephard, and Heron systematically reviewed colour map usage across published Earth science figures and showed through perceptual experiments that rainbow-style palettes -- which are very commonly used in geoscience -- introduce false visual boundaries and can make analysts perceive features in data that are not actually there \cite{Crameri2020}. Their recommendation for sequential data (anything with a natural ordering from low to high) is to use palettes that vary monotonically in perceived lightness without hue reversals. The blue-to-dark palette in MPGV Monitor follows this: every step darker means a stronger earthquake, with no colour cycling that might accidentally suggest a non-monotonic relationship. The same principles shaped the twilight mode, where the goal is categorical rather than ordinal -- distinguishing twelve months -- so a narrow hue range is used where the differences are visible but none of the months is perceptually ``higher'' than another.

One further issue with rendering earthquake data in React is performance. React's reconciliation loop re-renders every child component when state changes, and for a catalogue of several thousand events that means recreating thousands of marker elements on every filter adjustment. MPGV Monitor avoids this by computing the filtered event array with \texttt{useMemo} (so it is only recalculated when the actual filter values change) and managing the Leaflet marker layer group directly through an imperative \texttt{useRef} reference rather than through React's tree. This way the browser patches only the markers whose colour or visibility changed rather than tearing down and rebuilding the full set.

\subsection{Multi-Source Data Integration}

Running a monitoring system from a single catalogue is straightforward. Running it from two is considerably more work, because the same earthquake will typically appear in both catalogues as two separate records with slightly different origin times, depths, and magnitudes -- depending on which agency's detection pipeline processed it and how quickly. Without deduplication, the merged catalogue inflates event counts and makes the map misleading.

Melgarejo-Hern{\'a}ndez et al.\ built a modular ingestion framework specifically for this problem, targeting near-real-time aggregation from multiple open seismic web providers \cite{MelgarejoHernandez2026}. Their approach matches candidate duplicate pairs by applying three simultaneous tolerance windows: origin-time difference, epicentral distance (as a Haversine calculation), and magnitude difference. If a pair of records passes all three windows, they are treated as the same event and the richer record is kept; otherwise both are retained independently. The exact threshold values depend on the precision of the contributing networks. For a dense national network like the IMO network in Iceland, temporal windows of a few seconds and spatial windows of a few kilometres are generally sufficient to catch duplicates without falsely merging distinct events.

This model of distributed, service-oriented seismic data access is now standard across European seismology. Strollo et al.\ describe EIDA (European Integrated Data Archive), a federated system that connects twelve national data centres through FDSN-compliant web services and makes waveform archives from over 12,000 stations accessible through a uniform REST interface \cite{Strollo2021}. The Skjálftalísa API is Iceland's national equivalent: a lightweight HTTP service that exposes IMO event data as JSON without requiring any special client software or credentials, which is what makes it practical to scrape automatically from a Python backend.

MPGV Monitor's reconciliation pipeline works along the same lines as the Melgarejo-Hernández et al.\ framework. Each scraping cycle retrieves fresh events from the MPGV archive and from Skjálftalísa, then runs a pairwise matching pass across the combined set of new arrivals and existing catalogue entries. A match is accepted when all three offsets -- temporal (typically 30--60 seconds), spatial (typically 10--20\,km Haversine distance), and magnitude -- fall inside their respective thresholds. The winning record gets a provenance flag noting whether it came from MPGV, Skjálftalísa, or was matched from both, and is written to the \texttt{merged\_events} table. Unmatched events go in with their source flag set accordingly. The Flask API then serves the whole merged catalogue through a \texttt{GET /earthquakes} endpoint, consistent with the REST delivery model described by Strollo et al.\ \cite{Strollo2021}. All filtering -- by time window, by magnitude threshold -- happens client-side in the browser from this single payload rather than being applied as server-side query parameters, which simplifies the API and avoids the need for the server to maintain per-user state \cite{Netek2023}.

\subsection{Backend Architecture}

Running a seismic monitoring application involves a background process that wakes up periodically, fetches new events, reconciles them against what is already stored, and writes the results to a database -- all while an HTTP server sits alongside it serving API requests to the frontend. Getting those two things to coexist without locking each other out is the main architectural challenge for a lightweight single-process deployment.

MPGV Monitor uses \textbf{Flask} as the HTTP layer. Flask is a micro-framework: it provides routing, request parsing, and response serialisation and leaves everything else to the developer. For this application that minimalism is an advantage, since the backend does not need an authentication system, a template engine, or an admin interface. The entire application lives in a single \texttt{app.py} file that wires a SQLAlchemy ORM to a SQLite database, starts a background scheduler, and registers half a dozen routes.

The database engine is \textbf{SQLite}. SQLite stores the entire earthquake catalogue as a single file on disk (\texttt{data/earthquakes.db}), which keeps deployment simple -- no database server to configure or maintain. Its access pattern is a good fit for this workload: writes happen once per scraping cycle in a short batch transaction, while reads are frequent but simple full-table scans that return the whole catalogue. The one concurrency concern is that SQLite's default journal mode serialises all writes and reads, which could cause the scheduler thread to block API requests while it is committing new events. This is resolved by enabling \textbf{WAL mode} (Write-Ahead Logging) at startup. In WAL mode, readers work against a stable checkpoint while the writer appends to a separate log, so the two threads do not block each other. \texttt{PRAGMA synchronous = NORMAL} is also set to reduce the number of fsync calls -- for a monitoring application where missing a single scraping cycle is inconsequential, full durability at every commit is not worth the latency cost.

The scheduler is \textbf{APScheduler}'s \texttt{BackgroundScheduler}, which runs ingestion jobs in a daemon thread within the same Python process. Each job has its own interval -- Skjálftalísa is polled more frequently than the MPGV archive, which changes more slowly -- and fires independently of HTTP traffic. Because everything runs in one process, the whole application deploys as a single \texttt{gunicorn} worker; there is no need for a separate worker dyno or message queue, which matters for keeping hosting costs down on a platform like Render.

The API layer itself is deliberately thin. Routes do nothing beyond querying SQLAlchemy and serialising the results to JSON. Derived fields like formatted date strings and colour assignments are computed in the frontend, keeping the API stable and easy to inspect during debugging. The one exception is \texttt{/shakemap\_lookup}, which takes an event's datetime and coordinates and runs a Haversine search against a cached ShakeMap index on the server. That computation belongs on the server because the ShakeMap index is not sent to the frontend and because running it client-side against an indeterminate number of candidates would be awkward.

\subsection{ShakeMap and Derived Hazard Products}

An earthquake catalogue records where and when a rupture occurred and how large it was, but says nothing about what the shaking was actually like at any given location on the ground. Ground motion depends on distance from the rupture, the radiation pattern, the propagation path, and local site amplification -- factors that vary considerably from event to event and place to place. ShakeMap, maintained and operated by the USGS, addresses this by combining seismic station recordings with ground-motion prediction equations to produce spatial maps of peak ground acceleration, peak ground velocity, and Modified Mercalli Intensity shortly after a significant earthquake \cite{ShakeMapManual}. ShakeMaps are updated as more station data arrive, and they are widely used by emergency managers, insurers, and structural engineers to assess damage potential and prioritise response.

The problem for an earthquake monitoring interface is that ShakeMaps and earthquake catalogues live in completely separate places. The USGS catalogue assigns events a unique identifier, and ShakeMap products are keyed to that identifier -- not to geographic coordinates or origin time. If a user spots a cluster in MPGV Monitor and wants to check whether any of the events caused significant shaking, they have to leave the application, figure out the corresponding USGS event ID (which may differ from the IMO or MPGV identifier for the same event), navigate to the ShakeMap portal, and search manually. In practice, most non-specialist users never bother with that workflow even when the ShakeMap would directly answer their question.

MPGV Monitor addresses this by building a lookup at the event level. When the detail panel opens for a specific earthquake, the frontend sends a request to \texttt{/shakemap\_lookup} with the event's UTC origin time and decimal-degree coordinates. The backend compares these against a cached index of recent USGS ShakeMap events, finds the entry with the smallest combined temporal and spatial distance, and returns its URL if it falls within the acceptance thresholds. The detail panel then shows a direct link to the ShakeMap product. The user goes from noticing an event to viewing its shaking map in a single click without leaving the application or knowing anything about USGS event identifiers.

\subsection{Where Existing Approaches Fall Short}

After going through the platforms above and reading the relevant papers, three problems kept coming up that pointed toward what MPGV Monitor would need to do.

The first is that every operational portal draws from a single catalogue \cite{imo_quakes_48h, usgs_latest_map, emsc_home}. For Iceland, this is a real gap: the MPGV archive and the Skjálftalísa API both cover Icelandic seismicity, but through different detection workflows, with different magnitude completeness levels and different update delays. There is no public interface that shows both together or even acknowledges the discrepancy. Melgarejo-Hern{\'a}ndez et al.\ make the same point about multi-network monitoring more broadly \cite{MelgarejoHernandez2026}. The reconciliation pipeline in MPGV Monitor grew directly out of that gap.

The second problem is that existing interfaces stop at about 48 hours. That is fine for a daily briefing but not much use for a researcher trying to understand how the Reykjanes swarms evolved across 2021--2024, which zones lit up first, and how the eruption sequences connected to the earlier unrest. The IRIS IEB goes further back but is not Iceland-specific and does not combine multiple Icelandic sources \cite{iris_ieb_app}. Mazzei and Quaroni's point about purpose-built seismic interfaces providing much better analytical depth than general-purpose tools applies directly here \cite{Mazzei2022, Netek2023}.

The third is the ShakeMap gap. Earthquake locations and shaking-intensity products live in completely separate places, and the workflow needed to connect them, looking up a USGS event ID, navigating to the ShakeMap portal, searching by approximate time, is one that most non-specialist users simply will not bother with \cite{ShakeMapManual}. The inline ShakeMap lookup in MPGV Monitor was added specifically to close that gap with a single click.

\subsection{Positioning of MPGV Monitor}

MPGV Monitor is not trying to replace the IMO portal or the USGS viewer. It has a much narrower focus: Iceland-specific, multi-year, with a reconciled catalogue drawn from two sources instead of one. The target user is someone who already knows Iceland is seismically active and wants to explore that activity over a longer time span than 48 hours, with enough filtering and visual control to actually see patterns.

The literature reviewed above shaped specific design decisions. The reconciliation approach, matching events from MPGV and Skjálftalísa by time, distance, and magnitude, follows the framework described by Melgarejo-Hern{\'a}ndez et al.\ \cite{MelgarejoHernandez2026}, and the resulting API follows the REST conventions that Strollo et al.\ document for FDSN-compliant seismic services \cite{Strollo2021}. The choice of PMTiles vector tiles for the roadmap view and Esri raster tiles for satellite and dark mode reflects Netek et al.'s finding that vector delivery wins on bandwidth at equivalent zoom levels, while raster remains the practical option for photorealistic imagery \cite{Netek2020}. The colour palette for earthquake markers uses a monotonically darkening blue scale rather than a rainbow ramp, in line with Crameri et al.'s work on how rainbow palettes introduce false perceptual boundaries in geoscience figures \cite{Crameri2020}. The decision to ship the full merged catalogue to the browser in a single response and filter client-side came from Netek et al.'s observation that for datasets of this size, the server round-trip costs more than the in-browser computation \cite{Netek2023}. And the inline ShakeMap link in the event panel closes the catalogue-to-hazard-product gap that the ShakeMap manual itself describes but that no Iceland-facing interface currently bridges \cite{ShakeMapManual}.

Mazzei and Quaroni's conclusion that a purpose-built seismic WebGIS consistently serves domain users better than a general-purpose tool adapted for earthquake data \cite{Mazzei2022} is probably the most direct validation for the project's overall direction. What makes MPGV Monitor different from what they built is the Iceland-specific context: two catalogues that disagree and must be reconciled, an unusually active eruption period that made multi-year access essential, and institutional data sources (MPGV, Skjálftalísa, EPOS) that no general-purpose tool is wired to consume.

\section{Project Overview}

\subsection{Initial Setup}
The project went through several distinct phases before reaching its current form. The earliest version did most of its work on the server: Flask scraped the data, Folium rendered a static map in Python, and the frontend was little more than a page that displayed whatever the backend had generated. That worked as a proof of concept, but it meant every interaction required a round trip to the server, the time slider was barely functional because filtering was coupled to the backend scraping logic, and adding new features was slow because changing one thing tended to break another.

    \caption{Early prototype of the MPGV Monitor frontend using a server-side Folium map. All rendering was handled in Python, resulting in a static output with no client-side interactivity or time-slider support.}

Switching to a Vite + React frontend and a Flask API backend fixed the core problem: the browser now owns the rendering and filtering logic, so changing the time window or magnitude threshold no longer requires a server round-trip. That shift also made the time slider and magnitude scale practical to build, since they are purely client-side controls that operate on data already in memory.

Python remains the core language of the backend due to its mature ecosystem for web development and data processing. Flask serves as the lightweight web framework responsible for handling API requests and serving earthquake data in JSON format. The data ingestion logic combines traditional HTML scraping from the Icelandic Meteorological Office’s MPGV archive (\texttt{hraun.vedur.is}) with high-frequency seismic data fetched through the Skjálftalísa API. MPGV records are collected using \texttt{BeautifulSoup} and \texttt{requests}, while Skjálftalísa events are retrieved in structured JSON form and stored in a dedicated raw-data table. Both sources are cleaned, normalised, and written to an SQLite database. A reconciliation algorithm subsequently merges MPGV and Skjálftalísa events into a unified catalogue based on temporal, spatial, and magnitude-based matching rules.
The result is a clean, queryable catalogue with no duplicated entries.

Unlike the earlier implementation, where filtering and processing were performed on the backend and visualised through static Folium maps, the new system uses React to dynamically display earthquake data on an interactive map. An intermediate version of the frontend used the Google Maps JavaScript API for geospatial rendering; however, this introduced a dependency on a paid API key and vendor-specific billing. The current version replaces Google Maps with Leaflet, an open-source mapping library, integrated through \texttt{react-leaflet}. This design lets the frontend render maps using freely available tile services and update in place without full page reloads or external API credentials, something that was difficult to achieve in the earlier backend-heavy architecture.

Vite, a modern build tool and development server, was chosen for the frontend instead of the traditional Create React App. Vite accelerates development through faster builds, hot module replacement, and optimized performance. With React’s component-based structure, the frontend is modular and scalable, making it easier to introduce new features. Dependencies for the backend are managed through a \texttt{requirements.txt} file, including Flask, pandas, requests, BeautifulSoup, SQLAlchemy for database management, APScheduler for automated updates, and additional modules for Skjálftalísa ingestion, EPOS ShakeMap verification, and volcano data retrieval.
On the frontend, dependencies are tracked in \texttt{package.json}, including React~18, \texttt{react-leaflet}~4.2 and \texttt{leaflet}~1.9 for map rendering, \texttt{maplibre-gl} and \texttt{@maplibre/maplibre-gl-leaflet} for the PMTiles-backed vector roadmap layer, \texttt{pmtiles} and \texttt{protomaps-themes-base} for self-hosted vector tile rendering, \texttt{leaflet.heat} for heatmap visualization, \texttt{axios} for HTTP communication, and \texttt{lodash} for utility functions. The previous version used \texttt{@react-google-maps/api} for Google Maps integration; this dependency has been entirely removed in the current Leaflet-based architecture.

A reconciliation algorithm subsequently merges MPGV and Skjálftalísa events into a unified dataset. This process compares events from both sources using temporal proximity, spatial distance, and magnitude similarity to identify matches and resolve duplicates. The resulting merged catalogue, stored in the \texttt{earthquake\_merged} table, provides improved accuracy in event location, depth, and magnitude while ensuring consistency across updates.

In addition to earthquake data, the system ingests auxiliary information from the \textbf{EPOS Iceland} APIs. The EPOS Volcanoes API supplies volcano locations, elevation values, and descriptive metadata, enabling the display of volcano overlays on the map. The EPOS ShakeMap API provides shaking intensity products that can be associated with individual earthquakes; these are cross-referenced against the merged catalogue to supply optional ShakeMap links for supported events. This extra data lets users see which volcanoes are near a cluster and check whether EPOS has a ShakeMap for a given event.

All data from MPGV, Skjálftalísa, and EPOS endpoints are stored in an SQLite database, which supports efficient queries, automated updates, and consistent long-term storage. The backend exposes this information through Flask API routes, while the frontend retrieves and visualizes the data in real time on a Leaflet-based map using free tile providers (self-hosted PMTiles for the roadmap view, Esri World Imagery for satellite, and Esri World Dark Gray for dark and heatmap modes). Features such as the time slider, magnitude scale, timeline-based or magnitude-based marker colouring, density heatmap visualization, volcano overlays, and ShakeMap integration are made possible by this multi-source ingestion framework.

Taken together, the MPGV scraper, Skjálftalísa client, EPOS integration, and reconciliation pipeline give the system a single, deduplicated catalogue drawn from multiple independent sources. This catalogue underpins every frontend feature, from time-filtered marker rendering to ShakeMap drill-down, and can accommodate new feeds without restructuring the existing pipeline.

\section{Data Scraping and Merging}

The \textbf{MPGV Monitor} system relies on a unified earthquake catalogue that combines multiple sources into a single, quality-controlled dataset. This chapter traces the evolution of the data pipeline from an initial single-month prototype to the current multi-source ingestion workflow and introduces the conceptual design of the reconciliation process. The emphasis is on \emph{how} the scraping and merging strategy matured over time, rather than on the implementation details of the backend, which are discussed separately in Chapter~5.

\vspace{0.4cm}

\subsection{Initial Approach}

The earliest implementation of data scraping focused on extracting earthquake records for a single month, October~2023, from the Icelandic Meteorological Office’s MPGV archive. This preliminary test served as a proof of concept, demonstrating that the monthly HTML pages on \texttt{hraun.vedur.is} could be parsed reliably and that automated harvesting of Icelandic earthquake data was technically feasible.

Using Python libraries such as \texttt{requests}, \texttt{BeautifulSoup}, and \texttt{pandas}, the script retrieved and parsed the HTML table, cleaned the dataset, and retained only records with magnitudes $\geq 3.0$. The processed data was then stored in a text file for basic visualization and preliminary validation.

\begin{figure}[H]
\centering
\includegraphics[width=\linewidth]{Screenshots/Raw_Data.png}
\caption{Extract from the initial raw MPGV dataset for October 2023 after basic cleaning and magnitude filtering.}
\end{figure}

The initial dataset contained 30 entries, which were reduced to 15 after filtering. Although limited in scope, this experiment confirmed that automated scraping was viable, that the MPGV HTML tables were sufficiently stable for programmatic parsing, and that the extracted attributes (date--time, latitude, longitude, depth, magnitude) could be normalized for further processing.

This first prototype treated the MPGV archive as a static data source and did not attempt to maintain a historical catalogue or support continuous updates. Nevertheless, it provided a concrete starting point for designing a more general data pipeline.

\vspace{0.4cm}

\subsection{Previous Approaches}

As the project evolved, two intermediate approaches were developed before arriving at the final database-driven, multi-source system. Both of these methods still relied on MPGV as the sole data provider, but they gradually expanded the temporal coverage and improved the structure of the stored data.

\subsubsection*{Manual Scraping with Text File Storage}

In the first extension, the scraper was generalised to fetch not only October~2023 but also the most recent month’s dataset from MPGV and store it locally in a plain-text file. Data was updated only when the script was executed manually. This approach was sufficient for exploratory analysis and basic visualisations, since the text file could be reloaded into Python notebooks or plotting tools.

However, the method had three important limitations. First, it could not efficiently retrieve historical records spanning multiple years. Second, each manual run overwrote the previous file, making it difficult to preserve a consistent long-term catalogue. Third, the loosely structured text format complicated downstream processing and increased the risk of format inconsistencies.

\subsubsection*{Dynamic Scraping with CSV Storage}

To expand coverage and improve structure, the scraper was redesigned to traverse multiple years and months programmatically, consolidating results into a single CSV file. Instead of targeting one fixed month, the script discovered available year and month links from the MPGV index page and iterated over them to harvest all records since June~2020.

\textbf{Code Snippet: Aggregating Monthly Records into CSV}

\begin{verbatim}
def scrape_all_to_csv():
    all_data = pd.DataFrame(columns=['DateTime','Lat','Lon','Depth','Mw'])
    response = requests.get(BASE_URL)
    soup = BeautifulSoup(response.content, 'html.parser')

    year_links = [a['href'].strip('/') for a in soup.find_all('a')
                  if a['href'].endswith('/')]

    for year in year_links:
        for month in get_months(year):
            monthly_data = get_monthly_data(year, month)
            all_data = pd.concat([all_data, monthly_data])

    all_data.to_csv("earthquakes.csv", index=False)
\end{verbatim}

This CSV-based approach addressed some of the shortcomings of the manual text-file workflow. It allowed the entire MPGV archive to be downloaded in a reproducible manner, enabled simple filtering and aggregation using \texttt{pandas}, and provided a convenient input format for early visualisation experiments.

On the other hand, several issues emerged as the dataset grew. Maintaining synchronisation between the CSV file and any downstream visualisation or web frontend became increasingly fragile: every update required regenerating and redistributing the entire file. Moreover, performing repeated full-archive scrapes was inefficient and unnecessary once most historical data had already been ingested. These drawbacks motivated a transition from flat-file storage to a dedicated database.

\subsection{Current Approach: Multi-Source Ingestion and Conceptual Merging}

The final design replaces the earlier MPGV-only, file-based workflow with an integrated, multi-source ingestion pipeline backed by an SQLite database. Instead of treating MPGV as the sole data provider, the system now combines three authoritative sources:

\begin{itemize}
    \item the MPGV HTML archive (curated earthquake solutions),
    \item the Skjálftalísa JSON API (high-frequency preliminary detections),
    \item and EPOS Iceland endpoints for volcano and ShakeMap metadata.
\end{itemize}

All data is written to \texttt{earthquakes.db}, where it is organised into separate tables for MPGV events, Skjálftalísa raw detections, a merged catalogue, and auxiliary volcano and ShakeMap information. This chapter focuses on the \emph{data-level} view of this pipeline; the concrete SQLAlchemy models, scheduler configuration, and Flask routes are described in detail in Chapter~5.

\subsubsection*{Automated Updates with Periodic Jobs}

In the current system, updates are no longer triggered manually. Instead, a periodic job executes the ingestion and merging pipeline at fixed intervals. Conceptually, each cycle performs three main operations:

\begin{enumerate}
    \item Scrape the latest MPGV records and append any new events to the MPGV table.
    \item Fetch recent Skjálftalísa detections and update the raw Skjálftalísa table.
    \item Run the reconciliation algorithm to produce an up-to-date unified catalogue.
\end{enumerate}

Only events with magnitude $\geq 2.7$ are retained. Duplicate entries are avoided by combining database-level uniqueness constraints (for example on timestamp and coordinates) with event matching rules based on temporal proximity, spatial distance, and magnitude similarity. The effect is that repeated runs of the pipeline are \emph{idempotent}: if no new earthquakes have occurred, the contents of the merged catalogue remain unchanged, even though the reconciliation logic is executed again.

\subsubsection*{Conceptual Ingestion and Merge Pipeline}

From a conceptual perspective, the multi-source pipeline can be expressed as a three-stage dataflow:

\begin{enumerate}
    \item \textbf{Ingestion}: each source-specific module (MPGV scraper, Skjálftalísa client, EPOS volcano loader) harvests data from its respective endpoint and writes normalised records into dedicated tables.
    \item \textbf{Reconciliation}: a matching algorithm compares candidate events from MPGV and Skjálftalísa and decides whether they refer to the same earthquake based on time, distance, and magnitude tolerances.
    \item \textbf{Merged catalogue}: for each MPGV event, the algorithm either finds a corresponding Skjálftalísa detection and records a \texttt{matched} entry or classifies it as \texttt{v\_only} if no suitable counterpart exists. The result is stored in a unified table that is consumed by the frontend.
\end{enumerate}

At this stage, it is useful to view reconciliation primarily as a \emph{data integration} problem: two different catalogues with slightly different coverage and timing must be aligned into a single, provenance-aware representation. The exact mathematical thresholds, depth-selection policies, and implementation details of the matching algorithm are presented in Chapter~5, where the reconciliation logic is discussed as part of the backend architecture.

\subsubsection*{Illustrative Ingestion and Merging Workflow}

The overall workflow of the current pipeline can be summarised as a recurring multi-source process that culminates in a single display catalogue:

In the deployed system, the unified catalogue is exposed to the React frontend through RESTful API endpoints and rendered on an interactive Leaflet-based map. The design choice to separate ingestion, reconciliation, and delivery into distinct stages makes it easier to evolve each component independently. For example, additional data sources or alternative matching strategies can be incorporated without changing the general flow from raw source tables to a merged, visualisation-ready dataset. Similarly, the recent migration of the frontend rendering layer from Google Maps to Leaflet required no modifications to the data pipeline or API contracts.

\subsubsection*{Evolution of the Data Pipeline}

Overall, the data pipeline for \textbf{MPGV Monitor} has progressed through three major stages. The initial prototype scraped a single month of MPGV data into text files, suitable only for small-scale experiments. The subsequent CSV-based approach introduced dynamic scraping across years and months, enabling historical analysis but still relying on manual updates and monolithic flat-file storage. The final pipeline adopts a database-centric, multi-source architecture with automated updates and a dedicated reconciliation step that integrates MPGV and Skjálftalísa catalogues.

Each stage fixed a concrete problem left by the one before it. Text files broke under concurrent access. CSVs handled one source well enough but fell apart when a second catalogue had to be merged in. Only after moving to a database-backed pipeline could the system run continuous, unattended updates, which is the minimum bar for anything calling itself a real-time monitor. The next chapter describes the backend that grew out of this final stage: its database schema, scheduling infrastructure, reconciliation algorithm, ShakeMap validation pipeline, and the Flask API layer that hands the merged catalogue to the frontend.

\section{Backend Development}

The backend is a Flask application that runs continuously alongside an APScheduler background job. Every three minutes, the scheduler fires a sequence of three tasks: scrape the latest MPGV records, fetch recent Skjálftalísa detections, and reconcile both into a unified catalogue. Flask then serves that catalogue through a small set of JSON endpoints. \subsection{Core Database Models}

A central element of the backend architecture is the structured SQLite schema, exposed through SQLAlchemy ORM classes in the Flask application. The schema deliberately separates raw source tables from the derived, unified catalogue and auxiliary products. This separation provides consistency, traceability, and efficient querying across the entire pipeline. The main tables are \texttt{Earthquake} for MPGV-sourced events, \texttt{EarthquakeSRaw} for Skjálftalísa detections, \texttt{EarthquakeMerged} for the unified view, \texttt{Volcano} for EPOS volcano metadata, and \texttt{ShakeMapLink} for cached ShakeMap validation results.

The \textbf{Earthquake} model represents earthquake events scraped from the MPGV HTML archive (denoted internally as \emph{v} events). MPGV entries are curated and validated by the Icelandic Meteorological Office and therefore act as the authoritative baseline for the system. The table stores attributes such as timestamp, location, depth, and magnitude, all normalised from the monthly pages on \texttt{hraun.vedur.is}. A uniqueness constraint on the combination of timestamp and coordinates prevents duplicate insertions during repeated ingestion runs.

\begin{verbatim}
class Earthquake(db.Model):
    id         = db.Column(db.Integer, primary_key=True)
    date_time  = db.Column(db.String, index=True, nullable=False)
    latitude   = db.Column(db.Float, nullable=False)
    longitude  = db.Column(db.Float, nullable=False)
    depth      = db.Column(db.Float, nullable=False)
    mw_mean    = db.Column(db.Float, nullable=False)
\end{verbatim}

The \textbf{EarthquakeSRaw} model stores raw Skjálftalísa API detections (denoted as \emph{s} events). Skjálftalísa provides high-frequency, preliminary seismic detections that often appear before the corresponding MPGV solutions. These records are stored with their original event identifiers, magnitudes, timestamps, and coordinates. Because Skjálftalísa can include small or transient events and early solutions, the raw table deliberately preserves the data as-ingested to maintain provenance for the reconciliation step.

\begin{verbatim}
class EarthquakeSRaw(db.Model):
    id         = db.Column(db.Integer, primary_key=True)
    event_id   = db.Column(db.String, unique=True, nullable=False)
    date_time  = db.Column(db.String, index=True, nullable=False)
    latitude   = db.Column(db.Float, nullable=False)
    longitude  = db.Column(db.Float, nullable=False)
    depth      = db.Column(db.Float)
    magnitude  = db.Column(db.Float)
\end{verbatim}

The \textbf{EarthquakeMerged} model represents the unified catalogue that is served directly to the frontend. Each row corresponds to a single earthquake that has either been matched across MPGV and Skjálftalísa or originates from MPGV alone. During reconciliation, the system compares events from both sources using temporal, spatial, and magnitude thresholds (see Section~\ref{subsec:reconcile}) and decides whether they describe the same physical event. When a match is found, \textbf{origin time and magnitude ($M_w$) are taken from MPGV} (the curated, authoritative values), while \textbf{latitude, longitude, and depth are taken from the Skjálftalísa match} (which provides higher-precision hypocentral solutions). This field-level merging means that each matched row has the quality-controlled magnitude of the IMO solution but the more precise location of the Skjálftalísa detection. If no match is found, all fields are taken from MPGV and the row is recorded as \texttt{v\_only}.

\begin{verbatim}
class EarthquakeMerged(db.Model):
    id           = db.Column(db.Integer, primary_key=True)
    date_time    = db.Column(db.String, index=True, nullable=False)
    latitude     = db.Column(db.Float, nullable=False)
    longitude    = db.Column(db.Float, nullable=False)
    depth        = db.Column(db.Float)
    mw_mean      = db.Column(db.Float, nullable=False)

    status       = db.Column(db.String, nullable=False)   # 'matched' | 'v_only'
    v_src_key    = db.Column(db.String)
    s_event_id   = db.Column(db.String)
    match_dt_sec = db.Column(db.Float)
    match_dist_km= db.Column(db.Float)
    match_dm     = db.Column(db.Float)
\end{verbatim}

The \textbf{Volcano} table stores metadata for Icelandic volcanoes obtained from EPOS Iceland, including their geographic locations and elevations. This information is used to draw volcano overlays in the frontend and to support contextual analyses such as distance-to-volcano queries or swarm clustering.

\begin{verbatim}
class Volcano(db.Model):
    id           = db.Column(db.Integer, primary_key=True)
    name         = db.Column(db.String, nullable=False)
    description  = db.Column(db.Text)
    elevation_m  = db.Column(db.Float)
    elevation_ft = db.Column(db.Float)
    latitude     = db.Column(db.Float, nullable=False)
    longitude    = db.Column(db.Float, nullable=False)
    last_eruption= db.Column(db.String)
\end{verbatim}

Finally, the \textbf{ShakeMapLink} table acts as a cache of EPOS ShakeMap products associated with catalogued events. For each event timestamp, it stores the URL of the chosen ShakeMap, together with metadata describing the matching quality (time difference, spatial distance, and magnitude difference between the event and the ShakeMap solution).

\begin{verbatim}
class ShakeMapLink(db.Model):
    __tablename__ = "shakemap_links"

    dt          = db.Column(db.String, primary_key=True)
    url_view_file = db.Column(db.String)
    origin_time = db.Column(db.String)

    sm_lat   = db.Column(db.Float)
    sm_lon   = db.Column(db.Float)
    sm_mag   = db.Column(db.Float)
    sm_depth = db.Column(db.Float)

    dt_sec   = db.Column(db.Float)
    dist_km  = db.Column(db.Float)
    dm       = db.Column(db.Float)

    status   = db.Column(db.String)  # "valid" | "no_candidate" | "no_valid" | "error"
    note     = db.Column(db.String)
\end{verbatim}

The raw source tables are never overwritten or merged in place; they stay intact so that any reconciliation run can be repeated or audited. The merged catalogue, volcano metadata, and ShakeMap links are all derived products that can be rebuilt from the raw tables if the matching rules change.

\subsection{Dynamic Data Ingestion}

The dynamic ingestion pipeline is responsible for keeping the local database synchronized with the external MPGV, Skjálftalísa, and EPOS services. Rather than relying on manual runs or static files, the system uses three dedicated modules, \texttt{scrape.py}, \texttt{skjalftalisa\_client.py}, and \texttt{volcano\_scraper.py}, to harvest and normalise data from each source. All ingestion operations write directly into the ORM-backed tables described above.

A few practical realities shaped how the ingestion works. The external services go down from time to time, and occasionally return malformed responses, so each module has to fail without leaving the local database in a half-written state. Updates need to happen often enough that the map feels live, but not so often that the third-party APIs start rejecting requests. Raw records stay in their own tables so the merging step can be re-run on its own if the algorithm changes. And if a new data source appears later, plugging it in should not mean rewriting the existing modules. In practice, each ingestion module wraps its own networking, error handling, and field normalisation behind a single callable that the scheduler fires every three minutes.

\paragraph{MPGV Scraper.}

The MPGV scraper, implemented in \texttt{scrape.py}, parses the monthly HTML pages published by the Icelandic Meteorological Office. For each month, the scraper retrieves the \texttt{<table>} element containing earthquake records, converts its rows into Python dictionaries, cleans and normalises the values, and applies a magnitude threshold so that only events with $Mw_{\text{mean}} \geq 2.7$ are retained. Records with missing or malformed coordinates, depth, or magnitude are discarded to avoid polluting the catalogue with incomplete entries. A uniqueness constraint on \texttt{(date\_time, latitude, longitude)} prevents duplicate rows when the scraper is re-run.

\paragraph{Skjálftalísa Client.}

The Skjálftalísa ingestion module, implemented in \texttt{skjalftalisa\_client.py}, interacts with the Skjálftalísa API at \texttt{api.vedur.is/skjalftalisa/v1/quake/array}. Requests are sent as HTTP POST with a JSON body specifying \texttt{start\_time}, \texttt{end\_time}, \texttt{size\_min}, \texttt{event\_type}, and the list of fields to return. The service responds with column-oriented arrays (e.g.\ \texttt{"lat": [...], "long": [...]}); the client converts these into row-wise dictionaries and normalises UNIX timestamps to the uniform format \texttt{YYYY-MM-DD HH:MM:SS} in UTC. Requests spanning more than 365 days are automatically split into yearly chunks. The resulting records are inserted (or updated by \texttt{event\_id}) into the \texttt{earthquake\_s\_raw} table.

During routine scheduled cycles only the most recent 7 days of Skjálftalísa data are fetched (\texttt{fetch\_last\_n\_days(7)}), providing an efficient incremental update. A separate \texttt{backfill\_skjalftalisa\_since\_2020()} helper is available for one-time historical population and was used to seed the initial catalogue from June~2020 onwards.

\paragraph{EPOS Volcano Scraper.}

The \texttt{volcano\_scraper.py} module fetches volcano metadata from the EPOS Iceland API. Because EPOS exposes several endpoints and data formats, the scraper performs additional normalisation to reconcile different field names (for example, \texttt{lat\_dd} versus \texttt{latitude}) and ensure that all entries are represented in a consistent schema. Elevation is stored in metres and also converted to feet for convenience. This process populates the \texttt{volcano} table with up-to-date volcano locations and basic descriptive information.

\paragraph{Operational characteristics.}

A few practical realities shaped the error handling. External services go down from time to time, and the MPGV page layout changed slightly in late 2025, so each module has to deal with transient failures without leaving the database in a half-written state. In practice this means exceptions are caught and logged per cycle, failed cycles simply produce no new rows (they do not overwrite existing ones), and the next scheduled run resumes cleanly. Efficiency-wise, the MPGV scraper re-checks all historical months on every cycle but the uniqueness constraint means only genuinely new rows make it into the database; the Skjálftalísa client fetches only the last seven days in routine mode; and EPOS volcano metadata is refreshed infrequently because volcano locations do not change on the timescale of the deployment.

\subsection{Automated Scheduling}

Automated ingestion in \textbf{MPGV Monitor} is driven by \texttt{APScheduler}, which periodically triggers a composite backend job without any manual intervention. The scheduler is configured in \texttt{app.py} and attached to the Flask application context. It registers a recurring job that executes the entire ingestion and merging workflow at a fixed interval:

\begin{verbatim}
_scheduler = BackgroundScheduler(
    coalesce=True,
    misfire_grace_time=60
)
_scheduler.add_job(
    scheduled_scrape,
    "interval",
    minutes=3,
    max_instances=1
)
_scheduler.start()
\end{verbatim}

The choice of a three-minute interval reflects a compromise between data freshness and resource usage. Skjálftalísa can update at sub-minute cadence, whereas MPGV solutions are published on scales of tens of minutes to hours. Running the full update every three minutes ensures that Skjálftalísa detections are incorporated soon after they are available, while also catching new MPGV entries in a timely fashion, without placing excessive load on the external services or the local SQLite database.

The \texttt{max\_instances=1} parameter is critical from a reliability perspective. It guarantees that a new scheduler run is not started while the previous one is still active, thereby avoiding overlapping writes and potential race conditions. Each scheduled execution of \texttt{scheduled\_scrape} performs three steps: (1)~MPGV scraping (all available months from June~2020), (2)~Skjálftalísa fetching (incremental, the most recent 7~days only), and (3)~reconciliation into the merged table. ShakeMap validation is \emph{not} part of the scheduled cycle; it is run separately by executing \texttt{shakemap\_validator.py} directly, which audits all merged events and populates the \texttt{shakemap\_links} cache.

The scheduler itself is started \emph{lazily} rather than at application startup. It is registered inside a \texttt{@app.before\_request} hook and starts on the first HTTP request that reaches the server. This avoids starting background threads in Flask's reloader subprocess (only the worker process, identified by \texttt{WERKZEUG\_RUN\_MAIN=true} in debug mode, should run the scheduler).

In the current deployment, where the entire historical catalogue from June~2020 has already been ingested, many scheduler cycles log messages such as \enquote{\texttt{0 new earthquake records added (Flask).}} followed by \enquote{\texttt{Total: 1781}}. This behaviour illustrates that the pipeline is idempotent: the job can be re-run safely even when no new events are available, and the content of the merged table remains stable. When new earthquakes are published by the Icelandic Meteorological Office, the same mechanism automatically incorporates them into both the MPGV table and the unified catalogue.

From an architectural viewpoint, the scheduler runs as a background component alongside the Flask application. HTTP endpoints such as \texttt{/earthquakes}, \texttt{/volcanoes}, and \texttt{/shakemap/\{dt\}} remain responsive while ingestion is in progress. Because the ingestion and reconciliation steps operate within database transactions, partial failures (for example, a temporary API outage) do not corrupt existing tables: exceptions are caught and logged, and the next scheduled cycle resumes from a clean state.

\subsection{Reconciliation and Merging}
\label{subsec:reconcile}

The reconciliation algorithm integrates MPGV (\textit{v}) events with Skjálftalísa (\textit{s}) detections to form a unified earthquake catalogue. Its purpose is to determine whether a pair of events from the two sources represents the same physical earthquake. Matching is based on three criteria: temporal proximity, spatial distance, and similarity in magnitude.

For an MPGV event $v$ and a Skjálftalísa event $s$, a valid match must satisfy:

\[
|\Delta t| \leq 2 \text{ seconds}, \qquad
\Delta d < 10 \text{ km}, \qquad
|\Delta Mw| < 3.0,
\]

where $\Delta t$ is the absolute difference in origin times, $\Delta d$ is the great-circle epicentral distance, and $\Delta Mw$ is the magnitude difference. These thresholds were tuned empirically to maximise correct matches while avoiding spurious associations. Compared to an earlier version of the algorithm that used $|\Delta t| < 3$\,s and $|\Delta Mw| < 2.0$, the current thresholds tighten the temporal window to $\pm 2$\,seconds while relaxing the magnitude tolerance to $|\Delta Mw| < 3.0$, reflecting the observation that magnitude estimates can differ substantially between the two catalogues for the same physical event.

At runtime, the system loads all Skjálftalísa detections into a time-indexed structure, enabling efficient lookup of candidate events whose timestamps differ from the corresponding MPGV event by at most two seconds. The overall reconciliation workflow is illustrated in Figure~\ref{fig:reconcile-workflow}. For each MPGV entry, the algorithm retrieves all Skjálftalísa events satisfying the temporal constraint, computes the spatial separation and magnitude deviation, filters out invalid candidates, and classifies the event as either \texttt{v\_only} or \texttt{matched}. If exactly one candidate passes all three thresholds, it is accepted as the match. If two or more candidates pass, the situation is considered ambiguous and the MPGV event falls back to \texttt{v\_only} status rather than risking a spurious association.

\vspace{0.7cm}

\begin{figure}[H]

\centering    \includegraphics[width=\linewidth, height=20cm]{Screenshots/Reconciliation workflow.png}

\caption{Reconciliation workflow showing the branching logic for matching MPGV events against Skjálftalísa detections. Candidate events must pass temporal, spatial, and magnitude thresholds simultaneously; ambiguous multi-candidate cases fall back to \texttt{v\_only} status.}
\label{fig:reconcile-workflow}

\end{figure}

The corresponding Python implementation is shown below. It reflects the control flow depicted in Figure~\ref{fig:reconcile-workflow} and implements the threshold rules precisely. When a match is accepted (\texttt{write\_matched}), the merged row stores MPGV origin time and magnitude but Skjálftalísa latitude, longitude, and depth (depth policy \texttt{'s'} — use Skjálftalísa depth). Diagnostic information such as time offset (\texttt{match\_dt\_sec}), epicentral distance (\texttt{match\_dist\_km}), and magnitude deviation (\texttt{match\_dm}) is stored alongside each merged event, enabling quality assessment and downstream analysis.

\begin{verbatim}
for v in v_rows:
    candidates = []

    # Search Skjálftalísa events within ±2 seconds of the MPGV timestamp
    for s in s_index.get_window(v.date_time, window_sec=2):
        dt_abs  = abs(v.dt_ts - s.dt_ts)
        dist_km = haversine_km(v.lat, v.lon, s.lat, s.lon)
        dm      = abs(v.mw_mean - (s.magnitude or 0))

        # Candidate must satisfy all three thresholds
        if dt_abs <= 2 and dist_km < 10 and dm < 3.0:
            candidates.append((dist_km, dt_abs, dm, s))

    # No valid Skjálftalísa match → v_only
    if not candidates:
        write_v_only(v)
        continue

    # Exactly one candidate → accept as matched
    # Multiple candidates → ambiguous, fall back to v_only
    if len(candidates) == 1:
        dist, dt_abs, dm, best_s = candidates[0]
        write_matched(v, best_s, dt_abs, dist, dm)
    else:
        write_v_only(v)
\end{verbatim}

Because the reconciliation outcome is recorded in the \texttt{status} field and both MPGV and Skjálftalísa identifiers are kept, every match can be audited after the fact. If the thresholds turn out to be too tight or too loose, the algorithm can be re-tuned and the merge re-run without losing any raw data.

The current reconciliation implementation processes only MPGV (\textit{v}) events as the primary input and attempts to pair each with a Skjálftalísa (\textit{s}) detection. Skjálftalísa events that have no corresponding MPGV entry (i.e., would be \texttt{s\_only}) are not written to the merged table; they remain in the \texttt{earthquake\_s\_raw} table and are not served to the frontend. This policy keeps the merged catalogue anchored to the IMO's curated magnitude estimates, since standalone Skjálftalísa detections lack the validated $M_{w}$ values that MPGV provides. Adding \texttt{s\_only} support remains a planned extension for future versions.

\subsection{ShakeMap Validation Pipeline}
\label{subsec:shakemap}

While the merged earthquake catalogue provides a consistent record of seismicity, it does not directly describe the shaking intensity or ground-motion patterns associated with each event. To enrich the dataset with this information, the system includes a ShakeMap validation pipeline that searches for EPOS Iceland ShakeMap products corresponding to each merged earthquake. The validation logic, implemented in \texttt{shakemap\_validator.py}, queries the EPOS API, evaluates candidate ShakeMaps, and records the most plausible match in the \texttt{shakemap\_links} table.

\subsubsection*{Validation Procedure}

For each event in the merged catalogue with origin time $t$, epicentre $(\phi, \lambda)$, and magnitude $M_w$, the validator performs the following steps:

\begin{enumerate}
    \item \textbf{ShakeMap retrieval.} Query the EPOS ShakeMap API (\texttt{api.epos-iceland.is}) for products within a ±30-minute window around the event time, constrained to a bounding box padded by $0.3^{\circ}$ in each direction around the event epicentre.
    \item \textbf{Candidate evaluation.} For every returned ShakeMap, compute:
    \[
    |\Delta t| = |t_{\text{event}} - t_{\text{sm}}|, \quad
    \Delta d = \text{dist}\big((\phi,\lambda), (\phi_{\text{sm}},\lambda_{\text{sm}})\big), \quad
    |\Delta M| = |M_w - M_{w,\text{sm}}|.
    \]
    Candidates are accepted only if $|\Delta t| \leq 10$ min, $\Delta d \leq 10$ km, and $|\Delta M| \leq 0.5$. ShakeMaps exceeding any of these hard limits are rejected.
    \item \textbf{Best-match selection.} If multiple valid candidates remain, select the one with the smallest combination of temporal offset, spatial distance, and magnitude deviation using a lexicographic ordering.
    \item \textbf{Database update.} Store the selected ShakeMap (or the failure category) in the \texttt{shakemap\_links} table together with diagnostic values such as \texttt{dt\_sec}, \texttt{dist\_km}, and \texttt{dm}.
\end{enumerate}

If EPOS returns no ShakeMaps for the query window, the event is labelled \texttt{no\_candidate}. If candidates exist but none satisfy the validation thresholds, the status becomes \texttt{no\_valid}. Errors during API retrieval or metadata parsing result in the status \texttt{error}. Recording the failure reason explicitly, rather than silently dropping unmatched events, means the frontend can tell the user \emph{why} no ShakeMap is shown, not just that one is absent.

\subsection{Flask API Layer}

The final component of the backend is the Flask API layer, which exposes the processed and reconciled data stored in SQLite to the React frontend and external tools such as Postman or command-line clients. All endpoints provide JSON responses, and the API surface is intentionally read-only to preserve database integrity, as ingestion and reconciliation are handled exclusively by the scheduler.

The principal routes implemented in \texttt{app.py} are:

\begin{itemize}
    \item \texttt{/earthquakes} ,  returns the unified catalogue from \texttt{earthquake\_merged}, optionally filtered to the last \emph{N} days via a query parameter. Responses are cached in memory with a 60-second TTL.
    \item \texttt{/earthquakes\_csv} ,  downloads the merged earthquake catalogue as a CSV file, supporting the same optional day-based filtering.
    \item \texttt{/volcanoes} ,  returns volcano metadata from the \texttt{volcano} table for map overlay visualisation.
    \item \texttt{/shakemap\_lookup} ,  queries the EPOS API live for ShakeMap data near a specified event (parameters: \texttt{dt}, \texttt{lat}, \texttt{lon}); uses a different EPOS endpoint (\texttt{api.vedur.is}) than the batch validator and applies a looser proximity scoring rather than hard acceptance thresholds.
    \item \texttt{/shakemap/<dt>} ,  returns a cached or validated ShakeMap link and associated diagnostic metadata for the event whose timestamp is \texttt{<dt>}, if available. Reads from the \texttt{shakemap\_links} table populated by \texttt{shakemap\_validator.py}.
    \item \texttt{/health} ,  returns row counts for the \texttt{earthquake}, \texttt{earthquake\_s\_raw}, and \texttt{earthquake\_merged} tables, useful for operational monitoring.
    \item \texttt{/reconcile} ,  \textbf{POST} endpoint that manually triggers a reconciliation run; restricted to localhost (\texttt{127.0.0.1} or \texttt{::1}) and used exclusively for debugging and evaluation.
    \item \texttt{/scrape-volcanoes} ,  manually triggers a volcano metadata refresh from the EPOS API; also restricted to localhost only.
\end{itemize}

A typical endpoint serialises ORM objects into dictionaries and wraps them in a JSON response. For example, the endpoint providing the unified earthquake catalogue is defined as follows:

\begin{verbatim}
@app.route("/earthquakes", methods=["GET"])
def get_earthquake_data():
    with app.app_context():
        rows = EarthquakeMerged.query \
            .order_by(EarthquakeMerged.date_time.desc()) \
            .all()

        return jsonify([
            {
                "Date-time": r.date_time,
                "Latitude":  r.latitude,
                "Longitude": r.longitude,
                "Depth":     r.depth,
                "Mw_mean":   r.mw_mean,
                "status":    r.status
            } for r in rows
        ])
\end{verbatim}

Because the Flask application and the scheduler operate on the same SQLite database, all API calls always return the most up-to-date state of the catalogue without requiring additional scraping at request time. To reduce database load under repeated polling, the \texttt{/earthquakes} endpoint employs an in-memory response cache with a 60-second time-to-live (TTL). The cache is invalidated after each scheduled scrape cycle, ensuring that new data is available to clients within at most one minute of ingestion. Requests that include query parameters (such as \texttt{?days=NN}) bypass the cache to ensure accuracy.

Because API handlers are predominantly read-only while the scheduler handles writes, and SQLite's WAL mode permits concurrent readers alongside a single writer, user queries stay fast even during an active scrape. The JSON response format is also simple enough that the frontend can render markers, overlays, and ShakeMap icons from lightweight requests. Optional gzip compression via Flask-Compress further reduces response payload sizes for clients that support it.

\subsection{Summary}

The backend does four things: pull data from three sources, schedule those pulls automatically, reconcile the results into one deduplicated catalogue, and serve that catalogue through a handful of JSON endpoints. That is a small surface area for everything the system has to do, and the constraint turned out to be useful. When the MPGV page layout changed in late 2025, only \texttt{scrape.py} needed touching. When the frontend migrated from Google Maps to Leaflet, the backend did not change at all, because the frontend only ever sees a few GET endpoints returning flat JSON and the rendering engine behind the map is invisible to the API. Whether that loose coupling holds under future extensions, new data sources, richer queries, will depend on keeping the separation clear between what belongs in the pipeline and what belongs in the browser.

\section{Frontend Architecture and Implementation}
\label{sec:frontend}

The frontend is a React~18 single-page application built with Vite. It fetches the merged earthquake catalogue from the backend once on load and then every three minutes, and renders whatever the active filters leave behind as Leaflet markers on an interactive map. The user never waits for the server when adjusting time or magnitude controls; all filtering happens client-side against the already-downloaded catalogue.

\subsubsection*{Migration from Google Maps to Leaflet}

A previous version of the frontend used the Google Maps JavaScript API for all spatial rendering. While Google Maps provided high-quality cartography and smooth navigation, it introduced several practical constraints: a paid API key was required, usage incurred billing based on map loads, and the proprietary nature of the service created vendor lock-in. These constraints were particularly limiting for a research project intended for eventual handover to the Icelandic Meteorological Office, where ongoing API costs and credential management would add operational burden.

The current version replaces Google Maps entirely with \textbf{Leaflet}~1.9, an open-source JavaScript mapping library, integrated into React via the \texttt{react-leaflet}~4.2 bindings. This migration eliminates the need for any API key, removes usage-based billing, and provides full control over tile sources. The roadmap view uses a self-hosted PMTiles vector tile archive rendered via MapLibre~GL, so even the default basemap has no external CDN dependency. The specific tile providers used for each basemap mode are detailed in Section~\ref{subsec:frontend_leaflet}. In addition, the Leaflet-based architecture enabled the introduction of a new heatmap visualization mode, circular \texttt{L.circleMarker} rendering, and a fully custom zoom-responsive latitude/longitude grid overlay, features that were not present in the Google Maps version.

One decision made early on that kept paying off was keeping the backend and frontend truly separate. The backend handles ingestion, reconciliation, ShakeMap validation, and persistence. The frontend calls a fixed set of HTTP endpoints and renders what comes back. It has no knowledge of how the catalogue was produced or where the data came from. This meant that when the rendering layer was migrated from Google Maps to Leaflet, the backend did not need a single change, the endpoints stayed identical and the data format was untouched. That same boundary should make it straightforward to add new features on either side without the change propagating across both layers.

\subsection{User Interface Overview and Interaction Goals}
\label{subsec:frontend_ui_overview}

The frontend is designed around a map-first workflow. When the web application is opened, the map is displayed immediately in default mode and earthquake markers are rendered without requiring additional user actions. This default behavior supports rapid situational awareness by presenting the full available catalogue at first load.

The interface is composed of a small set of persistent controls arranged around the map canvas:

\begin{itemize}
    \item \textbf{Map menu (top-left):} a hover-activated menu that allows switching between \emph{Map}, \emph{Satellite}, \emph{Dark Mode}, and \emph{Heatmap}. These options provide alternative cartographic contexts while keeping the analytical overlays consistent.
    \item \textbf{Application title (top-center):} fixed title providing clear identity of the system.
    \item \textbf{About button (top-right):} opens a modal panel with an overview of the system, a CSV data export button, contact information, credits, and a disclaimer about limited mobile support.
    \item \textbf{Magnitude scale (right):} a vertical slider for magnitude threshold selection, coupled to a color scale when magnitude-color mode is enabled.
    \item \textbf{TimeWindow slider (left, vertical):} a multi-resolution temporal selector that supports navigating from year-level ranges into month-level and day-level windows. Supports both scroll-wheel zoom and drag-based panning.
    \item \textbf{Color-mode toggle (near the slider controls):} switches marker coloring between timeline-based encoding and magnitude-based encoding. The inactive scale becomes visually muted to reduce ambiguity.
    \item \textbf{Overlay toggles (left side):} switches for showing volcano markers and an optional latitude/longitude grid.
\end{itemize}

The controls work as a coordinated set: time and magnitude act as filters, the color-mode selector changes how the surviving markers are shaded, and the overlay toggles add contextual layers (volcanoes, lat/lon grid) independently of filtering. One deliberate design rule is that changing any filter automatically closes the event-inspection panel, so the user never sees stale detail data that no longer matches the active view.

\subsection{Backend Connection}
\label{subsec:frontend_api_layer}

A central design decision in MPGV Monitor is that the frontend does not communicate with the database directly. Instead, the backend exposes curated data through a stable set of HTTP endpoints (e.g., \texttt{/earthquakes}, \texttt{/volcanoes}, and ShakeMap-related routes). The frontend uses a single communication module, \texttt{api.js}, as the exclusive gateway to these endpoints.

Centralising all HTTP calls in one file means that if the backend URL changes or error handling needs updating, only \texttt{api.js} is touched. Components call \texttt{fetchEarthquakeData()} or \texttt{fetchVolcanoData()} without knowing or caring about URL paths or response formats.

\paragraph{Example (minimal API abstraction).}
A representative pattern used in \texttt{api.js} is:

\begin{verbatim}
export async function fetchEarthquakeData() {
  const response = await axios.get(`${API_URL}/earthquakes`);
  return Array.isArray(response.data) ? response.data : [];
}
\end{verbatim}

In practice, similar functions exist for volcano metadata and optional ShakeMap resources. The key point is architectural: UI components call stable functions such as \texttt{fetchEarthquakeData()} rather than repeating request logic throughout the codebase.

The ShakeMap helper, \texttt{fetchShakeMapValidated(dt, lat, lon)}, deliberately uses the browser's native \texttt{fetch()} API rather than \textit{axios}. It calls the live \texttt{/shakemap\_lookup} endpoint (which queries the EPOS API in real time) and returns a structured result \texttt{\{available, url, dt\_sec, dist\_km, dm\}} on success or \texttt{null} if no validated ShakeMap is found. The \texttt{dt\_sec} field is derived from the API's \texttt{minutes\_diff} field multiplied by 60. Note that the development build points the backend at port~5001 (\texttt{http://localhost:5001}), while the Flask server defaults to port~5002; the ports must therefore be aligned in local development.

\subsection{Top-Level Orchestration}
\label{subsec:frontend_app}

The \texttt{App.jsx} component is the coordinator of the frontend. It is responsible for:

(1) loading datasets using \texttt{api.js}; 
(2) storing global UI state (filters, toggles, selected event, color mode); 
and (3) distributing state and callbacks to child components.

This design follows a state-lifting approach: shared state lives at the highest common ancestor so that changes in one control (e.g., the magnitude slider) can consistently update other parts of the interface (e.g., the map markers and the event inspection panel).

At runtime, \texttt{App.jsx} performs an initial data fetch when the application loads. Earthquakes are requested from the backend and stored as an in-memory dataset used for map rendering. Because the backend performs reconciliation and produces a unified catalogue, the frontend can treat the dataset as authoritative and focus on interactive operations (filtering and encoding) without additional validation steps.

The orchestration role of \texttt{App.jsx} is also visible through callbacks: when the user adjusts the time window or magnitude threshold, the corresponding component reports changes upward through a function prop. \texttt{App.jsx} updates state, and React’s reactivity triggers downstream updates.

\subsection{Map Rendering and Marker Lifecycle}
\label{subsec:frontend_mapcomponent}

The map rendering logic is implemented in the \texttt{MapComponent.jsx} module (approximately 900 lines), which acts as the spatial rendering engine of the frontend. It is responsible for constructing the Leaflet map instance and managing the lifecycle of all map overlays. Unlike static map outputs, this component must support dynamic re-rendering of markers when filters, color mode, or overlays change.

\paragraph{Map initialization.}
Upon mounting, \texttt{MapComponent.jsx} initializes a Leaflet map via the \texttt{react-leaflet} \texttt{<MapContainer>} component. The initial configuration sets a default center at approximately $64.96^{\circ}$\,N, $-19.02^{\circ}$\,W with zoom level~6, appropriate for a full-Iceland view. The map uses \texttt{preferCanvas=false} (SVG renderer) to preserve the browser's native right-click context menu on markers, \texttt{zoomSnap=0.5} and \texttt{zoomDelta=0.5} for half-step zoom increments, and \texttt{minZoom=4.5} to prevent users from zooming out beyond Iceland's context. A \texttt{FitIcelandOnReady} subcomponent calls \texttt{map.fitBounds()} on mount to fit Iceland to the viewport and then locks \texttt{minZoom} dynamically to that fitted level. A \texttt{MapReadyHandler} subcomponent additionally calls \texttt{map.invalidateSize()} after 150\,ms and 500\,ms to ensure correct sizing after CSS layout completion.

\paragraph{Marker creation and updates.}
Earthquake markers are rendered as \textbf{circular markers} using Leaflet's \texttt{L.circleMarker} API. Each marker has a fixed radius of 5\,px (7\,px when selected) and a color computed from the magnitude and the active color mode. The radius is intentionally uniform across all magnitudes; visual weight is conveyed through color intensity rather than size, keeping the map uncluttered when thousands of events are displayed.

All earthquake markers are managed through a single \texttt{L.layerGroup}, enabling $O(1)$ show/hide operations for the entire layer. This is a significant performance improvement over the Google Maps version, which required iterating through individual markers. Markers are sorted ascending by magnitude before insertion so that higher-magnitude events appear on top in the SVG stack. Marker objects are stored in a \texttt{Map<quakeKey, \{marker, quake, index\}>} structure, and when the selected earthquake changes, only the two affected markers (previous and new selection) are updated rather than the entire collection.

\paragraph{Color encoding.}
Two color modes are supported:

\begin{itemize}
    \item \textbf{Timeline mode:} markers are colored by month using a 12-stop wine/mauve palette. January starts at a muted dusty rose (\texttt{\#b07888}); colors darken progressively through burgundy shades toward near-black in December (\texttt{\#0c0208}). The color is determined by \texttt{date.getUTCMonth()}, so all events in the same calendar month share the same hue regardless of the year. This palette was chosen for legibility on both light and dark basemaps.
    \item \textbf{Magnitude mode:} markers are colored using a 5-stop blue palette from light slate blue (\texttt{\#8aa0c0}, $M_{w,\min}$) through progressively darker navy tones to deep navy (\texttt{\#060820}, $M_{w,\max}$), interpolated linearly based on the normalized magnitude $t = (M_w - M_{w,\min}) / (M_{w,\max} - M_{w,\min})$.
\end{itemize}

\paragraph{Event selection and the information panel.}
Clicking a marker triggers a selection action. The selected marker receives a white stroke and a 4\,px size boost to distinguish it visually. An information panel appears showing magnitude, depth, event time, latitude, longitude, and, if a validated ShakeMap association exists, a button linking to the EPOS ShakeMap product. The ShakeMap lookup is performed asynchronously via \texttt{fetchShakeMapValidated()}.

The information panel is intentionally ephemeral. It closes automatically after 15 seconds and also closes immediately if the user changes time or magnitude filters or clicks the map background. This behavior prevents the UI from displaying details that no longer correspond to the currently visible filtered dataset.

\paragraph{Heatmap visualization.}
The heatmap mode, introduced in the Leaflet version, uses the \texttt{leaflet.heat} plugin to render a density-based heat overlay. Each earthquake contributes a point with a base weight of 1.0, boosted to 1.15 for events with $M_w \geq 4.0$ and 1.3 for $M_w \geq 5.0$. The heatmap radius is zoom-responsive (15--58\,px) and uses a custom gradient transitioning through dark blue, teal, amber, and red. The heatmap layer rebuilds only on data changes or zoom events; panning is free, maintaining approximately 60\,FPS.

\subsection{Basemap Selection}
\label{subsec:frontend_maptypeselector}

The basemap selector provides four modes: standard roadmap (self-hosted PMTiles vector tiles rendered via MapLibre~GL), satellite imagery (Esri World Imagery), a dark theme (Esri World Dark Gray Base), and a density-based heatmap (Esri World Dark Gray Base with a separate World Dark Gray Reference label overlay pane). This represents an expansion from the three modes available in the previous Google Maps version, with the heatmap being a new addition enabled by the Leaflet plugin ecosystem.

From an architectural standpoint, this component does not manage map state directly. Instead, it emits the selected map mode to \texttt{App.jsx}, which updates the global state. \texttt{MapComponent.jsx} then applies the correct tile layer configuration through the \texttt{TileLayerManager} subcomponent.

Keeping the selector ignorant of tile URLs and map state avoids tight coupling and makes the component easy to test in isolation: it only has to emit a string, and \texttt{MapComponent.jsx} handles the rest.

\subsection{Temporal Filtering}
\label{subsec:frontend_timewindow}

The TimeWindow slider supports exploration across multiple temporal resolutions. At a high level, the slider enables the user to restrict the visible earthquake catalogue to a selected interval. What distinguishes this control from a basic date picker is its multi-scale behavior: the slider presents coarse year-level ranges when zoomed out, and transitions into month-level and day-level resolution as the user zooms in.

The idea is that a seismologist browsing five years of data and a civil-protection officer zooming into yesterday's swarm need different temporal granularity, and the slider should handle both without a mode switch. Internally, the component reports the selected interval to \texttt{App.jsx} through a callback, and the filtered interval is applied when deriving the marker set shown on the map.

The temporal slider also interacts with color encoding. When timeline-color mode is enabled, marker colors reflect temporal progression across the active dataset (e.g., older to newer). When magnitude-color mode is enabled, the time slider remains functional as a filter but is visually muted to indicate that it is not the active encoding dimension.

\subsection{Magnitude Thresholding}
\label{subsec:frontend_magnitude}

The MagnitudeScale component provides a vertical threshold slider that ranges from the system’s minimum magnitude (filtered at ingestion to $Mw \geq 2.7$) to the maximum magnitude observed in the current dataset. The selected threshold defines which events remain visible. This filter is critical for exploring swarms: users can suppress smaller events to highlight only stronger earthquakes.

In magnitude-color mode, the component also acts as a legend. Marker colors correspond to magnitude intensity, enabling quick interpretation of spatial distributions of event strength. In timeline-color mode, the magnitude scale remains active as a filter but is visually muted, reinforcing the separation between \emph{filtering} and \emph{encoding mode}.

\paragraph{Example (mode-dependent color selection).}
A short illustrative snippet is sufficient:

\begin{verbatim}
const color = (mode === "magnitude")
  ? magnitudeColor(event.mw)
  : timelineColor(event.time);
\end{verbatim}

The thesis emphasis is the interaction logic: a single dataset supports multiple analytical encodings through a mode switch rather than duplicating rendering pipelines.

\subsection{Volcano Overlay}
\label{subsec:frontend_volcano}

The volcano overlay is a supplementary spatial layer that can be toggled on and off. When enabled, volcano markers are rendered as distinct orange/red triangle symbols (20$\times$20\,px SVG icons, fill colour \texttt{\#ff3c00}), visually separated from the circular earthquake markers. This layer supports contextual interpretation: clusters of seismicity can be compared against known volcanic systems.

From an architectural perspective, \texttt{VolcanoMarker.jsx} uses Leaflet's imperative API via the \texttt{useMap()} hook from \texttt{react-leaflet}, creating \texttt{L.marker} instances with custom \texttt{L.divIcon} icons (wrapping an \texttt{<img>} element whose \texttt{src} is an inline SVG data-URI) directly on the map. On first use the component creates a dedicated Leaflet pane, \texttt{volcanoPane}, with a \texttt{z-index} of 390, ensuring that volcano markers render above standard tile layers but below pop-up panels. This imperative approach was chosen because it provides finer control over marker lifecycle than the declarative \texttt{react-leaflet} \texttt{<Marker>} component. Each volcano marker is manually cleaned up on unmount via \texttt{map.removeLayer(marker)}. The component renders no JSX and returns \texttt{null}.

\subsection{Latitude/Longitude Grid Overlay}
\label{subsec:frontend_grid}

The latitude/longitude grid overlay is an optional aid for spatial orientation. When enabled, the map displays a grid of reference lines across the full view, implemented using \texttt{L.polyline} for grid lines and \texttt{L.marker} with \texttt{L.divIcon} for coordinate labels. This control is particularly useful when users want approximate spatial comparisons without continuously referencing the coordinates in the inspection panel.

The grid is \textbf{zoom-responsive}: the spacing and label precision adapt automatically as the user zooms in or out. At low zoom levels ($z < 5$), grid lines are spaced at $5^{\circ}$ intervals with zero decimal places; at high zoom levels ($z \geq 15$), the spacing narrows to $0.01^{\circ}$ with four decimal places. Intermediate levels introduce both major and minor (sub-)grid lines for improved readability. The grid rebuilds on \texttt{zoomend} and \texttt{moveend} events.

A \textbf{safe-zone calculation} ensures that latitude labels never overlap the TimeWindow slider panel on the left side of the interface: labels positioned less than 120\,px from the left edge of the viewport are suppressed. Grid line and label colors adapt automatically to the active basemap (light or dark theme).

As with the volcano overlay, the grid is controlled via a toggle in the interface. The overlay is treated as auxiliary and does not change earthquake filtering or encoding.

\subsection{About Modal}
\label{subsec:frontend_about}

The About panel is a modal overlay that provides reference information about the system. It is structured into several sections:

\begin{itemize}
    \item \textbf{Overview:} describes the purpose of MPGV Monitor, its coverage of 33 Icelandic volcanic systems, and the $M_w \geq 2.7$ detection threshold, along with brief descriptions of the two primary data sources (MPGV catalogue and Skjálftalísa API).
    \item \textbf{Data export:} a button that downloads the full merged earthquake catalogue (all events from June~2020 onward, $M_w \geq 2.7$) as a CSV file by calling the \texttt{/earthquakes\_csv} backend endpoint.
    \item \textbf{Contact:} lists the academic contacts responsible for the system (email addresses at the University of Iceland).
    \item \textbf{Credits:} lists the project contributors (thesis author, supervisor, and advisor).
    \item \textbf{Disclaimer:} notes that the system is optimised for desktop browsers and that mobile support is limited.
\end{itemize}

Opening the About panel does not touch the map state; filters, selected markers, and overlays remain exactly as they were. The panel can be closed by clicking the close button, pressing \texttt{Esc}, or clicking the backdrop. Focus is moved to the close button on mount to support keyboard navigation. A version identifier (\texttt{1.0}) is displayed in the panel footer.

\subsection{State Interaction Model and Cross-Component Consistency}
\label{subsec:frontend_state_model}

With several controls all affecting the same map, the main risk is inconsistency: a user changes the time window, but the info panel still shows a marker that no longer passes the filter. All shared state lives in \texttt{App.jsx}, and a few explicit rules keep things coherent:

\begin{itemize}
    \item \textbf{Filter changes invalidate inspection context:} changing the time window or magnitude threshold clears the selected event and closes the information panel.
    \item \textbf{Encoding mode is explicit:} a single toggle determines whether color encodes time or magnitude. The inactive legend/scale is visually muted to reduce ambiguity.
    \item \textbf{Overlay toggles are independent:} volcano markers and the grid can be enabled without affecting filtering.
    \item \textbf{Basemap changes preserve analytical state:} switching Map/Satellite/Dark changes cartographic context but does not reset filters or marker selection.
\end{itemize}

The net effect is that the map never lies: what the user sees always matches the active filter and encoding settings.

\subsection{Comparison with Existing Seismic Web Applications}
\label{subsec:frontend_comparison}

MPGV Monitor is not trying to replace global catalogues or real-time alert services. Its niche is Iceland-specific analytical exploration backed by a reconciled, multi-source catalogue. To make that positioning concrete, it helps to compare against what already exists.

\paragraph{Iceland-focused platforms.}
The IMO earthquake page shows epicentres from roughly the last 48~hours alongside a table and supporting plots \cite{imo_quakes_48h}. It is authoritative and immediately readable, but a researcher who wants to study how the Reykjanes swarm evolved over 2021--2024 has no temporal slider to work with. earthquakes.is \cite{earthquakes_is} fills a similar real-time niche with a simpler interface geared toward public monitoring. Neither service reconciles multiple catalogues or links events to ShakeMap products. MPGV Monitor keeps the map-first immediacy of these tools but adds multi-year temporal navigation, magnitude thresholding, dual colour encodings, and a backend that algorithmically matches MPGV and Skjálftalísa records before anything reaches the screen.

\paragraph{Global platforms.}
The USGS Latest Earthquakes application \cite{usgs_latest_map} covers the entire planet with standardized reporting and event-detail pages, an interface that has to work for Tokyo and Reykjavik alike. EMSC \cite{emsc_home,emsc_map} adds a ``citizen seismology’’ layer, incorporating crowdsourced felt-reports alongside institutional data. The IRIS Interactive Earthquake Browser \cite{iris_ieb_app,iris_ieb_help} targets researchers and educators, offering large-scale querying and CSV export over a Google Maps base. All three are valuable, but none is specialized for Iceland’s data landscape. MPGV Monitor trades global breadth for domain depth: because the backend already knows about MPGV page layouts, Skjálftalísa JSON schemas, and EPOS ShakeMap endpoints, the frontend can offer interactions, volcano overlays, ShakeMap drill-down, heatmap mode, that a general-purpose viewer cannot justify building.

\subsection{Summary}
\label{subsec:frontend_summary}

Replacing Google Maps with Leaflet removed the one external dependency that would have made handing this over to the Icelandic Meteorological Office complicated: a paid API key. The roadmap view uses a self-hosted PMTiles file so there is no tile CDN to depend on; satellite and dark mode pull from Esri free-tier services. Everything the frontend knows about the data comes through \texttt{api.js} talking to the backend. The filtering, the colour encoding, the heatmap, the volcano overlay, the lat/lon grid, none of it changes what the backend serves. That independence is what made the Google Maps migration cost nothing on the server side, and it should make future frontend changes equally isolated.

\section{Final Features}
\subsection{Final Feature Polishing}
Once the core Leaflet migration was functionally complete, a separate polishing phase addressed the rough edges that only become visible through sustained daily use and informal user testing. This section documents the main refinements, the reasoning behind them, and the trade-offs involved.

\subsubsection{Heatmap Gradient and Radius Tuning}

The initial heatmap implementation used a single fixed radius, which looked acceptable at the default zoom level but produced either a featureless blur (zoomed out) or isolated blobs (zoomed in). After experimenting with several radius--zoom mappings, a lookup table was adopted that scales the point radius with the zoom level:

\begin{table}[H]
\centering
\small
\begin{tabular}{l c c c c c c}
\hline
\textbf{Zoom} & 5 & 6 & 7 & 8 & 9 & 10+ \\
\textbf{Radius (px)} & 15 & 22 & 30 & 38 & 48 & 58 \\
\hline
\end{tabular}
\caption{Heatmap radius values at representative zoom levels.}
\label{tab:heatmap-radii}
\end{table}

The gradient was also redesigned from a generic red--yellow ramp to a seven-stop scale (transparent $\rightarrow$ dark indigo-blue $\rightarrow$ medium blue $\rightarrow$ teal $\rightarrow$ amber $\rightarrow$ orange $\rightarrow$ deep red) that gives a clearer visual separation between low-density background and high-density clusters such as the Reykjanes swarms. The maximum weight is set to 1.3 to match the heaviest event weight, ensuring the full colour gradient is utilized rather than saturating at the top.

\subsubsection{Latitude/Longitude Grid Overlay}

The grid overlay draws degree lines across the visible map extent and labels them along the edges. Two problems surfaced during testing. First, at certain zoom levels the labels overlapped with the TimeWindow slider on the left side of the screen. This was solved by defining a ``safe zone'' in pixel coordinates: labels whose screen position falls inside the slider's bounding box are simply not drawn. Second, the label text was hard to read against both light and dark tile layers. Adding a thin white halo (CSS \texttt{text-shadow}) around each label made them legible on all four basemaps without requiring per-layer colour logic.

\subsubsection{Marker Rendering Performance}

With the full dataset loaded (1\,781 merged events), the original per-marker DOM manipulation caused noticeable lag during filter changes on mid-range hardware. Three changes brought the frame rate back to acceptable levels:

\begin{enumerate}
    \item \textbf{SVG \texttt{L.circleMarker} with fixed radius.} Switching from \texttt{L.divIcon} (individual DOM nodes with inline SVG) to \texttt{L.circleMarker} reduces the per-marker overhead. A fixed radius of 5\,px (7\,px when selected) is used instead of a magnitude-scaled size, keeping all markers lightweight and uniformly fast to style.
    \item \textbf{Layer-group visibility.} Instead of adding and removing markers from the map on every filter change, all markers are placed in a \texttt{L.layerGroup} at load time. Filtering then toggles the group's visibility, an $O(1)$ operation, rather than iterating through thousands of individual layers.
    \item \textbf{Memoised icon computation.} The per-marker color and size (stored as \texttt{markerIcons}) is computed once via \texttt{useMemo} and only recomputed when \texttt{earthquakes}, \texttt{colorOwner}, or \texttt{maxMagnitude} change, avoiding per-render recalculation.
\end{enumerate}

\subsubsection{Z-Index Alignment}

Leaflet's internal pane system assigns z-index values in the 400--700 range by default, which is significantly higher than Google Maps' defaults. After the migration, several UI controls (the About button, the map-type selector, the magnitude scale) rendered \emph{behind} the tile pane. Fixing this required raising the z-index of \texttt{.controls} and \texttt{.about-button-container} to 1001 and the magnitude scale to 1000, values that sit safely above Leaflet's highest default pane (overlay pane at 400) while still leaving room for pop-ups and tooltips.

\subsubsection{CSV Export}

A recurring request during informal testing was the ability to download the displayed earthquake data for use in external tools (Excel, MATLAB, R). A new backend endpoint, \texttt{/earthquakes\_csv}, serialises the merged catalogue as a comma-separated file with headers matching the JSON field names. The About modal in the frontend provides a download link that hits this endpoint, so users can export whatever subset the current time and magnitude filters define.

\subsubsection{User Feedback and Interface Adjustments}

Several smaller changes came directly from watching users interact with the application during informal testing sessions:

\begin{itemize}
    \item The TimeWindow slider was moved slightly inward from the left edge after users on smaller screens reported that it overlapped the zoom controls.
    \item The default colour palette for timeline-based marker colouring was adjusted after feedback that the original green-to-red ramp was hard to distinguish for users with red--green colour deficiency.
    \item The overall interface layout was tightened so that the map occupies the maximum possible screen area, with controls kept compact and positioned along the edges rather than floating over the map centre.
\end{itemize}

These adjustments were minor individually, but collectively they made the difference between a prototype that worked and an interface that felt ready to show to external stakeholders.

\section{Deployment, Testing \& Debugging}
\subsection{Backend \& Frontend Testing}
Extensive testing was carried out on both the backend and frontend. The backend test suite, executed via \texttt{python -m pytest tests/ -v}, includes 41 passing tests across five test files:

\begin{itemize}
    \item \texttt{test\_haversine.py}: 10 tests for the \texttt{haversine\_km()} pure function, covering identical points, threshold boundary behaviour, and real Iceland locations.
    \item \texttt{test\_scrape\_parse.py}: 14 tests for MPGV HTML table parsing with mocked HTTP responses, verifying magnitude filtering and timestamp normalization.
    \item \texttt{test\_reconcile.py}: 13 integration tests for the \texttt{match\_and\_merge()} reconciliation algorithm, covering unique matches, ambiguous multi-candidate scenarios, unmatched events, and depth policy enforcement.
    \item \texttt{test\_volcano\_scraper.py}: 3 tests for the EPOS volcano metadata ingestion module, covering the primary API endpoint, the v1 fallback path, and the empty-response case.
    \item \texttt{test\_volcano\_scraper\_live.py}: 1 live integration test that queries the real EPOS volcano API, skipped by default to avoid depending on external service availability.
\end{itemize}

Test isolation is achieved through a \texttt{conftest.py} fixture that sets \texttt{DISABLE\_SCHEDULER}, redirects the database to a temporary file, and rebuilds the SQLAlchemy engine for each test session.

The frontend test suite uses Vitest with \texttt{@testing-library/react} and a jsdom environment. It contains 12 tests for the \texttt{TimeWindowSlider} component, covering basic rendering, year-mode label positioning, callback behaviour, and month-mode label formatting. The frontend tests are executed via \texttt{npm test} from the \texttt{frontend/} directory.

In addition to automated tests, manual user testing was conducted with sample users to evaluate UI responsiveness, data accuracy, and the usability of the Leaflet-based map interface following the migration from Google Maps.


\subsection{Early Deployment Testing (Historical)}

During an earlier phase of development, a preliminary deployment was carried out on the university's Pluto server to validate that the application could run in a networked environment. This deployment used the previous Google Maps--based version of the frontend and served primarily as a proof-of-concept exercise. It is no longer active and does not reflect the current Leaflet-based architecture; however, the experience informed several deployment decisions documented below.

\subsubsection{Setup and Challenges}
The application was hosted using \texttt{gunicorn}, a production-ready WSGI server, behind the server's public IP address on port~7000. Initial attempts encountered issues with Python path resolution (\texttt{ModuleNotFoundError}) and port conflicts when \texttt{gunicorn} was invoked without the correct working directory. These were resolved by explicitly setting the \texttt{--chdir} flag and activating the virtual environment before launching the server.

The final working command ran \texttt{gunicorn} in the background using \texttt{nohup}:

\begin{verbatim}
nohup gunicorn -b 0.0.0.0:7000 backend.app:app \
  --chdir ~/QuakeMap > gunicorn.log 2>&1 &
\end{verbatim}

The application was then accessible at \texttt{http://130.208.113.169:7000/} and responded correctly to HTTP requests.

\subsubsection{Lessons Learned}
This early deployment highlighted several practical considerations:

These lessons directly inform the planned production deployment strategy described below.

\subsection{Production Deployment}

The Leaflet-based version of MPGV Monitor has been deployed to a production server at the University of Iceland and is currently running. Deployment proceeds in two stages:

\begin{enumerate}
    \item \textbf{Internal testing deployment (completed):} The application is currently running on \texttt{pluto.cs.hi.is}, a Linux server (Ubuntu~24.04 LTS) managed by the University of Iceland's Computer Science department. It is accessible at \texttt{http://pluto.cs.hi.is/mpgv/}, where the university's web infrastructure proxies incoming requests from port~80 to the \texttt{gunicorn} process on port~6000.

    Deployment is handled by a \texttt{deploy.sh} script that covers the full update cycle in a single command. It sets up a Python virtualenv if needed, installs backend and frontend dependencies, and builds the React frontend with \texttt{VITE\_BASE\_PATH=/mpgv/} so that all asset paths resolve correctly under the proxy subpath. Before starting a new server instance it checks whether one is already running via a PID file and stops it gracefully if so. The new \texttt{gunicorn} process is started in the background with \texttt{nohup} and its output redirected to \texttt{server.log}; a companion \texttt{stop.sh} script reads the PID file to shut it down cleanly when needed.

    \texttt{gunicorn} runs with one worker process and eight threads (\texttt{gthread} worker class, 120\,s timeout). The decision to use a single worker rather than several was deliberate: multiple workers would each start their own APScheduler instance, and those concurrent scraping jobs would race on the SQLite database. A single worker with eight threads gives enough concurrency for the expected load -- a handful of simultaneous users each fetching one JSON payload -- without that problem. The Flask application serves the pre-built frontend bundle directly, so no separate static file server is needed, and the SQLite database persists across restarts, so the full historical catalogue from June~2020 onward is available immediately after each redeployment.

    \begin{figure}[H]
        \centering
        \includegraphics[width=\linewidth]{Screenshots/deployed_pluto.png}
        \caption{Terminal output of a successful \texttt{deploy.sh} run on the Pluto server, showing dependency installation, frontend build, and \texttt{gunicorn} startup on port~6000.}
    \end{figure}

    \item \textbf{Public production deployment:} Following successful internal testing, the application is intended to be deployed for public access through the Icelandic Meteorological Office (IMO). This deployment will require addressing tile provider licensing (see Section~\ref{subsec:tile_licensing}), configuring HTTPS, and ensuring the system meets the operational requirements for a publicly accessible monitoring tool.
\end{enumerate}

The modular architecture of MPGV Monitor, with a stateless Flask API backend and a static-asset React frontend, is well suited to standard deployment patterns. The frontend can be served as a pre-built static bundle via \texttt{nginx} or a CDN, while the backend can run as a persistent \texttt{gunicorn} process with the SQLite database on local storage.

Once a predictive model is developed (see Section~\ref{subsec:prediction_model}), it will be integrated into the backend and exposed through a dedicated API endpoint, enabling users to query predicted seismic activity in real time through the frontend interface.

\section{Future Development}

MPGV Monitor now handles the core loop, pulling data in, reconciling it, and letting users explore the result on a map, but a number of directions remain open. Some of these came up during user testing, others emerged from conversations with staff at the Icelandic Meteorological Office, and a few reflect longer-term research goals that go beyond what a single thesis can cover. The subsections below describe the ones I consider most promising.

\subsection{Accessibility and Inclusive Design}

The current interface assumes a mouse and does not meet formal accessibility standards. WCAG~2.1 \cite{WCAG21} organises its guidance around four principles, perceivable, operable, understandable, and robust, and the existing frontend falls short on most of them.

The most important gap is keyboard navigation. None of the interactive controls, the TimeWindow slider, the magnitude scale, the map type selector, or the overlay toggles, can currently be operated without a mouse. Adding full keyboard support would open the tool to users who rely on assistive switch devices or keyboard-only navigation. Alongside that, ARIA labels and roles need to be added to map markers, information panels, and controls so that screen reader software can convey the interface structure to visually impaired users \cite{WAI_ARIA}. The SVG-based earthquake and volcano icons would also need text alternatives.

On the visual side, the existing colour palettes have not been tested against common forms of colour vision deficiency. An earlier version of the timeline colour ramp used a green-to-red gradient that was hard to read for users with deuteranopia; the current wine/mauve palette is better but a formally colourblind-safe alternative, drawing on established guidance from Brewer \cite{Brewer2003ColorBrewer}, would be more robust. Text elements should also respect browser font-size preferences and stay legible when scaled to 200\%, in line with WCAG Success Criterion~1.4.4.

None of these changes are blocked by the architecture; they are a matter of time and priority.

\subsection{Automated Data Analysis and Visualization}

Right now, interpretation is left to the user. The API and CSV export make all the data available, but a researcher who wants a Gutenberg--Richter plot or a depth cross-section still has to download the CSV and open it in R or MATLAB. Adding built-in analysis would make the system more useful to the IMO staff and geoscientists who are the primary audience.

The Gutenberg--Richter law ($\log_{10} N = a - bM$) \cite{GutenbergRichter1944} is a natural starting point: an interactive frequency--magnitude plot that updates as the user adjusts the time window and magnitude filter would let researchers check the completeness threshold of the catalogue and compare b-values across zones. Temporal histograms showing daily or weekly event counts would make swarm activity and seasonal patterns visible at a glance, which would have been immediately useful during the 2021--2024 Reykjanes sequence.

For spatial analysis, automated clustering via DBSCAN \cite{Ester1996DBSCAN} could highlight active swarm zones without the user having to zoom in manually. Depth cross-sections along user-defined transects would help distinguish shallow tectonic events from deeper magma-related ones, a distinction that matters particularly in the Eastern Volcanic Zone. A summary dashboard with total event count, maximum magnitude, active regions, and reconciliation coverage would also serve operational briefings at the IMO better than the current raw map view.

All of this would sit on top of the existing API without changing the backend. The frontend would use a charting library such as D3.js or Chart.js to render the analysis panels, keeping them independent of the map rendering layer.

\subsection{Mobile Application}

The current interface is designed for desktop. It works on a phone in a pinch, but the controls are too small and the interaction model is wrong for touch. A dedicated mobile application would not just be a smaller version of the same thing; the main reason to build it is push notifications. Receiving an alert when a $M_w \geq 4.0$ event occurs anywhere in Iceland is something the existing web interface cannot do at all, and it is the feature most commonly requested during informal testing.

Beyond notifications, a native app could cache tile data and recent catalogue entries for offline use, which matters in highland areas of Iceland where connectivity is patchy. GPS-based positioning would let the app show the user's location relative to active seismic zones. And touch-optimized controls, pinch-to-zoom on the time axis, swipe-based event browsing, would feel more natural than adapting the current mouse-driven slider to a phone screen.

The backend would not need to change. The existing Flask API already returns everything a mobile client needs in standard JSON, so a cross-platform framework like React Native or Flutter could target iOS and Android from a single codebase while reusing the same map visualization concepts established in the Leaflet version.

\subsection{Prediction Model}
\label{subsec:prediction_model}

A planned future enhancement is the development of a machine learning model to predict earthquake occurrences based on historical data. The reconciled multi-source catalogue maintained by MPGV Monitor provides a quality-controlled training dataset that spans multiple years of Icelandic seismicity.

Initial models will focus on regression techniques for short-term rate forecasting, with the possibility of exploring recurrent neural network architectures such as Long Short-Term Memory (LSTM) networks for time-series prediction. LSTM networks have shown promise in modelling sequential dependencies in seismic data and have been applied to aftershock forecasting and seismicity rate estimation in recent studies \cite{DeVries2018LSTM}. Because the backend already runs periodic scheduled tasks, adding a prediction step fits naturally into the existing pipeline: the model would run after each reconciliation cycle and write its output to a new database table, which a dedicated API endpoint would then serve to both the web frontend and a future mobile application.

\subsection{Tile Provider Licensing for Production Deployment}
\label{subsec:tile_licensing}

The current Leaflet-based frontend uses freely available tile services that are suitable for development and low-traffic academic use. Before deploying the system as a public-facing service with significant traffic, the following licensing considerations must be addressed:

\begin{itemize}
    \item \textbf{PMTiles roadmap (OpenStreetMap-derived)}: the \texttt{iceland.pmtiles} file is already self-hosted and served alongside the frontend static assets, so it has no third-party dependency. The underlying OpenStreetMap data is free under the Open Database License (ODbL) \cite{OSM_TileUsage}, and no tile-request rate limits apply since tiles are fetched locally via HTTP range requests from the bundled file.
    \item \textbf{Esri World Imagery}: used for the satellite basemap. Available under a free tier with usage limits; a paid Esri licence or switch to an alternative imagery provider (e.g., Mapbox Satellite, Google Maps Static API) may be required at production-scale traffic.
    \item \textbf{Esri World Dark Gray Base and Reference}: used for dark mode and heatmap basemaps. Subject to the same Esri free-tier terms as World Imagery above.
\end{itemize}

For high-traffic deployments, the Esri dependencies can be replaced with self-hosted alternatives (for example, a custom MapLibre GL dark style loaded from a self-hosted PMTiles file), which would eliminate all third-party tile requests and provide full control over cartographic styling and availability.

\subsection{Database Migration}

A migration from SQLite to PostgreSQL is under consideration to handle larger datasets, support concurrent write operations from multiple ingestion workers, and improve performance for multi-user deployments. PostgreSQL's mature support for spatial queries through the PostGIS extension could also enable server-side spatial analysis, such as distance-based event queries and bounding-box filtering, reducing the computational burden on both the web frontend and a potential mobile client. Because all database access already goes through SQLAlchemy, the migration would mainly involve changing the connection URI and testing the ORM mappings against PostgreSQL's type system.

\subsection{Additional Enhancements}

A few smaller improvements are worth noting separately. The current in-memory 60-second cache works for a handful of users but would need to move to Redis for anything approaching production-scale traffic; rate limiting should come with it. Multilingual support, adding Icelandic alongside English, would help with local adoption and would matter if the IMO eventually points visitors there. A responsive layout for tablets and mobile browsers is also needed before the tool can be shared publicly without a disclaimer about desktop-only support. Further out, integrating additional real-time data streams, GPS deformation measurements, volcanic gas emissions, or InSAR-derived ground displacement, would give seismologists richer context for interpreting seismic patterns, though that goes beyond what a single thesis can cover.

% ============================ CHAPTER 10 ============================
\section{Conclusion}
This thesis described the design and implementation of MPGV Monitor, a web application that scrapes the MPGV HTML archive, queries the Skjálftalísa API, pulls ShakeMap metadata from EPOS, reconciles those three feeds into one deduplicated catalogue, and presents the result on a Leaflet-based interactive map.

The most consequential decision made during the project was migrating the frontend from the Google Maps JavaScript API to Leaflet. In practical terms, this meant the application no longer needs a paid API key, incurs no usage-based charges, and can be handed over to the Icelandic Meteorological Office without any third-party billing attached. It also opened up features that were difficult or impossible to implement under Google Maps, a density heatmap layer, canvas-accelerated marker rendering, and a zoom-responsive lat/lon grid overlay among them. On the data side, the reconciliation algorithm matches 81.2\,\% of MPGV events to their Skjálftalísa counterparts, and the backend's in-memory cache and idempotent update loop keep the system running reliably on a 3-minute polling cycle.

One lesson that kept proving itself throughout development was the value of keeping the backend and frontend loosely coupled. The project went through three rendering stacks, Folium, Google Maps, Leaflet, and the backend API survived all three without a single endpoint change. That outcome was not planned from the start; it fell out of the decision to expose only flat JSON and let the frontend handle all spatial logic.

There is still plenty of room to grow. On the user-facing side, keyboard navigation, screen-reader labels, and colourblind-safe palettes would open the tool to a wider audience, and a companion mobile app with push notifications would turn it from a passive dashboard into an active alerting system. On the analytical side, built-in Gutenberg--Richter plots, DBSCAN clustering, and summary dashboards would save users from having to export CSV files for offline analysis. Further out, a machine-learning prediction model, a move from SQLite to PostgreSQL, and a self-hosted tile server are all on the roadmap.

\section{Installation and Running}
\label{app:installation}

This appendix explains how to set up a local development instance of MPGV Monitor from a fresh clone of the repository. The steps below were tested on Windows~11, but the same commands work on Linux and macOS with minor path adjustments.

\subsection*{Prerequisites}

\begin{itemize}
    \item Python 3.10 or later
    \item Node.js 18 or later (includes \texttt{npm})
    \item SQLite 3 (bundled with Python on most platforms)
    \item Git
\end{itemize}

\subsection*{Clone the Repository}

\begin{verbatim}
git clone https://github.com/FaheemSajjad-dev/
           iceland-quake-monitoring-leaflet.git
cd iceland-quake-monitoring-leaflet
\end{verbatim}

\subsection*{Backend Setup}

\begin{enumerate}
    \item Create and activate a Python virtual environment inside the \texttt{backend/} directory:
\begin{verbatim}
cd backend
python -m venv venv
source venv/bin/activate        # Linux / macOS
venv\Scripts\activate           # Windows
\end{verbatim}

    \item Install the Python dependencies:
\begin{verbatim}
pip install -r requirements.txt
\end{verbatim}

    \item Start the Flask development server:
\begin{verbatim}
python app.py
\end{verbatim}

The server listens on port \textbf{5002} by default. On first launch it creates \texttt{data/earthquakes.db}, runs the initial scrape from all three data sources, and begins the three-minute APScheduler cycle. Log output confirms each completed scrape and reconciliation pass. Note: the frontend \texttt{api.js} module hard-codes port~5001 for local development; the \texttt{BACKEND\_PORT} environment variable (or a direct edit to \texttt{app.py}) must be set to \textbf{5001} if the default backend port is not changed, to ensure the two processes agree.
\end{enumerate}

\subsection*{Frontend Setup}

\begin{enumerate}
    \item Install Node.js dependencies:
\begin{verbatim}
cd frontend
npm install
\end{verbatim}

    \item Start the Vite development server:
\begin{verbatim}
npm run dev
\end{verbatim}

    \item Open \texttt{http://localhost:5174} in a browser. The frontend expects the backend at \texttt{http://localhost:5001}; this base URL is set in \texttt{frontend/src/api.js} and can be changed for different environments.
\end{enumerate}

\subsection*{Running Tests}

Backend unit and integration tests (41 tests):
\begin{verbatim}
cd backend
python -m pytest tests/ -v
\end{verbatim}

Frontend component tests (12 tests):
\begin{verbatim}
cd frontend
npm test
\end{verbatim}

\subsection*{Common Issues}

\begin{itemize}
    \item \textbf{Port already in use:} If port 5002 (backend default) or 5174 (Vite default) is occupied, either stop the conflicting process or change the port in \texttt{app.py} (backend) or \texttt{vite.config.js} (frontend). Note that \texttt{api.js} hard-codes port~5001 for local development; set \texttt{BACKEND\_PORT=5001} or update \texttt{api.js} accordingly if you change the backend port.
    \item \textbf{Missing \texttt{venv} on Linux:} Some distributions package \texttt{venv} separately. Install it with \texttt{sudo apt install python3-venv} (Debian/Ubuntu).
    \item \textbf{First scrape takes time:} The initial data pull from MPGV, Skjálftalísa, and EPOS can take 1--2 minutes. Subsequent three-minute cycles are incremental and much faster.
\end{itemize}

\subsection*{Example: \texttt{/earthquakes} Response}

Each element in the returned JSON array has the following structure:

\begin{verbatim}
