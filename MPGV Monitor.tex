\section*{Abstract}  
This thesis presents the development of \textbf{MPGV Monitor}, a full-stack web platform for dynamic visualization of seismic activity in Iceland. The system integrates automated data ingestion, real-time processing, and interactive geospatial rendering to produce a unified and reliable earthquake catalogue.

Unlike earlier versions that relied solely on monthly HTML pages from the Icelandic Meteorological Office’s MPGV site, the current system incorporates multiple live data sources. Earthquake information is now obtained through a hybrid scraping pipeline that ingests MPGV records together with high-frequency seismic data from the Skjálftalísa API. These datasets are cross-validated and merged using a reconciliation algorithm that matches events based on temporal proximity, spatial distance, and magnitude similarity. Additional improvement is provided by programmatically querying the EPOS API to verify shaking intensity products, as well as for volcano locations and metadata. All processed information is maintained in an SQLite database and provided via a Flask-based REST backend, while a Vite + React frontend renders the results on an interactive Google Maps interface.

The system enables users to explore temporal patterns, analyze correlations between magnitude, depth, and spatial clusters, and filter events by custom time window and magnitude scale. Challenges addressed include reconciling asynchronous data sources, preventing duplication, validating raw event streams, optimising database writes under frequent updates, and ensuring smooth frontend performance when handling thousands of records. Through these solutions, the platform achieves a stable balance between update frequency and responsiveness.

The final contributions of this work include a unified and quality-controlled earthquake catalogue, a robust multi-source ingestion pipeline, and an interactive visualization environment that supports temporal filtering, magnitude scaling, volcano overlays, ShakeMap verification and other features. Together, these components demonstrate the effectiveness of \textbf{MPGV Monitor} as a practical tool for seismic monitoring in Iceland. The system also establishes a foundation for future enhancements such as predictive modelling, improved caching and rate-limiting, and the integration of additional real-time hazard indicators.

\section{Introduction}
The \textbf{MPGV Monitor} project is a web-based interactive platform designed to visualize seismic activity across Iceland using near real-time earthquake data. The system follows a modern full-stack architecture that combines a Vite~+~React frontend, a Flask backend, and Google Maps integration for geospatial rendering. React’s component-driven structure provides efficient state management and high interactivity, while Flask exposes a lightweight REST API that delivers processed seismic data to the client. Together, these components enable a responsive and maintainable environment for monitoring earthquakes as they occur.

\subsection*{Context and Motivation}
Iceland, situated along the \textbf{Mid-Atlantic Ridge}, is one of the most seismically active regions in the world. The island lies at the boundary between the North American and Eurasian tectonic plates, which are continuously diverging. This divergent plate setting generates persistent extensional forces within the crust, producing frequent earthquakes and sustained volcanic activity. Unlike convergent margins, where seismicity is typically driven by compressional stresses, Icelandic earthquakes arise primarily from rifting processes, magma intrusion, and crustal deformation. As a result, the country experiences recurrent earthquake swarms as well as occasional larger seismic events, underscoring the importance of reliable and accessible seismic monitoring tools.

Volcanic activity increases these hazards. Iceland is located above a geological hotspot where magma from deep within the mantle rises toward the surface. Magma intrusions often generate intense earthquake swarms as they open or widen fractures in the crust. The \textbf{2010 Eyjafjallajökull eruption}, which disrupted global air travel, and the \textbf{2021 Fagradalsfjall eruption}, which attracted international attention, were both preceded by clear changes in seismic activity. Monitoring these patterns is important for understanding magma movement, anticipating eruptive behaviour, and reducing related risks.


Earthquakes in Iceland pose dangers ranging from structural damage and landslides to disruptions in infrastructure and transportation. While most events are moderate in magnitude, major earthquakes in regions such as the South Iceland Seismic Zone (SISZ) and the Tjörnes Fracture Zone (TFZ) have historically caused significant damage. Understanding the spatial and temporal patterns of seismic activity is therefore critical for disaster preparedness and public safety.

\subsection*{Need for a Modern Monitoring Tool}
Although the Icelandic Meteorological Office (IMO) provides earthquake data, existing platforms often lack real-time interactivity and flexible visualization tools that allow users to explore seismic activity intuitively. \textbf{MPGV Monitor} addresses this gap by offering an interactive, web-based monitoring system that integrates modern technologies for real-time data collection and visualization.

The seismic dataset is obtained from multiple authoritative sources, primarily the Icelandic Meteorological Office’s MPGV records (\texttt{hraun.vedur.is}) and the high-frequency Skjálftalísa API. Since both sources have been available consistently from June 2020 onward, the system integrates them into a unified catalogue through an automated ingestion pipeline. APScheduler triggers an update cycle every three minutes, during which new MPGV events are scraped, Skjálftalísa events are fetched, and both datasets are merged using predefined temporal, spatial, and magnitude-based matching rules. All events with magnitude $\geq 2.7$ are stored in an SQLite database, ensuring efficient querying, historical analysis, and protection against duplication or inconsistencies between sources.

\subsection*{System Features}
The backend, implemented in Flask, manages data retrieval, multi-source ingestion, reconciliation, and database updates, while also exposing REST endpoints to the frontend. In contrast to the project’s earlier prototype, which relied on static map generation, the current architecture shifts all rendering and interaction to a React-based interface. This enables real-time updates, smoother navigation, and a significantly more responsive user experience.

A key enhancement of the system is the timeline slider, which allows users to filter earthquakes by year, month, and day, with the default view showing all available processed data. Additional functionalities include magnitude-scale filtering, dynamic marker colouring based on the active time window or magnitude range, volcano overlays, optional latitude–longitude grid lines, each of which can be enabled or disabled through dedicated toggles and ShakeMap integration for verifying shaking intensity where available. The interface also supports multiple map styles—including roadmap, satellite, and dark mode—providing users with flexible and informative perspectives on Icelandic seismic activity.

\subsection*{Contributions and Future Directions}
\textbf{MPGV Monitor} serves a wide audience, including seismologists, local authorities, researchers, and the general public. By providing near real-time and intuitive seismic visualizations, the system contributes to improved earthquake preparedness, risk assessment, and scientific investigation.

Planned improvements include migrating from SQLite to PostgreSQL to handle larger datasets, introducing predictive models using machine learning, and optimizing performance through caching and request rate limiting. These steps aim to ensure scalability, maintainability, and long-term adoption by the Icelandic Meteorological Office.

In summary, MPGV Monitor demonstrates how modern web technologies can be leveraged to build a dynamic and reliable earthquake monitoring platform. By integrating automated data collection, an efficient backend, and an interactive frontend, the system provides a powerful tool for visualizing and understanding seismic activity in Iceland.

\section{Project Overview}

\subsection{Initial Setup}
The development of the \textbf{MPGV Monitor} project has undergone a substantial transformation since its initial version. The earlier prototype used Flask for backend services, where most data processing occurred server-side in Python. The frontend employed React but remained relatively static, relying on backend-generated map visualizations produced with Folium, which rendered basic OpenStreetMap tiles.
Although this approach yielded a functional prototype, it was constrained by limited interactivity, poor scalability, and reduced responsiveness. A key limitation was the absence of a fully functional time slider because the processing logic was tightly coupled to backend operations. Rendering dynamic visualizations directly in Flask also introduced performance bottlenecks when handling larger datasets.

\begin{figure}[H]
    \centering    \includegraphics[width=\linewidth, height=7cm]{Screenshots/Folium_Map_version.png}
    \caption{Folium Based Map Version}
\end{figure}

To address these limitations, the project transitioned to a more modernized architecture, combining Flask for backend API services with Vite and React for the frontend. This shift enabled greater interactivity, improved responsiveness, and better scalability by offloading much of the visualization logic to the client side. The new architecture also provided a more maintainable and extensible foundation for introducing advanced features such as the time slider and the earthquake magnitude scale etc.

Python remains the core language of the backend due to its mature ecosystem for web development and data processing. Flask serves as the lightweight web framework responsible for handling API requests and serving earthquake data in JSON format. The data ingestion logic combines traditional HTML scraping from the Icelandic Meteorological Office’s MPGV archive (\texttt{hraun.vedur.is}) with high-frequency seismic data fetched through the Skjálftalísa API. MPGV records are collected using \texttt{BeautifulSoup} and \texttt{requests}, while Skjálftalísa events are retrieved in structured JSON form and stored in a dedicated raw-data table. Both sources are cleaned, normalised, and written to an SQLite database. A reconciliation algorithm subsequently merges MPGV and Skjálftalísa events into a unified catalogue based on temporal, spatial, and magnitude-based matching rules.
This ensures efficient querying and avoids duplication of records.

Unlike the earlier implementation, where filtering and processing were performed on the backend and visualised through static Folium maps, the new system leverages React to dynamically display earthquake data on an interactive Google Maps component. This design allows the frontend to handle rendering, enabling seamless updates without requiring full page reloads. It significantly improves user experience by supporting real-time interactivity, which had been difficult to achieve in the backend-heavy architecture.

Vite, a modern build tool and development server, was chosen for the frontend instead of the traditional Create React App. Vite accelerates development through faster builds, hot module replacement, and optimized performance. With React’s component-based structure, the frontend is modular and scalable, making it easier to introduce new features. Dependencies for the backend are managed through a \texttt{requirements.txt} file, including Flask, pandas, requests, BeautifulSoup, SQLAlchemy for database management, APScheduler for automated updates, and additional modules for Skjálftalísa ingestion, EPOS ShakeMap verification, and volcano data retrieval.
On the frontend, dependencies are tracked in \texttt{package.json}, including React, \texttt{@react-google-maps/api} for Google Maps integration, and Tailwind CSS alongside custom modules for styling.

Overall, the transition to a Vite + React-based frontend and a lightweight Flask API backend resolved key limitations of the earlier version. It provided measurable improvements in responsiveness, scalability, and maintainability, while establishing a robust foundation for future enhancements.

A reconciliation algorithm subsequently merges MPGV and Skjálftalísa events into a unified dataset. This process compares events from both sources using temporal proximity, spatial distance, and magnitude similarity to identify matches and resolve duplicates. The resulting merged catalogue, stored in the \texttt{earthquake\_merged} table, provides improved accuracy in event location, depth, and magnitude while ensuring consistency across updates.

In addition to earthquake data, the system ingests auxiliary information from the \textbf{EPOS Iceland} APIs. The EPOS Volcanoes API supplies volcano locations, elevation values, and descriptive metadata, enabling the display of volcano overlays on the map. The EPOS ShakeMap API provides shaking intensity products that can be associated with individual earthquakes; these are cross-referenced against the merged catalogue to supply optional ShakeMap links for supported events. These external datasets extend the analytical capabilities of the system and enhance its usefulness for hazard context.

All data from MPGV, Skjálftalísa, and EPOS endpoints are stored in an SQLite database, which supports efficient queries, automated updates, and consistent long-term storage. The backend exposes this information through Flask API routes, while the frontend retrieves and visualizes the data in real time. Features such as the time slider, magnitude scale, timeline-based or magnitude-based marker colouring, volcano overlays, and ShakeMap integration are made possible by this multi-source ingestion framework.

Overall, the use of MPGV HTML scraping, Skjálftalísa API ingestion, EPOS datasets, and a reconciliation-based merging pipeline provides the MPGV Monitor with a comprehensive, scalable, and extensible data foundation. This enables responsive visualizations, robust filtering, and reliable seismic interpretation for users across research, public, and hazard-monitoring domains.

\section{Data Scraping and Merging}

The \textbf{MPGV Monitor} system relies on a unified earthquake catalogue that combines multiple sources into a single, quality-controlled dataset. This chapter traces the evolution of the data pipeline from an initial single-month prototype to the current multi-source ingestion workflow and introduces the conceptual design of the reconciliation process. The emphasis is on \emph{how} the scraping and merging strategy matured over time, rather than on the implementation details of the backend, which are discussed separately in Chapter~4.

\vspace{0.4cm}

\subsection{Initial Approach}

The earliest implementation of data scraping focused on extracting earthquake records for a single month---October~2023---from the Icelandic Meteorological Office’s MPGV archive. This preliminary test served as a proof of concept, demonstrating that the monthly HTML pages on \texttt{hraun.vedur.is} could be parsed reliably and that automated harvesting of Icelandic earthquake data was technically feasible.

Using Python libraries such as \texttt{requests}, \texttt{BeautifulSoup}, and \texttt{pandas}, the script retrieved and parsed the HTML table, cleaned the dataset, and retained only records with magnitudes $\geq 3.0$. The processed data was then stored in a text file for basic visualization and preliminary validation.

Although limited in scope, this experiment confirmed that automated scraping was viable, that the MPGV HTML tables were sufficiently stable for programmatic parsing, and that the extracted attributes (date--time, latitude, longitude, depth, magnitude) could be normalized for further processing.

\subsection{Previous Approaches}

As the project evolved, two intermediate approaches were developed before arriving at the final database-driven, multi-source system. Both of these methods still relied on MPGV as the sole data provider, but they gradually expanded the temporal coverage and improved the structure of the stored data.

\subsubsection*{Manual Scraping with Text File Storage}

In the first extension, the scraper was generalised to fetch not only October~2023 but also the most recent month’s dataset from MPGV and store it locally in a plain-text file. Data was updated only when the script was executed manually. This approach was sufficient for exploratory analysis and basic visualisations, since the text file could be reloaded into Python notebooks or plotting tools.

However, the method had three important limitations. First, it could not efficiently retrieve historical records spanning multiple years. Second, each manual run overwrote the previous file, making it difficult to preserve a consistent long-term catalogue. Third, the loosely structured text format complicated downstream processing and increased the risk of format inconsistencies.

\subsubsection*{Dynamic Scraping with CSV Storage}

To expand coverage and improve structure, the scraper was redesigned to traverse multiple years and months programmatically, consolidating results into a single CSV file. Instead of targeting one fixed month, the script discovered available year and month links from the MPGV index page and iterated over them to harvest all records since June~2020.

\textbf{Code Snippet: Aggregating Monthly Records into CSV}

\begin{verbatim}
def scrape_all_to_csv():
    all_data = pd.DataFrame(columns=['DateTime','Lat','Lon','Depth','Mw'])
    response = requests.get(BASE_URL)
    soup = BeautifulSoup(response.content, 'html.parser')

    year_links = [a['href'].strip('/') for a in soup.find_all('a')
                  if a['href'].endswith('/')]

    for year in year_links:
        for month in get_months(year):
            monthly_data = get_monthly_data(year, month)
            all_data = pd.concat([all_data, monthly_data])

    all_data.to_csv("earthquakes.csv", index=False)
\end{verbatim}

This CSV-based approach addressed some of the shortcomings of the manual text-file workflow. It allowed the entire MPGV archive to be downloaded in a reproducible manner, enabled simple filtering and aggregation using \texttt{pandas}, and provided a convenient input format for early visualisation experiments.

On the other hand, several issues emerged as the dataset grew. Maintaining synchronisation between the CSV file and any downstream visualisation or web frontend became increasingly fragile: every update required regenerating and redistributing the entire file. Moreover, performing repeated full-archive scrapes was inefficient and unnecessary once most historical data had already been ingested. These drawbacks motivated a transition from flat-file storage to a dedicated database.

\subsection{Current Approach: Multi-Source Ingestion and Conceptual Merging}

The final design replaces the earlier MPGV-only, file-based workflow with an integrated, multi-source ingestion pipeline backed by an SQLite database. Instead of treating MPGV as the sole data provider, the system now combines three authoritative sources:

\begin{itemize}
    \item the MPGV HTML archive (curated earthquake solutions),
    \item the Skjálftalísa JSON API (high-frequency preliminary detections),
    \item and EPOS Iceland endpoints for volcano and ShakeMap metadata.
\end{itemize}

All data is written to \texttt{earthquakes.db}, where it is organised into separate tables for MPGV events, Skjálftalísa raw detections, a merged catalogue, and auxiliary volcano and ShakeMap information. This chapter focuses on the \emph{data-level} view of this pipeline; the concrete SQLAlchemy models, scheduler configuration, and Flask routes are described in detail in Chapter~4.

\subsubsection*{Automated Updates with Periodic Jobs}

In the current system, updates are no longer triggered manually. Instead, a periodic job executes the ingestion and merging pipeline at fixed intervals. Conceptually, each cycle performs three main operations:

\begin{enumerate}
    \item Scrape the latest MPGV records and append any new events to the MPGV table.
    \item Fetch recent Skjálftalísa detections and update the raw Skjálftalísa table.
    \item Run the reconciliation algorithm to produce an up-to-date unified catalogue.
\end{enumerate}

Only events with magnitude $\geq 2.7$ are retained. Duplicate entries are avoided by combining database-level uniqueness constraints (for example on timestamp and coordinates) with event matching rules based on temporal proximity, spatial distance, and magnitude similarity. The effect is that repeated runs of the pipeline are \emph{idempotent}: if no new earthquakes have occurred, the contents of the merged catalogue remain unchanged, even though the reconciliation logic is executed again.

\subsubsection*{Conceptual Ingestion and Merge Pipeline}

From a conceptual perspective, the multi-source pipeline can be expressed as a three-stage dataflow:

\begin{enumerate}
    \item \textbf{Ingestion}: each source-specific module (MPGV scraper, Skjálftalísa client, EPOS volcano loader) harvests data from its respective endpoint and writes normalised records into dedicated tables.
    \item \textbf{Reconciliation}: a matching algorithm compares candidate events from MPGV and Skjálftalísa and decides whether they refer to the same earthquake based on time, distance, and magnitude tolerances.
    \item \textbf{Merged catalogue}: for each MPGV event, the algorithm either finds a corresponding Skjálftalísa detection and records a \texttt{matched} entry or classifies it as \texttt{v\_only} if no suitable counterpart exists. The result is stored in a unified table that is consumed by the frontend.
\end{enumerate}

At this stage, it is useful to view reconciliation primarily as a \emph{data integration} problem: two different catalogues with slightly different coverage and timing must be aligned into a single, provenance-aware representation. The exact mathematical thresholds, depth-selection policies, and implementation details of the matching algorithm are presented in Chapter~4, where the reconciliation logic is discussed as part of the backend architecture.

In the deployed system, the unified catalogue is exposed to the React frontend through RESTful API endpoints. The design choice to separate ingestion, reconciliation, and delivery into distinct stages makes it easier to evolve each component independently. For example, additional data sources or alternative matching strategies can be incorporated without changing the general flow from raw source tables to a merged, visualisation-ready dataset.

\subsubsection*{Evolution of the Data Pipeline}

Overall, the data pipeline for \textbf{MPGV Monitor} has progressed through three major stages. The initial prototype scraped a single month of MPGV data into text files, suitable only for small-scale experiments. The subsequent CSV-based approach introduced dynamic scraping across years and months, enabling historical analysis but still relying on manual updates and monolithic flat-file storage. The final pipeline adopts a database-centric, multi-source architecture with automated updates and a dedicated reconciliation step that integrates MPGV and Skjálftalísa catalogues.

This evolution reflects a shift from ad hoc data collection towards a robust, extensible ingestion and merging strategy that is capable of supporting long-term monitoring, near real-time updates, and advanced analysis. The next chapter builds on this conceptual foundation and presents the backend implementation in detail, including the database schema, scheduling infrastructure, reconciliation algorithm, ShakeMap validation pipeline, and Flask API layer that expose the merged catalogue to the frontend.

\section{Backend Development}

The backend of the \textbf{MPGV Monitor} system is implemented as a persistent Flask application that orchestrates data ingestion, reconciliation, storage, and delivery to the frontend. In contrast to the early prototypes described in Chapter~3, where scraping logic was embedded in standalone scripts and results were stored in flat files, the current backend adopts a modular architecture built around SQLAlchemy ORM models, an SQLite database, a periodic scheduling subsystem, and a set of RESTful API endpoints.

At a high level, the backend operates through several interconnected layers. Source-specific ingestion modules collect information from MPGV, Skjálftalísa, and EPOS endpoints; a reconciliation layer matches and merges events from the two seismic catalogues; a validation layer associates EPOS ShakeMaps with merged events; and the resulting products are stored in an SQLite database and exposed to the React frontend through a JSON-based API. These components run continuously under the coordination of \texttt{APScheduler}, which triggers the automated update cycle every three minutes and keeps the local catalogue synchronized with the external services.

\subsection{Core Database Models}

A central element of the backend architecture is the structured SQLite schema, exposed through SQLAlchemy ORM classes in the Flask application. The schema deliberately separates raw source tables from the derived, unified catalogue and auxiliary products. This separation provides consistency, traceability, and efficient querying across the entire pipeline. The main tables are \texttt{Earthquake} for MPGV-sourced events, \texttt{EarthquakeSRaw} for Skjálftalísa detections, \texttt{EarthquakeMerged} for the unified view, \texttt{Volcano} for EPOS volcano metadata, and \texttt{ShakeMapLink} for cached ShakeMap validation results.

The \textbf{Earthquake} model represents earthquake events scraped from the MPGV HTML archive (denoted internally as \emph{v} events). MPGV entries are curated and validated by the Icelandic Meteorological Office and therefore act as the authoritative baseline for the system. The table stores attributes such as timestamp, location, depth, and magnitude, all normalised from the monthly pages on \texttt{hraun.vedur.is}. A uniqueness constraint on the combination of timestamp and coordinates prevents duplicate insertions during repeated ingestion runs.

\begin{verbatim}
class Earthquake(db.Model):
    id         = db.Column(db.Integer, primary_key=True)
    date_time  = db.Column(db.String, index=True, nullable=False)
    latitude   = db.Column(db.Float, nullable=False)
    longitude  = db.Column(db.Float, nullable=False)
    depth      = db.Column(db.Float)
    mw_mean    = db.Column(db.Float, nullable=False)
\end{verbatim}

The \textbf{EarthquakeSRaw} model stores raw Skjálftalísa API detections (denoted as \emph{s} events). Skjálftalísa provides high-frequency, preliminary seismic detections that often appear before the corresponding MPGV solutions. These records are stored with their original event identifiers, magnitudes, timestamps, and coordinates. Because Skjálftalísa can include small or transient events and early solutions, the raw table deliberately preserves the data as-ingested to maintain provenance for the reconciliation step.

\begin{verbatim}
class EarthquakeSRaw(db.Model):
    id         = db.Column(db.Integer, primary_key=True)
    event_id   = db.Column(db.String, unique=True, nullable=False)
    date_time  = db.Column(db.String, index=True, nullable=False)
    latitude   = db.Column(db.Float, nullable=False)
    longitude  = db.Column(db.Float, nullable=False)
    depth      = db.Column(db.Float)
    magnitude  = db.Column(db.Float)
\end{verbatim}

The \textbf{EarthquakeMerged} model represents the unified catalogue that is served directly to the frontend. Each row corresponds to a single earthquake that has either been matched across MPGV and Skjálftalísa or originates from only one of them. During reconciliation, the system compares events from both sources using temporal, spatial, and magnitude thresholds (see Section~4.\ref{subsec:reconcile}) and decides whether they describe the same physical event. If so, the merged entry inherits MPGV parameters while retaining the Skjálftalísa identifier and diagnostic metrics such as time and distance offsets. Otherwise, the event is recorded as MPGV-only.

\begin{verbatim}
class EarthquakeMerged(db.Model):
    id           = db.Column(db.Integer, primary_key=True)
    date_time    = db.Column(db.String, index=True, nullable=False)
    latitude     = db.Column(db.Float, nullable=False)
    longitude    = db.Column(db.Float, nullable=False)
    depth        = db.Column(db.Float)
    mw_mean      = db.Column(db.Float, nullable=False)

    status       = db.Column(db.String, nullable=False)   # 'matched' | 'v_only'
    v_src_key    = db.Column(db.String)
    s_event_id   = db.Column(db.String)
    match_dt_sec = db.Column(db.Float)
    match_dist_km= db.Column(db.Float)
    match_dm     = db.Column(db.Float)
\end{verbatim}

The \textbf{Volcano} table stores metadata for Icelandic volcanoes obtained from EPOS Iceland, including their geographic locations and elevations. This information is used to draw volcano overlays in the frontend and to support contextual analyses such as distance-to-volcano queries or swarm clustering.

\begin{verbatim}
class Volcano(db.Model):
    id           = db.Column(db.Integer, primary_key=True)
    name         = db.Column(db.String, nullable=False)
    description  = db.Column(db.Text)
    elevation_m  = db.Column(db.Float)
    elevation_ft = db.Column(db.Float)
    latitude     = db.Column(db.Float, nullable=False)
    longitude    = db.Column(db.Float, nullable=False)
    last_eruption= db.Column(db.String)
\end{verbatim}

Finally, the \textbf{ShakeMapLink} table acts as a cache of EPOS ShakeMap products associated with catalogued events. For each event timestamp, it stores the URL of the chosen ShakeMap, together with metadata describing the matching quality (time difference, spatial distance, and magnitude difference between the event and the ShakeMap solution).

\begin{verbatim}
class ShakeMapLink(db.Model):
    __tablename__ = "shakemap_links"

    dt          = db.Column(db.String, primary_key=True)
    url_view_file = db.Column(db.String)
    origin_time = db.Column(db.String)

    sm_lat   = db.Column(db.Float)
    sm_lon   = db.Column(db.Float)
    sm_mag   = db.Column(db.Float)
    sm_depth = db.Column(db.Float)

    dt_sec   = db.Column(db.Float)
    dist_km  = db.Column(db.Float)
    dm       = db.Column(db.Float)

    status   = db.Column(db.String)  # "valid" | "no_candidate" | "no_valid" | "error"
    note     = db.Column(db.String)
\end{verbatim}

By maintaining both raw source tables and a carefully constructed merged catalogue, along with supplementary volcano and ShakeMap layers, the backend preserves the full provenance of ingested records while providing a clean, deduplicated dataset for visualisation and analysis.

\subsection{Dynamic Data Ingestion}

The dynamic ingestion pipeline is responsible for keeping the local database synchronized with the external MPGV, Skjálftalísa, and EPOS services. Rather than relying on manual runs or static files, the system uses three dedicated modules---\texttt{scrape.py}, \texttt{skjalftalisa\_client.py}, and \texttt{volcano\_scraper.py}---to harvest and normalise data from each source. All ingestion operations write directly into the ORM-backed tables described above.

The design of the ingestion framework is guided by four goals: robustness against temporary outages or malformed data, near real-time updates without overloading third-party APIs, explicit separation of raw and processed records, and extensibility for future data sources. Each module therefore encapsulates its own networking logic, error handling, and normalisation rules, while exposing a simple interface for the scheduler to trigger.

\paragraph{MPGV Scraper.}

The MPGV scraper, implemented in \texttt{scrape.py}, parses the monthly HTML pages published by the Icelandic Meteorological Office. For each month, the scraper retrieves the \texttt{<table>} element containing earthquake records, converts its rows into Python dictionaries, cleans and normalises the values, and applies a magnitude threshold so that only events with $Mw_{\text{mean}} \geq 2.7$ are retained. Records with missing or malformed coordinates, depth, or magnitude are discarded to avoid polluting the catalogue with incomplete entries. A uniqueness constraint on \texttt{(date\_time, latitude, longitude)} prevents duplicate rows when the scraper is re-run.

\paragraph{Skjálftalísa Client.}

The Skjálftalísa ingestion module, implemented in \texttt{skjalftalisa\_client.py}, interacts with the JSON-based Skjálftalísa API. The service returns column-oriented arrays of values, which the client converts into row-wise dictionaries containing event IDs, timestamps, latitudes, longitudes, depths, and magnitudes. Timestamps are normalised to the uniform format \texttt{YYYY-MM-DD HH:MM:SS} in UTC, and magnitudes are converted to floating-point values with appropriate filtering. The resulting records are inserted into the \texttt{earthquake\_s\_raw} table, keyed by Skjálftalísa’s \texttt{event\_id} for later matching.

\paragraph{EPOS Volcano Scraper.}

The \texttt{volcano\_scraper.py} module fetches volcano metadata from the EPOS Iceland API. Because EPOS exposes several endpoints and data formats, the scraper performs additional normalisation to reconcile different field names (for example, \texttt{lat\_dd} versus \texttt{latitude}) and ensure that all entries are represented in a consistent schema. Elevation is stored in metres and also converted to feet for convenience. This process populates the \texttt{volcano} table with up-to-date volcano locations and basic descriptive information.

\paragraph{Operational Characteristics.}

To prevent transient issues from corrupting the database, each ingestion module handles network timeouts, retries, and schema changes defensively. Failed cycles do not overwrite existing data, and exceptions are logged for later inspection. In practice, the ingestion pipeline is also optimised for efficiency: the MPGV scraper concentrates on recent months after the full historical archive has been ingested, the Skjálftalísa client typically fetches only the last \emph{n} days of activity, and EPOS metadata is refreshed infrequently, since volcano properties evolve slowly on the timescale of the deployment.

\subsection{Automated Scheduling}

Automated ingestion in \textbf{MPGV Monitor} is driven by \texttt{APScheduler}, which periodically triggers a composite backend job without any manual intervention. The scheduler is configured in \texttt{app.py} and attached to the Flask application context. It registers a recurring job that executes the entire ingestion and merging workflow at a fixed interval:

\begin{verbatim}
scheduler.add_job(
    scheduled_scrape,
    "interval",
    minutes=3,
    max_instances=1
)
\end{verbatim}

The choice of a three-minute interval reflects a compromise between data freshness and resource usage. Skjálftalísa can update at sub-minute cadence, whereas MPGV solutions are published on scales of tens of minutes to hours. Running the full update every three minutes ensures that Skjálftalísa detections are incorporated soon after they are available, while also catching new MPGV entries in a timely fashion, without placing excessive load on the external services or the local SQLite database.

The \texttt{max\_instances=1} parameter is critical from a reliability perspective. It guarantees that a new scheduler run is not started while the previous one is still active, thereby avoiding overlapping writes and potential race conditions. Each scheduled execution of \texttt{scheduled\_scrape} performs a full pass of the pipeline: MPGV scraping, Skjálftalísa fetching, reconciliation into the merged table, and optional ShakeMap validation.

In the current deployment, where the entire historical catalogue from June~2020 has already been ingested, many scheduler cycles log messages such as \enquote{\texttt{:)\ 0 new earthquake records added to SQLite via Flask.}} followed by \enquote{\texttt{Merged rows written: 1753}}. This behaviour illustrates that the pipeline is idempotent: the job can be re-run safely even when no new events are available, and the content of the merged table remains stable. When new earthquakes are published by the Icelandic Meteorological Office, the same mechanism automatically incorporates them into both the MPGV table and the unified catalogue.

From an architectural viewpoint, the scheduler runs as a background component alongside the Flask application. HTTP endpoints such as \texttt{/earthquakes}, \texttt{/volcanoes}, and \texttt{/shakemap/\{dt\}} remain responsive while ingestion is in progress. Because the ingestion and reconciliation steps operate within database transactions, partial failures (for example, a temporary API outage) do not corrupt existing tables: exceptions are caught and logged, and the next scheduled cycle resumes from a clean state.

\subsection{Reconciliation and Merging}
\label{subsec:reconcile}

The reconciliation algorithm integrates MPGV (\textit{v}) events with Skjálftalísa (\textit{s}) detections to form a unified earthquake catalogue. Its purpose is to determine whether a pair of events from the two sources represents the same physical earthquake. Matching is based on three criteria: temporal proximity, spatial distance, and similarity in magnitude.

For an MPGV event $v$ and a Skjálftalísa event $s$, a valid match must satisfy:

\[
|\Delta t| < 3 \text{ seconds}, \qquad
\Delta d < 10 \text{ km}, \qquad
|\Delta Mw| < 2.0,
\]

where $\Delta t$ is the absolute difference in origin times, $\Delta d$ is the great-circle epicentral distance, and $\Delta Mw$ is the magnitude difference. These thresholds were tuned empirically to maximise correct matches while avoiding spurious associations.

At runtime, the system loads all Skjálftalísa detections into a time-indexed structure, enabling efficient lookup of candidate events whose timestamps differ from the corresponding MPGV event by less than three seconds. The overall reconciliation workflow is illustrated in Figure~\ref{fig:reconcile-workflow}. For each MPGV entry, the algorithm retrieves all Skjálftalísa events satisfying the temporal constraint, computes the spatial separation and magnitude deviation, filters out invalid candidates, and classifies the event as either \texttt{v\_only} or \texttt{matched}. When multiple candidates pass the thresholds, a deterministic tie-breaking rule selects the most plausible match using a lexicographic ordering of distance, temporal offset, and magnitude difference.

The corresponding Python implementation is shown below. It reflects the control flow depicted in Figure~\ref{fig:reconcile-workflow} and implements the threshold rules precisely. Diagnostic information such as time offset (\texttt{match\_dt\_sec}), epicentral distance (\texttt{match\_dist\_km}), and magnitude deviation (\texttt{match\_dm}) is stored alongside each merged event, enabling quality assessment and downstream analysis.

\begin{verbatim}
for v in v_rows:
    candidates = []

    # Search Skjálftalísa events within 3 seconds of the MPGV timestamp
    for s in s_index.get_window(v.date_time, window_sec=2):
        dt_abs  = abs(v.dt_ts - s.dt_ts)
        dist_km = haversine(v.lat, v.lon, s.lat, s.lon)
        dm      = abs(v.mw_mean - (s.magnitude or 0))

        # Candidate must satisfy all three thresholds
        if dt_abs < 3 and dist_km < 10 and dm < 2.0:
            candidates.append((dist_km, dt_abs, dm, s))

    # No valid Skjálftalísa match → v_only
    if not candidates:
        write_v_only(v)
        continue

    # Choose best candidate via lexicographic ordering
    candidates.sort(key=lambda c: (c[0], c[1], c[2]))
    _, dt, dist, best_s = candidates[0]

    write_matched(v, best_s, dt, dist, dm)
\end{verbatim}

By encoding the reconciliation outcome directly in the \texttt{status} field and retaining both MPGV and Skjálftalísa identifiers, the merged catalogue preserves full provenance. This ensures that matches can be audited, alternative matching thresholds can be evaluated, and the system can accommodate potential future refinements to the algorithm.

\subsection{ShakeMap Validation Pipeline}
\label{subsec:shakemap}

While the merged earthquake catalogue provides a consistent record of seismicity, it does not directly describe the shaking intensity or ground-motion patterns associated with each event. To enrich the dataset with this information, the system includes a ShakeMap validation pipeline that searches for EPOS Iceland ShakeMap products corresponding to each merged earthquake. The validation logic, implemented in \texttt{shakemap\_validator.py}, queries the EPOS API, evaluates candidate ShakeMaps, and records the most plausible match in the \texttt{shakemap\_links} table.

\subsubsection*{Validation Procedure}

For each event in the merged catalogue with origin time $t$, epicentre $(\phi, \lambda)$, and magnitude $M_w$, the validator performs the following steps:

\begin{enumerate}
    \item \textbf{ShakeMap retrieval.} Query the EPOS ShakeMap API for products occurring within a 30-minute window centred on the event time and lying inside a latitude--longitude bounding box around the event location.
    \item \textbf{Candidate evaluation.} For every returned ShakeMap, compute:
    \[
    |\Delta t| = |t_{\text{event}} - t_{\text{sm}}|, \quad 
    \Delta d = \text{dist}\big((\phi,\lambda), (\phi_{\text{sm}},\lambda_{\text{sm}})\big), \quad
    |\Delta M| = |M_w - M_{w,\text{sm}}|.
    \]
    ShakeMaps exceeding predefined limits on any of these metrics are rejected.
    \item \textbf{Best-match selection.} If multiple valid candidates remain, select the one with the smallest combination of temporal offset, spatial distance, and magnitude deviation using a lexicographic ordering.
    \item \textbf{Database update.} Store the selected ShakeMap (or the failure category) in the \texttt{shakemap\_links} table together with diagnostic values such as \texttt{dt\_sec}, \texttt{dist\_km}, and \texttt{dm}.
\end{enumerate}

If EPOS returns no ShakeMaps for the query window, the event is labelled \texttt{no\_candidate}. If candidates exist but none satisfy the validation thresholds, the status becomes \texttt{no\_valid}. Errors during API retrieval or metadata parsing result in the status \texttt{error}. All outcomes are preserved explicitly, ensuring transparency in downstream visualisation.

\subsection{Flask API Layer}

The final component of the backend is the Flask API layer, which exposes the processed and reconciled data stored in SQLite to the React frontend and external tools such as Postman or command-line clients. All endpoints provide JSON responses, and the API surface is intentionally read-only to preserve database integrity, as ingestion and reconciliation are handled exclusively by the scheduler.

The principal routes implemented in \texttt{app.py} are:

\begin{itemize}
    \item \texttt{/earthquakes} --- returns the unified catalogue from \texttt{earthquake\_merged}, optionally filtered to the last \emph{N} days via a query parameter.
    \item \texttt{/volcanoes} --- returns volcano metadata from the \texttt{volcano} table for map overlay visualisation.
    \item \texttt{/shakemap/<dt>} --- returns a validated ShakeMap link and associated diagnostic metadata for the event whose timestamp is \texttt{<dt>}, if available.
    \item \texttt{/reconcile} --- manually triggers a reconciliation run; this endpoint is used exclusively for debugging and evaluation.
    \item \texttt{/scrape} --- performs a controlled ingestion cycle on demand; primarily useful during development and testing.
\end{itemize}

A typical endpoint serialises ORM objects into dictionaries and wraps them in a JSON response. For example, the endpoint providing the unified earthquake catalogue is defined as follows:

\begin{verbatim}
@app.route("/earthquakes", methods=["GET"])
def get_earthquake_data():
    with app.app_context():
        rows = EarthquakeMerged.query \
            .order_by(EarthquakeMerged.date_time.desc()) \
            .all()

        return jsonify([
            {
                "Date-time": r.date_time,
                "Latitude":  r.latitude,
                "Longitude": r.longitude,
                "Depth":     r.depth,
                "Mw_mean":   r.mw_mean,
                "status":    r.status
            } for r in rows
        ])
\end{verbatim}

Because the Flask application and the scheduler operate on the same SQLite database, all API calls always return the most up-to-date state of the catalogue without requiring additional scraping at request time. The clear separation between read-heavy API endpoints and write-heavy scheduled tasks ensures responsive user queries while maintaining consistency during ingestion or reconciliation. Furthermore, the simplicity of the JSON-based interface allows the frontend to efficiently render earthquake markers, volcano overlays, and ShakeMap icons using lightweight requests.

\subsection{Summary}

In summary, the backend of \textbf{MPGV Monitor} forms a robust, modular, and extensible system that integrates multi-source ingestion, automated scheduling, event reconciliation, ShakeMap validation, and RESTful delivery through a clean Flask API layer. The use of SQLAlchemy ORM models and an SQLite database enables reliable, transaction-safe operations; the ingestion modules encapsulate the complexities of interacting with MPGV, Skjálftalísa, and EPOS; the scheduler ensures timely updates without manual intervention; and the reconciliation and validation layers generate a provenance-aware, deduplicated catalogue.

Together, these components provide a stable foundation for the real-time visualisation and interactive exploration features of the frontend. The modular design also facilitates future extensions, such as additional data sources, predictive modelling, or enhanced query capabilities, ensuring that the system can evolve as new monitoring or research needs arise.

\subsubsection{Technical Challenges: Handling Multiple Requests Efficiently}

\subsection{Original Problem Statement}
In the development of the \textit{MPGV Monitor: Dynamic Visualization of Seismic Data for Iceland}, one of the key technical challenges was handling multiple user requests simultaneously. Initially, the web application featured a manual \textit{``Update Data''} button, which allowed users to scrape and update the earthquake dataset upon request. However, this approach introduced several issues:

\begin{itemize}
    \item \textbf{Race conditions:} If multiple users pressed the update button simultaneously, concurrent scraping processes could conflict, leading to inconsistent or corrupted data.
    \item \textbf{Performance bottlenecks:} Each update triggered a new scraping request, consuming significant computational resources and network bandwidth.
    \item \textbf{Data inconsistency:} Users accessing the map at different times might see outdated or incomplete data due to manual update delays.
\end{itemize}

To overcome these challenges, we implemented an automated, scalable data retrieval system that dynamically updates every three minutes while ensuring efficient database handling and real-time frontend updates.

\subsection{Adopted Approach: Automated Data Scraping and Database Integration}
To resolve the above issues, we introduced the following architectural changes:

\begin{enumerate}
    \item \textbf{Automated Data Scraping:} Instead of allowing manual updates, we used Flask's \texttt{APScheduler} to periodically fetch new earthquake data every three minutes.
    \item \textbf{Database Storage:} We replaced the CSV-based storage system with an SQLite database to handle concurrent read and write operations safely.
    \item \textbf{Frontend Auto-Refresh:} The frontend now periodically fetches new data without requiring a page refresh.
\end{enumerate}

A simplified version of the scheduled scraper implementation is shown below:

\begin{minted}{python}
from flask import Flask
from flask_sqlalchemy import SQLAlchemy
from apscheduler.schedulers.background import BackgroundScheduler

app = Flask(__name__)
app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///backend/data/earthquakes.db"
db = SQLAlchemy(app)

scheduler = BackgroundScheduler()

@scheduler.scheduled_job('interval', minutes=3)
def scheduled_scrape():
    with app.app_context():
        from scrape import scrape_all_earthquake_data
        scrape_all_earthquake_data()

scheduler.start()
\end{minted}

\subsection{Challenges Faced and Solutions Implemented}

During implementation, we encountered the following challenges:

\subsubsection{Issue 1: APScheduler Running Outside Flask Context}
Initially, \texttt{APScheduler} failed to interact with \texttt{SQLAlchemy} due to the lack of an application context. This resulted in the error:

\begin{minted}{text}
RuntimeError: The current Flask app is not registered with this 'SQLAlchemy' instance.
\end{minted}

\textbf{Solution:} We wrapped the database calls inside \texttt{with app.app_context()} to ensure the scheduler had access to the Flask application instance.

\subsubsection{Issue 2: Data Not Being Stored in SQLite}
After enabling scheduled scraping, we found that data was not appearing in the database. Debugging revealed that the scraper was still attempting to write to a CSV file instead of the SQLite database.

\textbf{Solution:} We modified \texttt{scrape.py} to use SQLAlchemy for database transactions:

\begin{minted}{python}
from app import app, db, Earthquake

def scrape_all_earthquake_data():
    with app.app_context():
        db.session.query(Earthquake).delete()
        # Scrape new data and insert into database
        for quake in scraped_data:
            db.session.add(Earthquake(**quake))
        db.session.commit()
\end{minted}

\subsubsection{Issue 3: Frontend Not Updating Automatically}
While the backend successfully updated data, the frontend did not reflect these changes unless manually refreshed.

\textbf{Solution:} We implemented a polling mechanism in React to fetch new data every three minutes:

\begin{minted}{javascript}
useEffect(() => {
    const loadData = async () => {
        const data = await fetchEarthquakeData();
        setAllData(data);
    };
    loadData();
    const interval = setInterval(loadData, 180000); // 3-minute polling
    return () => clearInterval(interval);
}, []);
\end{minted}

\subsection{Final Outcome}
After implementing these solutions, the system successfully:

\begin{itemize}
    \item Eliminates race conditions by running a single scheduled scraper instance.
    \item Improves performance by reducing redundant requests.
    \item Ensures that all users see the latest earthquake data without manual updates.
\end{itemize}

This approach significantly enhances scalability and user experience, making the system more robust for real-world deployment.

\subsection{Deployment Testing}

The deployment process for the web application involved hosting it on the Pluto server. The goal was to make the web application accessible via the public IP address and a specific port. This section describes the steps taken, challenges faced, and the final solution.

\subsubsection{Initial Challenges}
Initially, the application was run using the Flask development server with the following command:

\begin{verbatim}
python app.py
\end{verbatim}

While this worked locally, the Flask development server is not suitable for production. Moreover, it required the server session to remain active, making it unsuitable for long-term hosting. 

Attempts to run the application using \texttt{gunicorn} without proper configuration resulted in errors such as \texttt{ModuleNotFoundError} and port conflicts. For example, the following command failed due to a missing Python path:

\begin{verbatim}
gunicorn -b 0.0.0.0:7000 backend.app:app
\end{verbatim}

The error logs indicated issues with the Python path, which prevented the \texttt{backend} module from being located.

\subsubsection{Solution and Working Deployment}
To address these challenges, the following steps were implemented:

\begin{enumerate}
    \item Ensuring the virtual environment was activated:
    \begin{verbatim}
    source backend/venv/bin/activate
    \end{verbatim}
    
    \item Using \texttt{gunicorn} with the correct working directory and Python path:
    \begin{verbatim}
    gunicorn -b 0.0.0.0:7000 backend.app:app --chdir ~/QuakeMap
    \end{verbatim}

    \item Running the server in the background using \texttt{nohup} to keep it running after logging out:
    \begin{verbatim}
    nohup gunicorn -b 0.0.0.0:7000 backend.app:app \
      --chdir ~/QuakeMap > gunicorn.log 2>&1 &
    \end{verbatim}

    \item Verifying the server was running:
    \begin{verbatim}
    ps aux | grep gunicorn
    \end{verbatim}

    \item Ensuring the application was accessible via the server's public IP and port:
    \begin{verbatim}
    curl http://130.208.113.169:7000
    \end{verbatim}

    Users were able to access the web application at \texttt{http://130.208.113.169:7000/}.
\end{enumerate}

\includegraphics[width=\linewidth]{Screenshots/Deployment_Testing.png}

The results confirm that the application is successfully deployed and responds correctly to HTTP requests on \texttt{http://130.208.113.169:7000}.


\subsubsection{Why This Method Was Used}
This method was chosen due to its simplicity, flexibility, and compatibility with the existing server setup. The use of \texttt{gunicorn}, a production-ready WSGI server, ensured that the application could handle multiple concurrent requests efficiently. Running \texttt{gunicorn} in the background using \texttt{nohup} provided a practical solution for maintaining the application's availability without requiring root access or complex configuration changes.

Moreover, the approach leveraged existing tools and did not require additional installations like \texttt{tmux} or \texttt{screen}, which were not available on the server. By using \texttt{nohup}, the process was straightforward and effective, even in an environment with limited permissions.

\subsubsection{Benefits of This Approach}
The chosen method provided several advantages. It was straightforward to set up and required minimal configuration. The compatibility with the existing Python environment and server setup ensured smooth deployment without additional dependencies. Additionally, \texttt{gunicorn}'s lightweight nature made it resource-efficient and optimized for production. By exposing the application through the public IP and port, the solution facilitated easy accessibility without requiring complex networking configurations.

\subsubsection{Drawbacks and Limitations}
Despite its benefits, this method had certain drawbacks. If the server process crashed, it had to be restarted manually, as there was no automatic restart mechanism in place. Logging was limited to the \texttt{gunicorn.log} file, requiring manual monitoring for debugging purposes. The reliance on \texttt{nohup} for background execution made the process less robust compared to modern process managers like \texttt{systemd}. Additionally, this setup lacked load balancing capabilities, which limited scalability for handling high traffic.
