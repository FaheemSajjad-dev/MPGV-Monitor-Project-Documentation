\section*{\huge Abstract}
This thesis presents MPGV Monitor, a web application for visualising and exploring Icelandic earthquake activity from June 2020 onwards. The primary objective is to make historical and recent earthquake data accessible through an interactive map and connected analytical views, allowing users to examine events by location, time, and magnitude. During development, differences were identified between partially overlapping records from the Icelandic Meteorological Office (IMO) MPGV archive and the IMO Quakes API, including differences in reported time, location, magnitude, and depth. Reconciliation was therefore added to identify corresponding records, preserve source provenance, and support consistent presentation across the application.


MPGV defines the set of earthquakes presented by the application: an event enters the catalogue only when it is present in MPGV and satisfies the implemented threshold of $M_w \geq 3.0$. The backend searches the Quakes API for a corresponding record using temporal, spatial, and magnitude constraints. For a valid unique match, the MPGV-anchored event retains the MPGV time and magnitude and is enriched with Quakes API coordinates and depth. An event without such a match remains available as an MPGV-only record, while an unmatched Quakes API event does not independently enter the published catalogue. Match status and field provenance are retained so that depth-based analysis can distinguish matched values from MPGV-only source depths, which are labelled as unverified when included.

The React frontend uses MapLibre GL for vector, raster, and heatmap views and deck.gl for interactive earthquake markers. Users can navigate the map, adjust the time window and magnitude threshold, and colour markers by time or magnitude. Supplementary controls provide alternative map views, contextual overlays, recent selections, and event-level ShakeMap access. A connected Insights page applies date, magnitude, depth-quality, data-category, and time-grouping filters to the same catalogue and presents summary statistics, charts, sortable tables, and filtered data export. Events listed in Insights can be reopened on the map.

The principal contribution is an interactive computer-science visualisation application that connects geographic, temporal, and magnitude-based exploration with aggregate analysis, supported by a traceable MPGV-anchored data pipeline. MPGV Monitor is a research application rather than an earthquake-prediction system or a replacement for official operational monitoring. Remaining limitations include accessibility, external-service and tile-licensing dependencies, reliance on externally managed nginx TLS termination and HTTP-to-HTTPS redirects, and the concurrency constraints of SQLite. These limitations and outstanding evaluation needs are discussed separately from the implemented work.

\section{Introduction}
\label{sec:introduction}
Icelandic seismicity is monitored continuously, but the public interfaces through which it can be explored are mainly designed for recent-event awareness. The Icelandic Meteorological Office (IMO), for example, publishes a map of earthquakes detected during the previous 48 hours \cite{imo_quakes_48h}. Global services operated by the U.S. Geological Survey and the European-Mediterranean Seismological Centre provide broader geographical coverage \cite{usgs_latest_map,emsc_home}, while the IRIS Interactive Earthquake Browser supports longer-term catalogue exploration \cite{iris_ieb_app}. MPGV Monitor was conceived to provide a multi-year, Iceland-focused interface in which users could explore earthquakes by location, time, and magnitude through a map and connected analytical views. Links to relevant Icelandic ShakeMap products and explicit reconciliation of overlapping source records were incorporated as supporting capabilities.

\textbf{MPGV Monitor} was originally developed to make the MPGV earthquake catalogue accessible through that exploratory interface. The backend scrapes the MPGV archive and retrieves recent events from the IMO Quakes API, which was added as a secondary matching and enrichment source after differences and duplicate representations were identified during development. MPGV defines catalogue membership: the published catalogue contains qualifying MPGV events with $M_w \geq 3.0$ from 1~June~2020 onwards. Where a valid match exists, selected Quakes API fields enrich the MPGV-anchored event; unmatched Quakes API records do not independently enter the published catalogue.

The project has passed through several frontend implementations. The first prototype generated a static Folium map on the server, and a later version used the Google Maps JavaScript API. Google Maps provided a workable interactive prototype, but it introduced an API-key and billing dependency that was undesirable for an academic system intended for institutional deployment. Leaflet was subsequently used as an open-source replacement. In the final implementation described by this thesis, Leaflet has also been removed: MapLibre GL renders the map and its tile layers, while deck.gl renders the interactive earthquake markers. This separation allows the application to use the same WebGL-based map for vector, raster, and heatmap views, and avoids maintaining parallel mapping engines.

This chapter introduces the motivation and scope of the work, states the problem addressed by the application, and summarises its principal contributions. Detailed discussion of the scientific context, data pipeline, backend, frontend, and deployment is left to the later chapters.

\subsection*{Context and Motivation}
Iceland lies on the Mid-Atlantic Ridge at the divergent boundary between the North American and Eurasian plates. The hotspot beneath the island broadens and complicates this plate-boundary zone \cite[p.~35]{Einarsson2008}. Earthquake activity in Iceland reflects both tectonic and volcanic processes and includes frequent low-magnitude events, concentrated swarms, and occasional larger earthquakes \cite[pp.~75--79]{Jakobsdottir2008}. This scientific background is considered in more detail in the following chapter; for the present work, its main consequence is that useful exploration must connect space and time while allowing events to be filtered and compared by magnitude. A short list of recent epicentres cannot show how a swarm developed over several months, how activity shifted between volcanic systems, or which stronger events occurred within the sequence.

Recent unrest on the Reykjanes Peninsula made this limitation particularly visible during the development of the project. Large numbers of events may occur within a small region, and the significance of an individual point depends partly on its relationship to the surrounding sequence. A map therefore needs temporal and magnitude filters, alternative visual encodings, and access to a catalogue long enough for comparison. The application is not intended to replace operational monitoring or support eruption prediction. Its purpose is narrower: to make the available catalogue easier to explore by location, time, and magnitude. Source provenance supports that exploration by showing how displayed records were constructed.

Data quality is part of this problem. MPGV and the Quakes API do not provide identical records, and a single physical event may appear in both with small differences in time, coordinates, magnitude, or depth. Publishing both feeds without a catalogue-defining source would create duplicates and could give a misleading impression of event density. Using MPGV alone would preserve the defining catalogue but forgo the coordinates and depth available from accepted Quakes API matches. The backend therefore treats reconciliation as a supporting stage before visualisation rather than attempting to hide source differences in the user interface.

\subsection*{Need for a Modern Monitoring Tool}
The design problem was not simply to place earthquake markers on a web map. Existing public platforms already do that effectively for recent situational awareness. The original requirements were to retain an Iceland-focused catalogue from 1~June~2020 onwards, support geographic, temporal, and magnitude-based exploration through interactive controls, and connect event-level map inspection with aggregate analysis. During development, a further requirement emerged: corresponding MPGV and Quakes API records had to be reconciled without allowing the secondary source to redefine catalogue membership.

The ingestion pipeline uses APScheduler to initiate a three-minute cycle. Each successful cycle updates the MPGV source table, requests recent Quakes API events, rebuilds the MPGV-anchored catalogue from 1~June~2020 onwards, and then attempts to refresh volcano metadata from the IMO EPOS service. Candidate earthquake records are compared using temporal, spatial, and magnitude constraints. For a matched record, the policy retains the MPGV time and robust-mean moment magnitude but uses the Quakes API coordinates and depth. Records without a unique acceptable match remain in the catalogue with an MPGV-only status. Depth analysis uses matched Quakes API depths by default. MPGV-only depths can be included through the \emph{Include unverified MPGV depths} option and are labelled as unverified source values.

SQLite was selected because the catalogue and deployment are currently served by a single application instance, and its file-based operation keeps local setup and transfer straightforward. It is used with SQLAlchemy and write-ahead logging. This is an appropriate compromise for the present scale, but it is not presented as a general solution for a high-concurrency monitoring service. The application also limits public responses by date window and row count, applies per-client rate limits, and protects state-changing maintenance routes with an administrator token in production. These controls do not replace infrastructure-level security, but they prevent the research deployment from exposing unrestricted ingestion and reconciliation operations.

\subsection*{System Features}
The backend is a Flask application using SQLAlchemy for persistence. It exposes the merged earthquake catalogue, volcano records, catalogue limits for analysis, CSV export, health information, and on-demand ShakeMap lookup through a small REST interface. Normal ingestion is initiated by the scheduler; separate authenticated maintenance endpoints are available for controlled administrative use. The React 18 frontend is built with Vite and served from the same Flask deployment in production.

The main map uses MapLibre GL for the map view and deck.gl scatterplot layers for earthquake markers. Users can filter the displayed events by time and minimum magnitude, and can colour markers either by their position within the selected timeline or by magnitude. Four map modes are available: an OpenFreeMap vector map, Esri satellite imagery, an IMO terrain map, and a density-oriented heatmap over a dark OpenFreeMap style. The heatmap deliberately suppresses individual marker selection so that it represents spatial concentration rather than a second marker view. Optional overlays show IMO EPOS volcano metadata, EGDI/HIKE fault and fissure linework, and an Iceland-focused latitude/longitude grid. Selecting an earthquake opens an information card and, where an eligible product is available, provides access to the corresponding ShakeMap. Here, eligibility means that the product satisfies the application's lookup and matching criteria. A recent-selections panel allows previously inspected events to be reopened.

The map is complemented by an Insights page built with Recharts. It applies date, magnitude, depth-quality, data-category, and time-grouping filters to the same merged catalogue and presents summary statistics, five interactive charts, and tables of recent and strongest events. Filtered results can be exported as CSV or prepared for printing to PDF, and a \emph{View on Map} action returns an event to the map while preserving the current map state. Both pages use responsive layouts; mobile presentation changes the arrangement of controls, tables, and information panels rather than providing a separate application.

These features are intended to support exploratory use rather than automated scientific interpretation. In particular, the charts do not infer causes or forecast activity, and the ShakeMap link does not constitute an independent validation of an earthquake. The interface exposes available records and their provenance so that users can examine patterns while remaining aware of the limits of the underlying data.

\subsection*{Contributions and Future Directions}
The principal contribution of the project is the interactive map and earthquake exploration interface. It combines geographic navigation with temporal and magnitude filtering, alternative colour encodings, contextual overlays, event details, and ShakeMap access. These interactions make a multi-year Icelandic catalogue explorable without implying automated scientific interpretation.

A second contribution is the MPGV-anchored reconciliation and provenance pipeline. It records whether a row was uniquely matched or remains MPGV-only, retains match diagnostics, and carries that provenance into the API and analytical interface. A third contribution is the connection between the map and Insights views: the latter provides aggregate summaries, charts, tables, and filtered exports using the same catalogue and depth-quality policy, while the \emph{View on Map} interaction returns an event to its geographic context. A fourth contribution is the frontend's evolution from static Folium output and paid Google Maps access, through a Leaflet version, to a MapLibre GL and deck.gl architecture with no Google Maps credentials or Leaflet compatibility layer.

Several limitations remain. The present Pluto deployment is served publicly over HTTPS; nginx terminates TLS and redirects HTTP requests to HTTPS. These controls depend on server-level infrastructure outside the Flask application and repository. External tile and data-provider licensing also requires review before formal institutional deployment. SQLite remains suitable for the current single-instance research deployment but would need to be reconsidered if write concurrency or the number of application workers increased substantially.

Future work should first evaluate the reconciliation policy, the interface, and the operation of the deployed service. Useful extensions include a source-comparison view, clearer access to retained MPGV revisions, direct comparison of selected periods, and stronger monitoring and recovery procedures. These priorities are developed in Chapter~\ref{sec:future-development}. The work reported in this thesis remains the implemented ingestion, reconciliation, map, and Insights pipeline. Together, these components show how a map-centred application can support exploration by location, time, and magnitude while preserving provenance and consistent behaviour from acquisition to presentation.

\section{Background and Related Work}

This chapter reviews the evidence needed to position MPGV Monitor as a computer-science project. It introduces the Icelandic seismic-data context, interactive geospatial visualisation, multi-source catalogue integration, relevant earthquake information systems, and ShakeMap ground-motion products. The emphasis is on concepts and prior work that motivate the project; its architecture, reconciliation rules, and interface implementation are addressed in later chapters.

\subsection{Icelandic Seismic-Data Context}

\subsubsection{Brief Seismotectonic Context}

Iceland lies across the divergent boundary between the North American and Eurasian plates and above a mantle plume. The interaction of plate spreading and volcanism produces a complex arrangement of rift zones, transform zones, and volcanic systems rather than one continuous line of seismic activity. Earthquakes are therefore concentrated in identifiable regions, including the Reykjanes Peninsula, the South Iceland Seismic Zone, the Tj{\"o}rnes Fracture Zone, and the volcanic zones that cross the island \cite[pp.~35--37]{Einarsson2008}. This spatial structure is the principal geological fact required by the present thesis.

Icelandic catalogue data also record activity distributed through time. J\'onasson et al.\ combined historical and instrumental records from several sources, producing a long-term catalogue whose coverage and preferred parameters depend on the contributing material \cite[pp.~2197--2200]{Jonasson2021}. A recent-event list is useful for situational awareness, but it cannot by itself show whether activity in a region is isolated, recurrent, or part of a longer sequence. For an exploratory interface, spatial position and time must consequently be treated as connected dimensions, while magnitude provides an additional basis for filtering and comparing stronger events.

This thesis does not infer physical causes from patterns displayed in the application. Such interpretation requires seismological evidence beyond a web visualisation. The narrower implication is that the selected data should be explorable at national and regional scales and over short and multi-year intervals without presenting a visual pattern as a forecast or causal explanation.

\subsubsection{Monitoring and Earthquake Catalogues}

A physical earthquake and a catalogue record are not identical: a record is one source's estimated description of the event. Independent catalogues can assign different origin times, locations, and magnitude values to the same earthquake, and some events present in source data may be absent from a final catalogue \cite[p.~2202]{Jonasson2021}. Differences can arise from network and processing conditions, location methods, magnitude types, and the criteria used to select and merge records \cite[p.~2599]{Poggi2024}.

Harmonised catalogues consequently require explicit selection policies. In the Icelandic catalogue, the preferred location was chosen from available sources rather than by a universal first-choice rule, and the source was recorded in the catalogue \cite[p.~2203]{Jonasson2021}. Magnitudes were likewise selected or derived under documented rules with associated uncertainty estimates \cite[pp.~2204--2207]{Jonasson2021}. Although that study concerns a curated catalogue over a much longer period than MPGV Monitor, it establishes the relevance of source selection, uncertainty, and traceability to Icelandic catalogue integration.

In February 2026, IMO made SeisComP its primary earthquake monitoring and analysis system while retaining SIL as a secondary system during fine-tuning and historical-data transfer. The same institutional notice introduced an updated Skj\'alftal\'isa web interface and the Quakes API data gateway. It also stated that earthquake locations could change because of differences in processing methods and that the number of reviewed earthquakes might initially be lower during the transition \cite{imo_seiscomp_2026}.

The other principal project source is the IMO-hosted MPGV archive. Its monthly pages provide origin time, position, depth, automatic magnitude, robust-mean and median moment-magnitude estimates, station counts, fit information, and links to some ShakeMap products and input data. The accompanying explanation states that qualifying SIL events were compared with the alert system and that magnitude was recalculated from station peak-ground-velocity measurements when the correspondence rule was met \cite{imo_mpgv_archive}. The pages do not state that the archive is complete, so this thesis treats MPGV as a source name and does not infer completeness or superiority over the Quakes API.

MPGV Monitor selects records from 1~June~2020 onwards and applies the catalogue magnitude threshold defined in Section~\ref{subsec:data-sources-scope}. These are project-scope decisions, not statements about the full coverage of either source. Because the selected MPGV and Quakes API data overlap only partly and corresponding records can differ, simple concatenation could duplicate an earthquake. The project instead compares records, retains an MPGV-anchored result, and distinguishes accepted matches from MPGV-only records. The implemented thresholds, field choices, and diagnostics are documented in Section~\ref{subsec:reconcile}.

\subsection{Interactive Geospatial Visualisation}

\subsubsection{Web Mapping and Spatiotemporal Visual Analytics}

An interactive map allows users to change the visible extent, select records, and inspect geographic distribution. Zooming, panning, and selection are familiar operations in online mapping services \cite[p.~1596]{Andrienko2010}. For an earthquake catalogue these operations provide a starting point, while temporal controls, magnitude filters, and analytical views allow closer investigation of location, time, magnitude, and individual records.

Earthquake catalogues combine spatial, temporal, and magnitude information, which one representation cannot communicate equally well. Andrienko et al.\ describe coordinated multiple views as a generic approach for considering spatial, temporal, and thematic aspects together \cite[p.~1585]{Andrienko2010}. This is relevant to MPGV Monitor because its map, filters, event details, and aggregate views expose complementary aspects of the same catalogue.

Yuan et al.\ provide a seismic-domain example: their visual-analytics system integrated seismic and satellite observations, supported spatial and temporal selection, and enabled event comparison and drill-down \cite[p.~1413]{Yuan2010}. Its datasets, analytical objectives, three-dimensional viewer, and large-display environment differ from MPGV Monitor, but the study provides a relevant precedent for linked space-time exploration.

The appropriate detail depends on spatial and temporal scale. Andrienko et al.\ argue that interactive visual interfaces should support transitions between scales and comparisons among different scales and aggregations \cite[p.~1595]{Andrienko2010}. For MPGV Monitor, this suggests combining national and regional navigation with time and magnitude filtering and access to individual record details; it does not prescribe a particular implementation technology.

\subsubsection{Visual Encoding, Filtering, and Coordinated Views}

Earthquake records combine position with ordered attributes such as origin time, magnitude, and depth. Position can be mapped directly, while other attributes may be communicated through size, colour, legends, filters, linked views, or details. P{\H{o}}d{\"o}r and Kiszely compared raw, aggregated, two-dimensional, and three-dimensional earthquake-catalogue maps; the effectiveness of the representations varied by retrieval task \cite[pp.~160--161]{PodorKiszely2014}. The implication is to match the representation to the question while retaining access to exact values.

Large catalogues can be difficult to symbolise on one map, and aggregation can help users identify frequently affected areas, although it removes event-level detail. P{\H{o}}d{\"o}r and Kiszely also found that three-dimensional maps helped participants locate the largest event but were less effective for determining exact event counts and released energy \cite[pp.~156, 160--161]{PodorKiszely2014}. Their results support using a density summary as a complement to, rather than a replacement for, individual-event symbols.

In MPGV Monitor, the heatmap is a scale- and parameter-dependent summary of the filtered records. Its appearance depends on the included events and rendering choices such as magnitude weighting, zoom, and colour scale; it does not establish completeness, causation, or exact seismic-zone boundaries. The event-level map and details remain necessary for inspecting individual values and provenance.

Colour can communicate ordered values, but a perceptually uniform scale should represent equal data variations with equal perceptual weight \cite[p.~4]{Crameri2020}. Rainbow-like and other non-uniform maps can add artificial boundaries, hide variations, prevent intuitive ordering, and become unreadable under common colour-vision deficiencies \cite[p.~2]{Crameri2020}. Crameri et al.\ also recommend a colour bar, attention to background contrast, and selection of a colour-map class suited to the structure of the data \cite[pp.~6--7]{Crameri2020}.

These considerations apply to the project's magnitude and chronological colour modes because both encode ordered, rather than categorical, values. MPGV Monitor provides corresponding scales, but the literature motivates a design and evaluation requirement rather than proving that the implemented palettes are perceptually uniform, colour-vision safe, or equally effective on every map background.

Filtering determines which records contribute to symbols and summaries, so visible filter boundaries and exact record values are important. In Yuan et al.'s system, time-range and location selections propagated to linked displays \cite[p.~1415]{Yuan2010}. Applied to MPGV Monitor, the relevant principle is that time and magnitude filters should select a consistent catalogue subset across map and Insights views; whether the implementation achieves that consistently is evaluated later.

\subsubsection{Accessibility, Uncertainty, and Provenance}

Accessible visualisation involves more than distinguishable colours. WCAG 2.2 defines testable requirements concerning perceivable content, keyboard operation, focus, text alternatives, contrast, target size, and other aspects of web content \cite{WCAG22}. Conformance applies to complete pages and requires every applicable success criterion at the claimed level to be met. User testing can reveal practical barriers, but it does not by itself establish WCAG conformance.

Maps and charts can make information dependent on spatial or colour perception. WCAG requires, among other criteria, that colour is not the only visual means of conveying information and that interface components expose appropriate names, roles, and values \cite{WCAG22}. Labelled controls, filter summaries, tables, exact event details, and downloads can reduce dependence on visual marks, but their presence alone does not prove a complete accessible alternative or full keyboard and screen-reader support.

Uncertainty is inherent in earthquake catalogues. In the Icelandic harmonisation study, locations were selected among source solutions and their variability was used as a proxy for precision \cite[p.~2203]{Jonasson2021}; some moment magnitudes were derived from other magnitude types with reported uncertainty estimates \cite[pp.~2204--2207]{Jonasson2021}. Catalogue parameters are consequently processed estimates rather than direct ground truth, and an interface should avoid implying greater certainty than its sources provide.

Uncertainty and provenance answer different questions. Uncertainty concerns confidence or variability in a value; provenance describes how an end product was produced. Herschel et al.\ define provenance as information about a product's production process and identify motivations including accountability, reproducibility, and process debugging \cite[p.~881]{Herschel2017}. For a reconciled catalogue, this makes source identifiers, match status, diagnostics, and source-dependent field choices relevant even when no numerical uncertainty estimate is available.

This distinction supports a cautious presentation policy. MPGV Monitor records whether a merged row is matched or MPGV-only and identifies the source used for depth in its analytical view, but these labels do not certify scientific correctness. An MPGV-only row means that the current policy did not accept a Quakes API match; it does not mean that the earthquake is false. The data model and interface treatment are examined in later chapters.

\subsection{Multi-Source Earthquake-Catalogue Integration}

\subsubsection{Heterogeneous Records and Event Identity}

One physical earthquake can be represented by several source records with different identifiers and parameters, while separate earthquakes can occur close together. Exact equality is therefore unsuitable for finding corresponding records: independent catalogues maintain their own origin times and locations and can report several magnitude values for one event \cite[p.~2202]{Jonasson2021}. Conversely, unqualified concatenation can double-count overlapping records in event totals, density summaries, and lists.

The output must preserve the distinction between source records and the constructed merged record. Catalogue harmonisation requires explicit criteria for duplicate identification, merging, parameter conversion, and preferred-source selection \cite[p.~2599]{Poggi2024}. If the relationship to the inputs is lost, users cannot tell whether a value came directly from one source or from a selection or transformation, weakening interpretation and maintenance.

\subsubsection{Candidate Matching, Deduplication, and Source Traceability}

Earthquake-catalogue studies commonly compare temporal and spatial proximity when identifying duplicate records. Poggi et al.\ used tuned time and distance windows, then added a magnitude-difference condition; they also cautioned that no single window captured every duplicate without admitting some independent events \cite[p.~2602]{Poggi2024}. Time, distance, and magnitude therefore provide complementary evidence, but their thresholds remain catalogue- and context-dependent rather than universally valid.

Deduplication need not discard the evidence behind a decision. Provenance can retain source identifiers, comparison diagnostics, status, and the source selected for output values, enabling audit and later reprocessing \cite[p.~881]{Herschel2017}. In this thesis, the literature motivates comparison across several event attributes, conservative handling of ambiguous cases, and traceability in the merged catalogue. MPGV Monitor's MPGV-anchored rule and its one-to-one constraint are project policies documented and tested later, not methods claimed to have been prescribed by the reviewed papers.

\subsection{Existing Earthquake Information and Visualisation Systems}

\subsubsection{Operational Web Interfaces}

The following comparison is limited to official documentation for selected interfaces checked on 22~July~2026. It considers service scope, time range, source model, filtering, and product linkage where these bear on the thesis. The observations are not a user study and may change as the services evolve.

IMO provides more than one public route into Icelandic earthquake information. Its established whole-country page presents preliminary events from the preceding 48 hours on a map with a table and supporting plots \cite{imo_quakes_48h}. In February 2026, IMO also launched an updated Skj\'alftal\'isa interface, described officially as providing map layers and analyses of depth, frequency, and temporal evolution, together with the new Quakes API data gateway \cite{imo_seiscomp_2026}. These services are authoritative sources for current Icelandic monitoring. Their official descriptions do not, however, state that they expose pairwise reconciliation between the MPGV archive and Quakes API records.

USGS Latest Earthquakes provides a global recent-event map linked to event pages and catalogue search \cite{usgs_latest_map}. Its underlying ANSS Comprehensive Earthquake Catalog is not a single-network feed: ComCat collects source parameters and products from contributing seismic networks, retains contributor and review information, and associates products such as moment tensors, felt reports, and ShakeMap with events \cite{usgs_comcat}. It supports broad and historical queries beyond the recent-map defaults. USGS therefore demonstrates both multi-network collection and event-level product integration, although it is not specialised for the selected Icelandic source relationship addressed in this thesis.

The EarthScope/IRIS Interactive Earthquake Browser is oriented towards longer-range exploration. Sumy et al. document queries by time, location, depth, and magnitude and two-dimensional or pseudo-three-dimensional displays \cite[pp.~2922--2924]{Sumy2020}. They also describe event-detail tables and data export, together with a freely rotatable pseudo-three-dimensional view \cite[pp.~2924--2925]{Sumy2020}. Its current official help additionally documents statistics and animation. The default dataset is USGS-based, while a mixed-source option includes additional records, principally from the International Seismological Centre and USGS \cite{iris_ieb_help}. The browser is therefore a close precedent for multi-year filtering and exploratory representations, although it does not document reconciliation of MPGV with the current IMO Quakes API.

The comparison shows that operational interfaces serve different purposes: current national monitoring, global recent-event information, multi-network product integration, or long-range catalogue exploration. Existing systems therefore cannot be characterised collectively as short-term, single-source marker maps. The narrower question is whether the reviewed interfaces make the relationship between the selected MPGV and Quakes API records an explicit and traceable object of exploration.

\subsubsection{Research Systems and Empirical Studies}

Together, the studies suggest that an earthquake-catalogue interface should coordinate spatial, temporal, and event-level exploration while selecting representations according to the retrieval task \cite[pp.~1413--1415]{Yuan2010}\cite[pp.~156, 160--161]{PodorKiszely2014}. For MPGV Monitor, this provides a design rationale for linked filtering and complementary event and density views, not evidence that the implemented interface is effective.

Sumy et al. also provide an empirical evaluation of the IEB. Their 2018 pop-up survey yielded 495 usable responses after exclusions \cite[pp.~2925--2926]{Sumy2020}. In the feature analysis, data mapping and visualisation, detailed information, and data customisation and filtering were the three most frequent codes \cite[pp.~2929--2931]{Sumy2020}. Because the authors identify English-language, self-selection, and membership biases \cite[p.~2932]{Sumy2020}, the results motivate MPGV Monitor's map, exact details, and filters but do not establish the usability of this project.

The research literature therefore supports linked spatial and temporal exploration, filtering and encoding by magnitude, overview and detail, event comparison, and carefully chosen aggregation. These findings inform the interface requirements, while usability and analytical effectiveness must be evaluated with the intended data, tasks, and users.

\subsubsection{Comparative Synthesis}

Among the systems reviewed, long time ranges, multi-source collection, filtering, export, analytical views, and ground-motion products already exist in different combinations. ComCat is explicitly multi-network, IEB offers historical mixed-source exploration, and the current IMO environment includes an analytical Skj\'alftal\'isa interface. MPGV Monitor is therefore not positioned by claiming that these capabilities are individually novel.

The narrower gap concerns the source relationship examined here. The reviewed official interfaces do not document an exploratory view of accepted matches and unmatched MPGV records between the IMO-hosted MPGV archive and current Quakes API, nor the same MPGV-anchored catalogue used across a map and an Insights page. This is a finding within the reviewed sample and access date, not proof that no comparable application exists.

Historical exploration is likewise one part of the project scope rather than a unique capability. IEB and USGS support long or custom time ranges, but not the selected Icelandic reconciliation model; IMO's documented interfaces serve a different operational context. This motivates a multi-year Iceland-focused view whose filters and summaries operate on the reconciled project catalogue.

Ground-motion access adds another part to the project scope. USGS associates ShakeMap products with ComCat events, and IMO publishes an EPOS ShakeMap service. MPGV Monitor therefore exposes available Icelandic products from the same event-inspection context as its reconciled records, linking an established product type and service to the project's catalogue workflow.

\subsection{ShakeMap and Ground-Motion Products}

An earthquake catalogue reports source parameters such as origin time, location, depth, and magnitude, whereas ShakeMap portrays the spatial distribution and severity of shaking. Worden et al. describe an uncertainty-weighted combination of direct observations, converted observations, and estimates from prediction equations or numerical models \cite[p.~3083]{Worden2010}. The resulting products include measures such as peak ground acceleration, peak ground velocity, spectral acceleration, and intensity \cite{ShakeMapManual}. These location-dependent products answer a different question from source magnitude and should not be treated as interchangeable with it.

Within the revised interpolation method, native observations, converted observations, and predictions are weighted according to their constraints, with observation influence, site amplification, and variance incorporated across the output grid \cite[pp.~3084--3087]{Worden2010}. The manual also documents uncertainty products and distinctions between observed and estimated values \cite{ShakeMapManual}. A continuous map should consequently be interpreted with its inputs and metadata rather than as a dense grid of direct measurements.

USGS ShakeMap is the general methodological and technical reference, but it is not the service queried by the current application. IMO's EPOS API documents a distinct \enquote{Shakemaps Iceland} endpoint at \texttt{api.vedur.is} \cite{imo_epos_api}. The older MPGV institutional pages also link some products created with USGS ShakeMap software adapted to Icelandic attenuation, intensity-conversion, and site-condition information \cite{imo_mpgv_archive}. Product availability is event-dependent, and the service record does not imply that every catalogue event has a corresponding map.

For MPGV Monitor, ShakeMap access links a reconciled catalogue record to an available Icelandic ground-motion product. The active application queries the current Icelandic endpoint, but its association rule belongs in the backend chapter. The literature-review requirement is that catalogue parameters and ground-motion estimates remain conceptually distinct and that product availability and source remain clear.

\subsection{Research Gap and Positioning}

The reviewed literature establishes three connected needs. First, Icelandic earthquake activity should be explorable by location, time, and magnitude. Second, partially overlapping catalogue records require explicit matching decisions, conservative treatment of ambiguity, and retained provenance. Third, maps, filters, aggregate views, and ground-motion products communicate different aspects of the data and should remain coordinated without being conflated.

Within the scope of the reviewed systems, MPGV Monitor combines several elements for a selected Icelandic dataset: multi-year exploration by location, time, and magnitude from June 2020 onwards; comparison and reconciliation of MPGV and IMO Quakes API source records; a traceable MPGV-anchored merged catalogue; linked map and Insights exploration; and access to available Icelandic ShakeMap products. Together, these elements define the implemented contribution assessed in the following chapters.

Several limits follow from the review. The selected date range and threshold exclude events outside the project scope. Matching and source-priority policies require empirical evaluation, and provenance labels do not remove parameter uncertainty. Accessibility conformance, colour performance, and the benefit of linked views likewise require direct evaluation. These questions are addressed, where evidence is available, in the design, implementation, testing, and limitations chapters.

The next chapter turns from this evidence base to the project itself. It describes the development context, data sources, and overall system structure before the subsequent chapters examine acquisition, reconciliation, backend services, and the user interface in detail.

\subsection{Data Sources and Selected Project Scope}
\label{subsec:data-sources-scope}

\subsubsection{Earthquake Catalogue Sources}

The IMO-hosted MPGV archive defines the events in the final published catalogue. Its monthly pages provide origin time, position, depth, and documented magnitude fields, including the robust-mean moment-magnitude value retained by MPGV Monitor \cite{imo_mpgv_archive}. The IMO Quakes API supplies a secondary, machine-readable stream of event identifiers and earthquake attributes for matching and enrichment \cite{imo_quakes_api}. The two streams partially overlap, but Quakes API records do not independently enter the published catalogue.

Source records are retained separately before reconciliation because their reported time, position, depth, and magnitude may differ. Candidate comparison determines whether two records plausibly represent the same physical event; simple concatenation could instead publish overlapping source records as independent catalogue events. The resulting catalogue is MPGV-anchored and preserves match status and field provenance. In this thesis, \emph{canonical catalogue} denotes this persisted reconciliation output; \emph{merged catalogue} refers to the same output when describing its construction or database table. Detailed acquisition and reconciliation methods are deferred to Chapters~4 and~5.

\subsubsection{Contextual Services and Layers}

External services also provide context that is intentionally kept outside the earthquake catalogue. IMO/EPOS volcano metadata are refreshed for geographic display. ShakeMap information is requested on demand for an eligible selected event \cite{imo_epos_api}. EGDI/HIKE fault and fissure linework is obtained from the official Icelandic tectonic-boundaries dataset and displayed as a client-side map layer \cite{egdi_hike_iceland_tectonics}.

These sources have different semantics from the reconciled earthquake records. Volcano features and structural linework are not added to catalogue counts, and a ShakeMap is an event-related product whose availability depends on the external service and the selected event. Displaying earthquakes together with volcanoes or tectonic linework supports geographic inspection; it does not establish a causal relationship or perform volcano-proximity analysis.

\subsubsection{Selected Catalogue Scope and Interpretation}

For the published MPGV-anchored catalogue, \(M_w\) denotes the MPGV robust-mean moment-magnitude field. The catalogue applies \(M_w \geq 3.0\). Generic ``magnitude'' or \(M\) is used when comparing sources because the available evidence does not establish that every raw Quakes API magnitude has the same type.

The catalogue begins on 1~June~2020 as a deliberate project boundary supporting a consistent multi-year application scope. It should not be interpreted as the start of the source archives or as evidence of complete institutional coverage from that date. Events before the boundary and MPGV catalogue events with \(M_w < 3.0\) are outside the presented dataset; apparent frequencies and spatial or temporal patterns are consequently conditional on both selections.

Published merged rows are either matched records or MPGV-only records. A match retains the MPGV time and magnitude while using the accepted Quakes API coordinates and depth; an MPGV-only row retains the MPGV values and its unmatched status. Quakes API rows without an accepted match remain available as raw source records but are not independently published as catalogue events. Contextual layers are excluded from catalogue totals, and ShakeMap coverage is event-dependent. These rules define an application dataset rather than a catalogue-completeness analysis, and the interface must not be used as an earthquake forecast or operational warning service.

\subsection{Evolution of the Acquisition Approach}

The earliest documented acquisition experiment used a single MPGV monthly page. Later project stages explored flat-file and CSV-oriented storage while extending acquisition across more than one month. The original scripts and output files for these stages are not retained in the repository history, so their exact algorithms and results cannot be verified from the current artefact. The implementation preserved in the repository uses persistent database-backed source storage. \subsection{Current Multi-Source Earthquake Acquisition}
\label{subsec:current-earthquake-acquisition}

\subsubsection{MPGV Archive Acquisition}
\label{subsubsec:mpgv-acquisition}

The MPGV HTML acquisition path begins at \url{http://hraun.vedur.is/ja/Mpgv/}. Beneath this base, year indexes follow the pattern \nolinkurl{{BASE_URL}{year}/}, and monthly pages follow \nolinkurl{{BASE_URL}{year}/{year}-{MM}.html} \cite{imo_mpgv_archive_index}. The scheduled Flask path discovers links matching four-digit year directories and, within each directory, monthly pages named in the \texttt{YYYY-MM.html} form. It currently traverses every discovered year and month. The selected catalogue and reconciliation boundary is 1~June~2020, as established in Chapter~3. This date is not a cutoff applied by the MPGV scraper, the beginning of the source archive, or evidence of complete institutional coverage. Earlier MPGV records may therefore be retained in raw source storage; reconciliation and public catalogue delivery apply the 1~June~2020 boundary.

For each monthly page, BeautifulSoup locates the HTML table with the class \texttt{dataframe}. The parser reads rows from the table body and ignores rows containing fewer than eight cells. From accepted rows it selects the date-time, latitude, longitude, depth, and the value from the MPGV robust-mean moment-magnitude field. Other source fields are not retained.

Parsing and normalisation preserve the exact MPGV timestamp, including any fractional seconds, and use it as the stable source identity. Consequently, two events reported within the same whole second can remain distinct. Latitude, longitude, depth, and robust-mean moment magnitude are converted to numeric values, and the threshold $M_w \geq 3.0$ is applied before a row enters the candidate catalogue. Rows with unavailable magnitudes remain ineligible; malformed eligible rows are counted so that abnormal page-level parse loss can cause the candidate to be rejected rather than being silently accepted.

The scheduled path constructs the complete MPGV candidate catalogue in memory before changing the persisted current state. It checks the discovered year and month structure, requires usable monthly tables and table bodies, verifies the expected recent period, and requires valid and unique source identities and a configured minimum catalogue size. Page-level parse-loss limits and suspicious catalogue reductions provide further safeguards. These checks reduce the risk of accepting an incomplete acquisition, but they remain heuristic safeguards rather than proof that the external archive is complete.

After validation, the candidate is synchronised transactionally with the \texttt{earthquake} source table, which also retains historical revisions. An unchanged exact revision can be reactivated, while changed source values for an existing identity create a retained historical revision; exactly one accepted revision is marked current for each source identity, and reconciliation reads only current MPGV rows. If fetching, parsing, or validation fails, synchronisation does not begin. If persistence fails during synchronisation, the transaction is rolled back. In either case, the previous current MPGV state is preserved. MPGV HTTP requests use timeouts but do not implement a source-specific retry loop.

\subsubsection{IMO Quakes API Acquisition}
\label{subsubsec:quakes-api-acquisition}

The second source stream is retrieved with \texttt{GET} from \url{https://api.vedur.is/quakes/events}. The IMO Quakes API returns a GeoJSON \texttt{FeatureCollection} containing \texttt{Point} features \cite{imo_quakes_api}. The application normalises the event identifier, UTC timestamp, longitude, latitude, optional depth, and optional magnitude from each usable feature; fields outside this acquisition purpose are not retained.

The scheduled workflow requests the most recent seven rolling days using the generic API magnitude threshold $M \geq 3.0$. It sends the parameters \texttt{start\_time}, \texttt{end\_time}, \texttt{size\_min}, and \texttt{format=json}. Requests are clamped to 1~June~2020 to maintain the selected historical scope. Because the active endpoint does not provide pagination, a separate historical backfill path divides longer intervals into date windows of at most 365~days. These windows are not API pages.

API timestamps are converted to UTC and stored to second precision. GeoJSON coordinates are converted to numeric longitude and latitude, while depth and magnitude can remain absent. Features with unusable structure, coordinates, timestamps, or identifiers are skipped, and a row without a usable event identifier is not persisted.

Normalised IMO Quakes API source records use the event identifier as a stable source key. New identifiers are inserted; for an existing identifier, stored time, coordinate, depth, or magnitude values are updated only when at least one value has changed. The accepted records are persisted in one batch transaction. The HTTP client uses a timeout, validates HTTP status, and makes up to three attempts with short waits after failures. This improves resilience to transient failures, although it cannot guarantee source availability.

\subsection{Scheduled Acquisition and Persistence}
\label{subsec:scheduled-acquisition}

The recurring workflow runs every three minutes and performs the following sequence:

\begin{enumerate}
    \item discover and parse all MPGV pages, build and validate the complete $M_w \geq 3.0$ candidate catalogue, and transactionally synchronise current source identities while retaining historical revisions;
    \item retrieve the most recent seven days from the IMO Quakes API and insert or update raw source records by event identifier, or use already stored Quakes API rows if the refresh fails;
    \item rebuild the selected range of the persisted canonical catalogue from eligible current MPGV rows and available Quakes API enrichment, and verify the current-to-canonical invariant;
    \item refresh volcano metadata; and
    \item invalidate the earthquake-response cache after successful canonical replacement and invariant verification.
\end{enumerate}

A rejected MPGV candidate stops the cycle before reconciliation and preserves both the previous current MPGV state and the previous canonical catalogue. Reconciliation is a separate transaction: if it fails, the canonical replacement is rolled back, while the previous canonical rows and earthquake-response cache are preserved. Successful acquisition therefore does not guarantee successful reconciliation during the same scheduled cycle, and cache invalidation occurs only after canonical replacement and invariant verification have succeeded. A volcano-refresh failure is logged but does not undo a successful canonical replacement.


This chapter focuses on the first two stages, which acquire the earthquake source records. Volcano metadata provide geographic context and remain separate from the two earthquake source streams. Active ShakeMap lookup is performed on demand for a selected record and is not part of the recurring earthquake acquisition sequence.

Source-specific identities and transaction boundaries make repeated successful runs stable, but they do not make the complete multi-stage workflow one atomic transaction. MPGV synchronisation, IMO Quakes API upsert, and canonical replacement commit separately. Scheduler ownership, ingestion locking, reconciliation replacement, invariant checking, and cache behaviour are detailed in Chapter~5.

\subsection{Preparation for Reconciliation}
\label{subsec:preparation-for-reconciliation}

After acquisition, both raw source tables provide comparable attributes: timestamp, latitude and longitude, depth, and magnitude. Sharing these fields makes comparison possible, but it does not show that an MPGV source record and an IMO Quakes API source record describe the same physical earthquake. Until the reconciliation policy has evaluated them, the two records form a \emph{candidate pair}.

Same-source revision handling and cross-source reconciliation serve different purposes. MPGV persistence uses the exact source timestamp as its identity, retains changed historical revisions, and marks one accepted revision current; IMO Quakes API persistence uses the service's event identifier and can update an existing source record. Cross-source reconciliation then compares current MPGV rows with stored IMO Quakes API rows using temporal, spatial, and magnitude criteria. The exact thresholds, candidate scoring, ambiguity handling, one-to-one allocation, selected output fields, and diagnostic fields are specified in Chapter~5.

The published output is MPGV anchored. Each qualifying MPGV source record produces either a matched merged catalogue record or an MPGV-only merged catalogue record. An unmatched IMO Quakes API source record remains in raw storage and is not independently published as a Quakes-only merged record. This boundary preserves the distinction between acquisition-time source-key handling and the later decision to accept or reject a candidate pair.

Chapter~4 describes the acquisition, parsing, normalisation, validation, and source-specific persistence procedures in detail. The scheduled workflow requests the latest seven days of Quakes records at the generic threshold $M \geq 3.0$. MPGV acquisition continues to build the complete candidate from the discovered archive hierarchy before changing current flags.

The same scheduled cycle calls \texttt{volcano\_scraper.py} after successful canonical replacement and invariant verification. \subsection{Automated Scheduling and Safeguards}

Background processing is coordinated by an APScheduler \texttt{BackgroundScheduler}. Unless disabled through configuration, Flask attempts to start the service on the first request; direct execution also starts it before the development server. The interval job runs every three minutes with \texttt{coalesce=True}, \texttt{misfire\_grace\_time=300}, and \texttt{max\_instances=1}. Coalescing prevents accumulated missed intervals from being replayed as a burst, the grace period bounds delayed execution, and \texttt{max\_instances=1} prevents overlap within the elected scheduler instance.

Protection against overlap across application processes requires additional controls. A process-lifetime file lock elects one scheduler owner. Every scheduled or manually triggered ingestion operation must also acquire a non-blocking in-process thread lock and an exclusive ingestion lock file. The file records the owner process identifier and can be recovered when that process is no longer alive. Consequently, \texttt{max\_instances=1} is only one layer of the exclusion policy rather than a cross-process guarantee by itself.

\newpage

Within the lock, the recurring job executes the following sequence:

\begin{enumerate}
    \item build and validate the complete MPGV candidate, then synchronise current MPGV identities while retaining historical revisions;
    \item request and store the most recent seven days of Quakes API data, or continue with already stored Quakes rows when that retrieval fails;
    \item replace the selected canonical range through reconciliation and verify the current-to-canonical invariant;
    \item attempt the independent volcano refresh; and
    \item invalidate the default earthquake-response cache after canonical replacement and invariant verification have succeeded.
\end{enumerate}

The safeguards preserve different prior states at different failure boundaries. Rejection of the MPGV candidate stops the cycle before reconciliation and preserves the previous current MPGV and canonical catalogues. Quakes retrieval failure does not stop reconstruction because stored Quakes rows remain available. Reconciliation builds replacement rows within a database transaction; an exception rolls that replacement back and leaves both the previous canonical rows and the response cache intact. A later volcano failure does not reverse the canonical transaction. The complete cycle is therefore deliberately composed of several controlled transactions rather than presented as one atomic operation.

After reconciliation, the backend compares the eligible current MPGV identities with the canonical source keys. It also checks the total canonical count against the sum of \texttt{matched} and \texttt{v\_only} rows, rejects missing or duplicate MPGV identities, and rejects repeated Quakes assignments. Cache invalidation occurs only after these checks pass, so the normal catalogue endpoint does not expose a failed replacement through a newly invalidated cache.

\subsection{Reconciliation and Merging}
\label{subsec:reconcile}

Reconciliation constructs an MPGV-anchored catalogue from current MPGV rows and the locally stored Quakes API records. MPGV rows are the primary inputs: every qualifying row in the selected range produces one canonical row, whereas an unmatched Quakes event does not independently enter the catalogue. The algorithm uses project constants for temporal proximity, great-circle distance, and magnitude difference:

\[
|\Delta t| \leq 2 \text{ seconds}, \qquad
\Delta d < 10 \text{ km}, \qquad
|\Delta M| < 3.0.
\]

The stored Quakes rows are indexed by whole-second timestamp. For each current MPGV row, including those whose source timestamp contains fractional seconds, the algorithm inspects the five whole-second buckets from two seconds before to two seconds after the MPGV timestamp. A pair becomes a candidate only when it satisfies all three inequalities. When the stored Quakes magnitude is absent, the implementation substitutes the MPGV magnitude for this comparison, so missing magnitude alone does not reject a temporally and spatially eligible pair. The thresholds define current application behaviour; their suitability for physical event identification requires separate empirical evaluation.

Allocation then proceeds in two stages. First, for every Quakes \texttt{event\_id}, the algorithm selects the MPGV candidate with the lexicographically smallest tuple

\[
(|\Delta t|,\; \Delta d,\; |\Delta M|,\; \text{MPGV database identifier}).
\]

This comparison resolves competition when more than one MPGV row is eligible for the same Quakes event. Second, the winning MPGV row is accepted as \texttt{matched} only if that MPGV row has exactly one candidate under the implemented ambiguity rule. An MPGV row with no candidate, more than one candidate, or a unique candidate won by another MPGV row remains \texttt{v\_only}. The final integrity checks ensure that no Quakes event identifier is assigned to more than one canonical row.

For an accepted match, the canonical record retains the exact MPGV source timestamp and MPGV robust-mean moment magnitude and uses the Quakes coordinates and depth. The diagnostic time, distance, and magnitude differences and both source identifiers are stored with the row. For \texttt{v\_only}, time, coordinates, depth, and magnitude remain the MPGV values. Reconciliation replaces only the requested date range. Replacement rows are assembled before the existing canonical rows in that range are deleted, and deletion plus insertion are committed together. A database error triggers rollback. This makes rerunning the procedure stable at the storage level and permits a later Quakes update to replace a previous \texttt{v\_only} result with a match. It does not make a successful match proof that the two source records represent the same physical earthquake, nor does it establish scientific accuracy for the selected output fields.

\subsection{ShakeMap Access Paths}
\label{subsec:shakemap}

The active frontend obtains event-level ShakeMap access through \texttt{/shakemap\_lookup}. It sends the selected event timestamp and coordinates to Flask, which retrieves the current IMO/EPOS ShakeMap list from \url{https://api.vedur.is/epos/seismic/shakemaps}. For each parsable item, the backend computes the absolute time difference in minutes and great-circle distance in kilometres and minimises the score $3|\Delta t_{\mathrm{min}}| + \Delta d_{\mathrm{km}}$. The best item is rejected when its time difference exceeds 180~minutes or its distance exceeds 200~km. This active rule does not compare magnitudes and is intentionally documented separately from earthquake-catalogue reconciliation.

The selected product URL is returned only after outbound-link validation. The URL must use HTTPS, contain no embedded credentials, use no non-standard port, remain within a fixed allowlist of IMO/EPOS hosts, and fit the configured length bound. Redirects are disabled for the upstream request, the response must advertise JSON content, and ShakeMap responses are marked \texttt{no-store}. These controls limit which externally supplied links can be opened by the frontend; they do not validate the scientific contents of the product.

The repository also contains \texttt{shakemap\_validator.py}, an offline batch utility that can query a separate EPOS endpoint, apply its own time, distance, and magnitude limits, and write status and diagnostic values to \texttt{ShakeMapLink}. The associated \texttt{/shakemap/<dt>} route can read a valid cached entry. Neither the scheduler nor the active frontend invokes this batch path, so it is retained as an audit or maintenance facility rather than represented as the production lookup mechanism. No fixed audit counts are reported here because the result depends on the database snapshot, external service, and execution date.

Public request behaviour is bounded at several layers. The default rate limit is configurable and is supplemented by route-specific limits for earthquake and volcano data, ShakeMap lookup, CSV export, and maintenance operations. The \texttt{days} parameter accepts a positive bounded integer or the complete catalogue, and both catalogue and CSV queries reject result sets above their configured row limits. ShakeMap timestamps, coordinates, response type, and outbound URL are validated before a link is returned.

State-changing maintenance routes require an \texttt{X-Admin-Token} in production; if no token is configured, those routes are disabled. Local-address access without a token is available only when the application is explicitly running in development mode with the corresponding option enabled. The authentication check uses constant-time token comparison, and maintenance work must acquire the same ingestion lock as the scheduler.

The production frontend and API are served from the same origin. Cross-origin access is reflected only for the configured localhost development origins. Responses receive content-type, framing, referrer, content-security, permissions, base-URI, and form-action headers. Optional Flask-Compress integration supplies gzip-compatible compression when the package is installed. Proxy-derived client and scheme information is trusted only when the configured proxy count is exactly one, matching the documented nginx-to-Gunicorn topology.

SQLite uses write-ahead logging and normal synchronous mode for the scheduler/API access pattern. The default \texttt{/earthquakes} response is cached for 60~seconds and invalidated immediately after a successful scheduled canonical replacement and invariant check. This cache is process-local; deployments with more workers would require corresponding review of scheduler ownership, cache consistency, SQLite write concurrency, and shared rate-limit storage.

\subsection{Verification Boundary and Limitations}

Repository tests exercise the reconciliation thresholds, exact boundary behaviour, ambiguous candidates, competition for one Quakes identifier, source-dependent depth selection, idempotent reconstruction, late-arriving matches, changed Quakes enrichment, fractional MPGV timestamps, and the current-to-canonical invariant. Additional tests cover source parsing, Quakes normalisation, request limits, rate limiting, maintenance authentication, security headers, and API validation. These tests provide implementation evidence for the behaviours described above but do not measure event-matching accuracy against an independently labelled catalogue.

No database totals are used as architectural evidence in this chapter. Counts change as MPGV revisions accumulate, Quakes rows are updated, and the canonical catalogue is rebuilt. In particular, the proportion of \texttt{matched} rows cannot by itself validate the thresholds: a high or low fraction does not reveal false matches or missed physical correspondences without an external reference and an explicit evaluation design.

The backend remains a research-system implementation. Its application controls reduce accidental or unauthorised use of exposed operations, but they do not establish high availability, comprehensive security, catalogue completeness, scientific correctness, or suitability for high-concurrency deployment. Those boundaries remain separate from the fact that the implemented transactions, locks, invariants, and validation checks behave as specified by the code.

\subsection{Summary}

The current backend separates source persistence, canonical catalogue construction, contextual data, and service delivery. MPGV revisions retain a current-source identity, Quakes rows are updated by service identifier, and reconciliation applies a conservative one-to-one allocation before replacing the selected canonical range transactionally. Scheduler ownership, ingestion locks, candidate validation, invariant checks, and controlled cache invalidation protect the recurring workflow at distinct failure boundaries. Volcano metadata are refreshed as a non-fatal contextual stage, while active ShakeMap access is performed on demand rather than through the offline batch cache.

Flask exposes the catalogue and supporting services to the MapLibre GL/deck.gl map and Recharts Insights interface while also serving the built React application. The frontend rendering libraries do not determine the database or API contract: replacing a browser-side renderer need not alter source acquisition or reconciliation so long as the expected data fields and interactions remain stable. Maintaining that separation is important if later work adds sources, queries, deployment workers, or analytical functions.

\section{Frontend Architecture and Implementation}
\label{sec:frontend}

The frontend is a React~18 single-page application built with Vite. Its two user-facing routes are the interactive map and the connected Insights page. The map presents the canonical frontend dataset produced by the backend, applies time and magnitude filters in the browser, and combines earthquake data with optional contextual overlays. The current spatial stack is MapLibre~GL, integrated through \texttt{react-map-gl/maplibre}, with deck.gl used for interactive earthquake markers. Recharts is used by the Insights route. The earlier progression from Folium to Google Maps and then Leaflet is summarised in Chapter~3; Leaflet is a historical stage and is not part of the current runtime or dependency tree.

Chapter~6 describes current frontend responsibilities and component interaction. Reconciliation, scheduler ownership, maintenance routes, and ShakeMap matching rules remain backend concerns described in Chapters~4 and~5. The frontend consumes their published responses without treating the reconciled catalogue as scientific validation of source records.

\subsection{API Consumption, Refresh, Loading, and Error States}
\label{subsec:frontend_api_layer}

Backend requests are represented by functions in \texttt{api.js}. During local development the API origin uses the current host on port~5001; in production it uses Vite's configured base path. Axios retrieves \texttt{/earthquakes}, \texttt{/volcanoes}, and \texttt{/insights/limits}. The on-demand \texttt{/shakemap\_lookup} request uses the browser \texttt{fetch} API with cache bypass. External map styles, tiles, and fault geometry are loaded by the map component rather than routed through the Flask API.

On initial mount, \texttt{App.jsx} starts earthquake and volcano requests together and associates them with an \texttt{AbortController}. A three-minute interval repeats the catalogue-loading operation, and every active controller is aborted when the effect is replaced or the component unmounts. A successful earthquake response replaces the in-memory catalogue. An empty earthquake array or a failed request sets the catalogue error state. Volcano retrieval is deliberately non-fatal to the map: \texttt{fetchVolcanoData()} returns an empty array for an ordinary request failure, and the earthquake interface can continue without that contextual overlay.

The loading presentation has separate boundaries. Map style changes show a map-loading overlay until the active MapLibre instance reports that it has loaded. Insights is lazy-loaded through \texttt{React.lazy} and \texttt{Suspense}; before its catalogue and limits are ready it displays a status-labelled skeleton. Catalogue and limits failures on Insights are presented with alert roles and retry actions, and a valid filter combination with no matching rows produces a no-results state. The map route tracks catalogue failure but does not currently render a separate catalogue-error banner, so an empty map alone does not distinguish a valid empty response from a failed catalogue request. \subsection{deck.gl Earthquake Rendering and Selection}
\label{subsec:frontend_earthquake_rendering}

Earthquake points are rendered by a deck.gl \texttt{MapboxOverlay} attached to the MapLibre map. The filtered records are normalised into numeric longitude, latitude, and magnitude values, assigned their active colour, and sorted in ascending magnitude order. This ordering determines draw order so that larger-magnitude records are drawn after smaller ones. Magnitude does not determine marker radius in the current code: the visible radius varies with map zoom from approximately 2.5 to 5~pixels, and selection adds 2~pixels.

Two \texttt{ScatterplotLayer} instances use the same data. The visible layer is non-pickable and draws the coloured circles at 0.88 opacity. Its selected record receives a two-pixel white outline. A second transparent layer is pickable and uses three times the visible radius, creating a larger pointer target without changing the apparent symbol. Pointer hover changes the canvas cursor and a successful pick passes the corresponding catalogue record to the shared selection callback. In Heatmap mode both deck.gl layers are removed.

This arrangement keeps the basemap, raster modes, labels, heatmap, grid, faults, and volcanoes in MapLibre's geographic layer system while delegating the dense interactive earthquake point set to deck.gl. It is a single WebGL map composition, not a MapLibre canvas embedded inside another mapping library.

\subsection{Temporal and Magnitude Filtering}
\label{subsec:frontend_filtering}

The catalogue is downloaded independently of map filtering. \texttt{App.jsx} derives the visible subset in the browser whenever the selected calendar interval, magnitude threshold, or catalogue changes. Dates are parsed as UTC. In month precision, comparisons use inclusive year-month bounds; in day precision, inclusive year-month-day bounds are used. Records without a parseable date or numeric magnitude are excluded, and the magnitude condition is inclusive: an event remains visible when its magnitude is greater than or equal to the selected threshold.

\texttt{TimeWindowSlider.jsx} spans June~2020 to the current date and changes its presentation among year, month, week, and day resolutions. The user can zoom the temporal extent with the wheel or dedicated zoom buttons, shift it by dragging or touch movement, and then pass the resulting bounds to \texttt{App.jsx}. Updates to the parent filter are delayed briefly so continuous interaction does not immediately issue a React state update for every movement. The time control continues to filter in both colour modes and in Heatmap mode.

\texttt{MagnitudeScale.jsx} supplies the minimum-magnitude threshold and the magnitude legend. Its lower bound is 3.0. The display maximum is calculated as
\[
M_{\mathrm{display,max}}=\max\left(6,\left\lceil M_{\mathrm{catalogue,max}}\right\rceil\right),
\]
so the control retains a stable scale up to at least magnitude~6 while expanding to the next integer if a larger event is present. Whole-number tick labels are regenerated when this maximum changes. Filtering and colour ownership remain separate: changing the threshold changes membership of the displayed set, whereas changing colour mode changes its encoding.

\subsection{Timeline and Magnitude Colour Encodings}
\label{subsec:frontend_colour}

Timeline mode assigns colour by UTC year, not by calendar month and not by normalising against the active filter window. The general palette contains seven stops for 2020--2026, progressing from bright teal for the earliest year to deep navy for the latest year. Values outside that range are clamped to the nearest endpoint. Satellite mode substitutes a seven-stop pink-to-purple palette to maintain contrast over aerial imagery. The timeline track and marker functions use corresponding year stops.

Magnitude mode interpolates through a five-stop sequence from amber and orange through red to dark red. Its normalisation uses the fixed minimum magnitude and the dynamic display maximum defined above. The marker size is not used as a second magnitude encoding, so magnitude affects colour and draw order while zoom and selection control radius. When Timeline owns colour, the magnitude scale remains active as a filter but is visually muted; when Magnitude owns colour, the temporal control remains active but is visually muted.

These encodings describe implemented mappings only. Chapter~6 does not infer perceptual effectiveness or scientific meaning from the palettes; such claims would require separate evaluation.

\subsection{Heatmap and Contextual Overlays}
\label{subsec:frontend_overlays}

\paragraph{Heatmap.} Heatmap mode converts the currently supplied earthquake records to GeoJSON and renders them through a native MapLibre \texttt{heatmap} layer. The per-event weights are 0.20 below magnitude~4, 0.30 from magnitude~4 to below~5, and 0.45 at magnitude~5 or above. Radius is linearly interpolated from 34~pixels at zooms~4 and~6 to 24~pixels at zoom~8 and 16~pixels at zoom~12. Intensity rises from 0.75 at zoom~4 to 1.15 at zoom~8 and 1.4 at zoom~12, while opacity decreases at higher zoom. The seven-stop density gradient moves from transparent indigo through blue, teal, amber, and orange to red. A MapLibre control displays a low-to-high density legend. Because the mode represents aggregate density, marker picking, Recent Selections, and the fault overlay are unavailable while it is active. Entering Heatmap clears the selected earthquake and volcano, and the heatmap cannot select an individual event.

\paragraph{Volcanoes.} Volcano metadata are rendered with declarative MapLibre \texttt{Marker} elements using the application's volcano icon and an associated information card. The overlay can be toggled independently of earthquake filters. On desktop, enabling it opens \texttt{RightPanel}, which lists volcanoes alphabetically and allows the same selection state to be changed from the list or map. The right panel is not rendered on mobile. Volcano and earthquake selections are mutually exclusive, and a selected volcano is cleared automatically after 15~seconds.

\paragraph{Faults and fissures.} The tectonic overlay is requested on first use from the EGDI/HIKE WFS endpoint documented in Chapter~2 \cite{egdi_hike_iceland_tectonics}. Its promise and returned GeoJSON are cached for subsequent toggles. The request uses an Iceland bounding box, then retains features whose \texttt{country\_cd} is \texttt{IS} and excludes records whose observation method is \texttt{sonar survey}. The resulting geometry is supplied to a MapLibre line layer with an accompanying fault/fissure legend. \texttt{App.jsx} turns the overlay off when Heatmap is selected.

\paragraph{Latitude/longitude grid.} The optional grid is generated as GeoJSON line and symbol features for the current bounds. Longitude spacing decreases from $1^{\circ}$ at national zoom levels through intermediate values to $0.002^{\circ}$ at the highest configured levels; latitude spacing is half the corresponding longitude spacing. Label precision increases with zoom. Label positions are recalculated after movement and zoom completion and are shifted or suppressed to avoid the map-type selector, panels, attribution rail, and viewport edges. The grid remains independent of the earthquake filters and is available in all four map modes.

\subsection{Map--Insights Navigation and State Behaviour}
\label{subsec:frontend_map_insights}

\subsubsection{Route Lifecycle and Map Coordination}

The route is derived from the browser path and updated with the History API. Insights is loaded with \texttt{React.lazy} only when first requested. After that first mount, its container remains mounted and is hidden when the map route is active. This preserves both applied and draft Insights filters when the user returns to the map and later reopens Insights. The map container is likewise hidden rather than re-created by route navigation, so its filters and overlay choices remain in \texttt{App.jsx}.

The two routes share the downloaded catalogue but intentionally do not share filter controls. Insights can filter by date, magnitude range, depth range, depth-quality policy, data category, and time grouping without replacing the map's date window or minimum-magnitude threshold. Its View on map action finds the corresponding original catalogue event by date-time and coordinates, returns to the map, and focuses that event. If Heatmap is active it first changes to Map because individual-event selection is not available in Heatmap.

When the requested Insights event already satisfies the map filters, it is selected normally. If the active map filters exclude it, \texttt{App.jsx} appends that event as a temporary filter exception for 15~seconds. The existing map filters are not changed, and the exception is removed automatically. This makes the navigation target visible without silently rewriting either route's analytical state.

\subsubsection{Filter Initialisation and Depth Policy}

\texttt{AnalysisPage.jsx} first normalises the catalogue returned to \texttt{App.jsx}. It parses backend timestamps as UTC, converts coordinates and magnitude to numeric values, and assigns each row a presentation category of \texttt{matched} or \texttt{mpgv\_only}. Depth is treated separately: a finite depth on a matched row is labelled as a reference Quakes API value, a finite depth on an MPGV-only row is labelled as an unverified MPGV source value, and a missing or non-numeric depth is marked unavailable. This transformation is client-side presentation logic and does not modify the stored canonical record.

Initial filter bounds combine the client catalogue and backend policy metadata. The earliest usable event supplies the initial start date, while the current date supplies the upper calendar bound. In parallel, the page requests \texttt{/insights/limits} for both \texttt{reference\_only} and \texttt{include\_unverified}. Those responses provide the magnitude limits and the depth limits eligible under each policy. The analytical interface is initialised only after both the earthquake data and the two limits responses are available; changing the depth-quality policy replaces the depth bounds with the corresponding policy-specific range.

The filter component maintains a draft separate from the applied filter state. It supports inclusive start and end dates, minimum and maximum magnitude, minimum and maximum depth, source category, depth-quality policy, and day, week, month, or year time grouping. Numeric pairs are clamped to the available bounds, reversed minimum/maximum pairs are corrected at the edited boundary, and submission is rejected for invalid dates, negative or non-numeric values, ranges outside the catalogue bounds, or a minimum above its maximum. Reset restores the default full range with matched depths only.

The implementation deliberately distinguishes event selection from depth eligibility. Date, magnitude, and category determine the catalogue rows used for event counts, magnitude summaries, exports, and result tables. The selected depth range and depth-quality policy then determine which of those rows contribute to depth averages, shallowest and deepest values, the depth histogram, and the magnitude--depth scatter plot. An event without an eligible depth therefore remains in non-depth analysis instead of disappearing from the catalogue summary.

\subsubsection{Derived Summaries and Charts}

Normalisation, filtering, depth selection, and aggregate construction are memoised so that they are recomputed when their declared inputs change rather than on every render. The summary area reports eight values from the applied selection: event count, strongest event, average magnitude, average eligible depth, shallowest and deepest eligible events, and the matched and MPGV-only counts with percentages. A separate depth-quality statement records the number of reference depths and the number of unverified depths included or excluded by policy. When unverified MPGV depths are enabled, the interface adds a visible warning rather than presenting them as equivalent to matched Quakes API depths.

Five Recharts views are built from the same derived analysis. Magnitude distribution uses fixed 0.2-unit bins beginning at the catalogue threshold. Depth distribution uses adaptive bins and an overflow class for unusually large values, with reference and unverified depths separated when the latter are enabled. The magnitude--depth scatter plot retains the source category and depth provenance in its tooltip and uses a distinct symbol for unverified values. Average magnitude over time and event category over time use the selected day, week, month, or year grouping; empty periods inside the selected range are retained as zero-count buckets. The MPGV-only series in the category chart is displayed when the include-unverified policy is active. Both time charts provide a brush-controlled visible range and a reset action without changing the applied catalogue filters.

\subsubsection{Results, Export, and Failure States}

Below the charts, the page presents the ten most recent and ten strongest events from the applied catalogue selection. Each table displays five rows per page, can be sorted by date or magnitude, identifies matched and MPGV-only categories, labels the displayed source, and marks unverified depths. The View on map action uses the route coordination described above to restore the geographic context of the chosen record.

The CSV export contains every event in the applied catalogue selection together with date-time, coordinates, depth, magnitude, category, source, depth source, and depth-quality fields. It also prepends the export time, active filters, selected depth policy, and a depth-quality summary. The PDF action invokes the browser print workflow and relies on the page's print stylesheet; it is therefore a print-oriented export rather than a separately generated server document. Both actions are disabled when the applied selection is empty.

Loading and failure states are represented explicitly. A skeleton is shown until catalogue data, policy limits, and initial filters are ready. Catalogue and limits failures have separate retry paths, invalid filter input is exposed as an alert, and a valid filter combination with no matching events produces a no-results state instead of empty charts and tables. These states keep network failure, invalid input, and an empty analytical result distinguishable in the interface.

\subsection{Responsive and Accessibility Implementation}
\label{subsec:frontend_responsive_accessibility}

The primary responsive breakpoint is 767~pixels. On entry to the mobile layout the left drawer is collapsed; when returning to desktop, the previous desktop collapsed state is restored. The desktop volcano panel is omitted on mobile, control spacing and attribution are compacted, and the selected earthquake is presented inside the expanded left drawer instead of in a competing map card. CSS variables incorporate safe-area insets for devices whose browser viewport is interrupted by display cut-outs or system UI. Map resizing and grid-label placement react to the resulting panel dimensions. Insights has additional responsive rules for narrower chart, filter, and result-table layouts.

Accessibility support that is explicit in the implementation includes native buttons, checkboxes, and range inputs; accessible names on map actions; magnitude-slider value metadata and keyboard handling; keyboard-operable time zoom buttons; modal \texttt{dialog} and \texttt{aria-modal} semantics; focus placement on modal close buttons; Escape and backdrop dismissal; hidden-route state; and status or alert roles for Insights loading and error presentation. Decorative icons are generally hidden from the accessibility tree.

There are also implementation limitations. Earthquake markers are picked from the deck.gl canvas and are not individual keyboard-focusable elements. The custom draggable and wheel-operated time track does not expose complete keyboard semantics, although its zoom buttons are keyboard operable. The map-type button declares \texttt{aria-haspopup="listbox"} and expanded state, but the popup does not implement the corresponding complete listbox and option roles. These observations describe code-level support and gaps; they are not a claim of standards conformance or evaluated usability.

\section{Testing and Deployment}
\label{sec:testing-deployment}

\subsection{Chapter Scope}

This chapter verifies the implemented system through the automated backend and frontend suites, frontend linting and production-build checks, reproducible HTTP-level integration checks, and read-only inspection of the current University of Iceland Pluto deployment. The automated checks and public HTTP checks were repeated on 11~August~2026; the server-process inspection described below was performed on 10~August~2026. They establish observed software behaviour and deployment configuration; they are not a formal usability study, a performance benchmark, an availability guarantee, or a scientific validation of event matching.

\subsection{Backend Automated Testing}

The active backend suite uses pytest and the isolated application fixture at \path{backend/tests/conftest.py}. From the repository root, the Python interpreter in the project virtual environment executed \texttt{python -m pytest backend/tests -ra}. Pytest collected 114 tests: 113 passed and one was skipped. The skipped test is an opt-in live request to the EPOS volcano catalogue and requires \texttt{RUN\_LIVE\_EPOS\_TESTS=1}; keeping it disabled in the normal suite avoids making a successful test run depend on an external service.

The suite covers the major backend boundaries rather than only isolated helper functions. Source-acquisition tests exercise MPGV HTML parsing, candidate-catalogue completeness checks, malformed-row and abnormal-drop rejection, exact source identities, revisions, and the preservation of fractional timestamps. IMO Quakes API client tests check request construction and malformed-feature handling, while volcano tests cover the documented EPOS endpoint, its fallback response form, and empty responses.

Reconciliation tests cover accepted and rejected time, distance, and magnitude boundaries; MPGV-only output; depth-source policy; idempotent replacement; provenance diagnostics; and exclusion of API-only events. They also exercise two rules that are particularly important to the canonical catalogue: an ambiguous set of Quakes candidates remains MPGV-only, and one Quakes event cannot be assigned to more than one MPGV event. Regression cases retain distinct events with fractional timestamps and check that the replacement catalogue remains anchored one-to-one to the current MPGV source identities.

Application-level tests cover catalogue invariants, rollback behaviour, cache invalidation only after successful reconciliation, concurrent scheduler attempts, ingestion-lock recovery, and single scheduler ownership. The public and maintenance interfaces are checked for bounded query parameters and result limits, configurable route-specific rate limits, exemption of the health endpoint, administrative authentication, and safe handling of ShakeMap timestamps, coordinates, response types, and outbound URLs. Tests also cover Insights catalogue limits and the preservation of existing volcano or canonical rows when replacement fails.

These tests demonstrate that the implemented acquisition, reconciliation, locking, and delivery policies behave as encoded for the fixtures and regression cases. They do not establish that the reconciliation thresholds identify every physical earthquake correctly, measure false-match or missed-match rates against an independently labelled catalogue, or validate the scientific accuracy of the source observations.

\subsection{Frontend Testing and Build Verification}

The frontend package defines separate \texttt{test}, \texttt{lint}, and \texttt{build} scripts. Executing \texttt{npm test} in \texttt{frontend/} ran Vitest with React Testing Library and jsdom: all 77 tests in 13 test files passed. The suite is no longer limited to the TimeWindow slider. It covers time-window labels and zoom controls, magnitude display limits and keyboard input, numerical filter bounds, depth-quality policies, analysis transformations and ordering of fractional UTC timestamps, result tables, summaries, recent selections, and loading and error states.

Higher-level component tests verify coordination of the initial earthquake and volcano requests, preservation of Insights state across route changes, temporary display of an Insights-selected event outside the active map filters, and renewed ShakeMap lookup when an event is reselected. Architecture checks assert that the active map path uses MapLibre and deck.gl without Leaflet compatibility imports. Tests also exercise specific accessibility behaviour, including range metadata, vertical-key handling for magnitude controls, accessible analysis-range values, Escape dismissal, and disabled states. These checks support the stated behaviours but do not amount to accessibility conformance or browser-based usability testing; jsdom does not render the actual WebGL map.

The configured ESLint command, \texttt{npm run lint}, completed without errors. The production command, \texttt{npm run build}, also completed successfully and generated the Vite distribution. Vite emitted a non-fatal warning that some minified chunks exceed 500~kB. This is recorded as a build and future optimisation consideration, not as evidence of a measured performance problem.

\subsection{Integration and Manual Verification}

HTTP-level checks were made against the deployed application without changing server state. A request to \url{http://pluto.cs.hi.is/mpgv/} returned a permanent redirect to \url{https://pluto.cs.hi.is/mpgv/}. The HTTPS map route and \texttt{/mpgv/analysis} route both returned the built application successfully. The deployed HTML referenced JavaScript and CSS below \texttt{/mpgv/assets/}, and a referenced JavaScript bundle returned successfully. This confirms that the Vite base path and Flask frontend fallback are aligned for the public subpath.

The same-origin \texttt{/mpgv/earthquakes}, \texttt{/mpgv/volcanoes}, and \texttt{/mpgv/insights/limits} interfaces returned JSON successfully. The \texttt{/mpgv/health} endpoint also returned the expected MPGV, Quakes API, and canonical-table count fields. These are reproducible integration and catalogue-sanity checks only. No sample-user study, task-completion measurement, responsive-device inspection, scientific data-accuracy evaluation, or load test was performed as part of this verification pass.

\subsection{Current Pluto Deployment}

The publicly reachable instance is the project's current research deployment. It runs under the University of Iceland account at \texttt{\textasciitilde/iceland-quake} on Pluto, which reported Ubuntu~24.04.3~LTS during inspection. The public route is \url{https://pluto.cs.hi.is/mpgv/}. Public responses identify nginx, and the observed HTTP response redirects to HTTPS. Gunicorn itself listens only on \texttt{127.0.0.1:6000}; nginx therefore forms the public reverse-proxy boundary while TLS terminates outside the application process. The nginx configuration was not inspected, so the claims here are limited to the established deployment arrangement and externally observed responses rather than undocumented directive-level detail.

The running command uses Gunicorn with one worker, eight threads, the \texttt{gthread} worker class, a 120-second timeout, and a 5-second keep-alive. The PID recorded in \texttt{server.pid} referred to a live Gunicorn master, and the loopback port was listening during inspection. This is the verified current configuration, not a claim that the same settings are suitable for arbitrary traffic levels.

The repository-owned \texttt{deploy.sh} defaults to port~6000 and base path \texttt{/mpgv/}. It selects an available Python interpreter, creates or refreshes the backend virtual environment when required, installs the Python requirements, runs \texttt{npm ci}, and builds the frontend with \texttt{VITE\_BASE\_PATH} set to the normalised base path. It then stops the PID recorded for an existing instance and starts Gunicorn with output appended to \texttt{server.log}; \texttt{stop.sh} provides the corresponding PID-based stop operation. The deployed \texttt{frontend/dist/index.html} contained \texttt{/mpgv/} asset paths, confirming the production-build configuration rather than relying only on the script's intended behaviour.

Flask serves the built \texttt{frontend/dist} files and the single-page fallback from the same application that provides the JSON interfaces. The deployment is not stateless: the default SQLite database is retained under \texttt{backend/data}, while scheduler and ingestion ownership files are kept in the private \texttt{runtime} directory. The deployment script rebuilds generated dependencies and frontend assets but does not replace these persisted data directories. This allows data to survive ordinary application redeployments, although it is not a backup or disaster-recovery guarantee.

The active APScheduler job is configured for a three-minute interval with one instance at a time. Chapter~5 describes the process-lifetime scheduler-owner lock, ingestion lock, transaction boundaries, invariant checking, and cache update rules that guard scheduled work. The current single-worker Gunicorn configuration limits scheduler creation in this deployment, while the ownership and ingestion locks provide explicit safeguards if process topology changes or maintenance actions overlap. A live \texttt{scheduler-owner.lock} and successive completed ingestion entries approximately three minutes apart were observed during read-only inspection.

\subsection{Operational Boundaries and Limitations}

The verification establishes a working research deployment, but it does not establish service-level availability, automatic crash recovery, scalability, or readiness for institutional operations. The PID-and-log deployment model is repository controlled; no independent process-supervisor or restart policy was verified. SQLite, process-local caching, and any in-memory rate-limit storage constrain scale-out unless those components are replaced or shared. Actual private environment values were deliberately not inspected, so this chapter does not claim a particular secret configuration or rate-limit storage backend.

The application also depends on external catalogue, ShakeMap, volcano, fault, map-style, tile, font, and imagery services whose availability and licensing remain outside the Gunicorn process. The automated suites use mocks for most external paths and skip the live EPOS volcano check by default. The production build's large-chunk warning, incomplete keyboard semantics identified in Chapter~6, and the absence of formal usability, accessibility-conformance, performance, and scientifically labelled reconciliation studies remain explicit limitations. Deployment through the Icelandic Meteorological Office is a possible future direction rather than an established commitment.

\subsection{Summary}

The active repository passed 113 of 114 collected backend tests, with one deliberately skipped live external-service check; all 77 frontend tests passed, and both linting and the production build completed successfully. HTTP-level integration checks confirmed the HTTPS \texttt{/mpgv/} application, redirect behaviour, subpath assets, frontend routes, JSON interfaces, and health response. Read-only Pluto inspection confirmed the MapLibre/deck.gl build served by Flask behind nginx and a loopback Gunicorn process, together with the current port, worker and thread settings, SQLite persistence, and scheduler locks. These results verify implemented behaviour and the current research deployment within the stated operational and scientific limits.

\section{Future Development}
\label{sec:future-development}

The main parts of MPGV Monitor are now implemented: scheduled acquisition, MPGV-anchored reconciliation, the interactive map, the Insights page, export, responsive layouts, and the current research deployment. Future work should therefore concentrate on evaluating and strengthening this system rather than adding unrelated prediction features. The most useful next steps concern reconciliation evidence, source history, interaction design, and operation of the deployed service.

\subsection{Reconciliation Evaluation and Source Comparison}

The current reconciliation policy uses fixed limits of $|\Delta t| \leq 2$ seconds, distance below 10~km, and $|\Delta M| < 3.0$. It also requires an unambiguous one-to-one assignment. These rules are tested as software behaviour, but their scientific matching accuracy has not been measured against an independently reviewed catalogue. A useful next step would be to assemble a representative sample of matched, ambiguous, and MPGV-only events and review it with domain experts. Comparing the results under nearby threshold values would show which decisions are stable and where the current policy is sensitive.

The application already stores match status, source identifiers, and time, distance, and magnitude differences. The interface mainly uses this information to distinguish matched from MPGV-only records and to control depth analysis. A source-comparison view could show the MPGV and Quakes values side by side for a selected event, together with the recorded differences and the reason that no match was accepted. This would make the reconciliation process easier to inspect without presenting an uncertain candidate as a confirmed event identity.

\subsection{Acquisition, Revisions, and Catalogue Coverage}

The scheduler currently rebuilds the MPGV candidate from the discovered archive pages, fetches a rolling seven-day Quakes API window, and reconstructs the canonical catalogue. Validation checks prevent an empty, malformed, or unexpectedly reduced MPGV candidate from replacing the current state. This is suitable for the present catalogue, but repeated full-archive requests create unnecessary dependence on every historical page. Incremental acquisition with recorded checkpoints could reduce that work, provided that periodic full checks remain available to detect corrections to older pages.

MPGV source revisions are retained in the database, while the map and Insights page show only the accepted current version. Exposing a small revision history for an event would help explain changes in magnitude, depth, or coordinates over time. Operational logging could also report stale source data, repeated acquisition failures, and unusual revision volumes more clearly instead of requiring manual inspection of the server log.

The published catalogue starts on 1~June~2020 and contains MPGV events at $M_w \geq 3.0$. Extending that range or adding another earthquake source would require a new, explicit catalogue policy. Earlier coverage would need checks for changes in MPGV page structure and for the availability of suitable Quakes records. An additional source should first be stored separately and evaluated as a matching or context source; it should not automatically change catalogue membership.

\subsection{Interaction, Accessibility, and User Evaluation}

The current Insights page already provides summary values, magnitude and depth distributions, a magnitude--depth plot, temporal charts, result tables, and CSV and PDF-oriented export. A more useful extension than adding another general dashboard would be to support direct comparison. For example, users could compare two selected periods or inspect several events side by side while retaining their source status and depth provenance. A user-defined map area linked to the Insights filters could also connect geographic selection with the existing temporal and magnitude analysis.

Responsive layouts and several accessible control behaviours are implemented, but they have not been evaluated through a formal usability or accessibility study. The deck.gl earthquake markers are not individually keyboard focusable, the custom time track has incomplete keyboard semantics, and the map-type popup does not yet implement its full declared listbox pattern. These gaps should be addressed and then tested with keyboard and screen-reader users. Short task-based sessions with seismologists and other intended users would also show whether the terminology, provenance labels, filters, and connection between Map and Insights are understandable in practice. Mobile work should focus first on testing and improving the responsive web interface on real touch devices rather than assuming that a separate native application is required.

\subsection{Operational Robustness and Scale}

The Pluto instance is a working research deployment, but process startup, logs, and recovery are still managed through repository scripts and a PID file. A longer-running service would benefit from supervised startup, automatic restart, log rotation, database backups, and monitoring that alerts an administrator when ingestion or health checks fail. Recovery procedures should also be tested rather than inferred from the presence of database and lock files.

SQLite and the process-local catalogue cache fit the current single-instance configuration, and the application defaults to in-memory rate-limit storage. These choices would become constraints if the catalogue, request volume, or number of application workers grew substantially. PostgreSQL and shared cache or rate-limit storage would then be reasonable changes, but migration should be driven by measured load and concurrency requirements. The external map, imagery, font, fault, volcano, and ShakeMap services also need a provider and licensing review before any formal institutional deployment; self-hosting selected assets is one option, not a current feature.

\subsection{Summary}

The next stage should improve confidence in the reconciliation policy, make source differences and revisions easier to inspect, evaluate the existing interface with users, and strengthen deployment monitoring and recovery. These changes extend the completed catalogue-exploration system without turning it into a forecasting or hazard-assessment platform.

\section{Conclusion}
\label{sec:conclusion}
This thesis addressed two related problems. The first was how to provide geographic, temporal, and magnitude-based exploration of several years of Icelandic earthquake records. The second arose during development, when overlapping MPGV and IMO Quakes API records were found to differ in time, coordinates, magnitude, and depth. Displaying both feeds directly could create duplicate representations, while using either source without an explicit policy would hide how the displayed values had been chosen.

MPGV Monitor was designed and implemented as a React and Vite frontend with a Flask backend, SQLite persistence, and scheduled acquisition through APScheduler. MPGV defines catalogue membership: the published range begins on 1~June~2020 and includes MPGV events with $M_w \geq 3.0$. The Quakes API is used as a secondary matching and enrichment source. The current rules compare time, distance, and magnitude and accept only an unambiguous one-to-one assignment. A matched row keeps the exact MPGV time and MPGV robust-mean moment magnitude and uses the Quakes coordinates and depth. If no acceptable match is found, the event remains in the catalogue as MPGV-only; a Quakes-only event does not enter the catalogue by itself.

The final interface combines a MapLibre GL map with deck.gl earthquake layers. Users can explore the catalogue geographically, change the time window and minimum magnitude, switch between timeline and magnitude colour encodings, inspect events, and use the Map, Satellite, Terrain, and Heatmap modes. Volcanoes, faults and fissures, the coordinate grid, recent selections, and eligible ShakeMap links provide additional context. The connected Insights page adds filters, summary values, five charts, sortable result tables, depth-quality controls, export, and a return-to-map action. The responsive layout presents these functions on desktop and mobile-sized screens without maintaining a separate frontend.

The main technical contribution is the connection between this interactive exploration interface and an explicit, traceable reconciliation pipeline. Exact MPGV source identities, retained revisions, match diagnostics, conservative ambiguity handling, one-use Quakes assignment, transaction boundaries, and scheduler and ingestion locks make the implemented data policy inspectable. The frontend preserves that policy by exposing match categories and depth provenance instead of treating every depth value as equally reliable. Automated tests cover these implementation rules, API limits, interface state, filtering, and build behaviour. The application is also available as a current research deployment on Pluto through HTTPS.

Several limits remain. The matching thresholds have not been validated against an independently labelled event set, so the thesis does not establish scientific matching accuracy. The interface has not undergone formal usability or accessibility evaluation, and no performance or load benchmark establishes how it behaves at a substantially larger scale. The deployment still relies on SQLite, process-local state, repository-managed startup, externally operated nginx configuration, and several external data and map services. These are acceptable boundaries for the present research deployment, but they would need further work before stronger operational claims could be made.

The completed project demonstrates that an MPGV-anchored catalogue can be constructed while selected Quakes API records enrich it under a documented matching policy. It also provides one interface for geographic, temporal, magnitude-based, and aggregate exploration of the resulting records. The reasonable conclusion is therefore limited but useful: the system is a working foundation for traceable multi-source catalogue exploration. Further confidence should come from evaluation of the reconciliation policy, the interface, and the deployment rather than from adding prediction or hazard-assessment claims that the project was not designed to support.

\section{Installation and Running}
\label{app:installation}

This appendix explains how to set up a local development instance of MPGV Monitor from a fresh clone of the repository. The commands distinguish the activation step used by Windows from the corresponding POSIX-shell command. The repository also contains a Bash helper, \texttt{run-local.sh}, but the manual procedure below does not depend on that script.

\subsection*{Prerequisites}

\begin{itemize}
    \item Python 3.10 or later
    \item Node.js 18 or later (includes \texttt{npm})
    \item SQLite support (included with standard Python installations)
    \item Git
\end{itemize}

\subsection*{Clone the Repository}

\begin{verbatim}
git clone https://github.com/FaheemSajjad-dev/
           iceland-quake-monitoring-leaflet.git
cd iceland-quake-monitoring-leaflet
\end{verbatim}

\subsection*{Backend Setup}

\begin{enumerate}
    \item Create a Python virtual environment inside the \texttt{backend/} directory:
\begin{verbatim}
cd backend
python -m venv venv
\end{verbatim}

Activate it using the command for the current shell:
\begin{verbatim}
Windows Command Prompt: venv\Scripts\activate
PowerShell:             venv\Scripts\Activate.ps1
Linux / macOS:          source venv/bin/activate
\end{verbatim}

    \item Install the Python dependencies:
\begin{verbatim}
pip install -r requirements.txt
\end{verbatim}

    \item Start the Flask development server:
\begin{verbatim}
python app.py
\end{verbatim}

The development server listens on port~\textbf{5001} by default, matching \path{frontend/src/api.js}. Direct execution enables the background scheduler unless it is disabled through configuration. The SQLite schema is created when the application starts, but a new database is not synchronously populated before the server begins listening. The first scheduled acquisition runs after the configured interval, or a fresh deployment can be populated through the protected \texttt{POST /initialize-data} maintenance route. Normal scheduled work rebuilds the MPGV candidate, fetches the latest seven days from the Quakes API, reconciles the selected catalogue range, and refreshes volcano metadata.
\end{enumerate}

\subsection*{Frontend Setup}

\begin{enumerate}
    \item In a second terminal, install the exact Node.js dependency versions recorded by the lock file:
\begin{verbatim}
cd frontend
npm ci
\end{verbatim}

    \item Start the Vite development server:
\begin{verbatim}
npm run dev
\end{verbatim}

    \item Open \texttt{http://localhost:5174} in a browser. The frontend expects the backend at \texttt{http://localhost:5001}; this base URL is set in \texttt{frontend/src/api.js} and can be changed for different environments.
\end{enumerate}

\subsection*{Running Tests}

Backend unit and integration tests (114 collected in the current suite):
\begin{verbatim}
cd backend
python -m pytest tests/ -v
\end{verbatim}

Frontend component and utility tests (77 tests in 13 files):
\begin{verbatim}
cd frontend
npm test
\end{verbatim}

The frontend lint and production-build checks are:
\begin{verbatim}
npm run lint
npm run build
\end{verbatim}

At the final verification, 113 backend tests passed and the opt-in live EPOS test was skipped; all 77 frontend tests passed. Test totals are snapshots of the repository and should be updated if the suite changes.

\subsection*{Common Issues}

\begin{itemize}
    \item \textbf{Port already in use:} The defaults are 5001 for Flask and 5174 for Vite. If the backend port is changed through \texttt{PORT} or \texttt{BACKEND\_PORT}, the local URL constructed in \texttt{frontend/src/api.js} must be changed to the same value.
    \item \textbf{Missing \texttt{venv} on Linux:} Some distributions package \texttt{venv} separately. Install it with \texttt{sudo apt install python3-venv} (Debian/Ubuntu).
    \item \textbf{Empty fresh database:} Starting Flask creates the tables but does not block until external acquisition has completed. Keep the scheduler enabled and allow a scheduled cycle to finish, or use the authenticated initialisation route. The application should not be expected to show catalogue data before one of those paths succeeds.
    \item \textbf{External-source failure:} MPGV, Quakes API, EPOS, tile, and WFS services are network dependencies. Acquisition and contextual-layer failures are logged, while the safeguards described in Chapters~4 and~5 preserve previously accepted catalogue state where applicable.
\end{itemize}

\subsection*{Example: \texttt{/earthquakes} Response}

Each element in the returned JSON array has the following field structure; the values below are illustrative rather than a reported catalogue result:

\begin{verbatim}
{
    "Date-time":  "2025-11-22 13:45:07",
    "Latitude":   63.8912,
    "Longitude": -22.3456,
    "Depth":      5.10,
    "Mw_mean":    3.40,
    "status":     "matched",
    "mpgv_source_id": "2025-11-22 13:45:07"
}
\end{verbatim}

The \texttt{status} field is either \texttt{matched}, meaning that one Quakes API record was accepted for the MPGV event, or \texttt{v\_only}, meaning that the MPGV event remains unmatched under the current policy. The canonical table does not create \texttt{s\_only} rows. The public JSON also carries the exact MPGV source identity; the fuller source relationship and numerical match diagnostics remain in the database model.
